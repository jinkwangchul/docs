MASTER_SPEC_추가갱신_Execution_Request_order_executions_설계_2026-07-03

작성 목적
- 본 문서는 ORDER_QUEUED 이후 실제 SendOrder 호출 직전/직후의 실행 요청 단위(Execution Request)를 정의하기 위한 MASTER_SPEC 추가 갱신자료이다.
- 본 문서는 코드 구현 문서가 아니라 order_id, execution_id, kiwoom_order_no 관계를 고정하기 위한 데이터/상태 설계 문서이다.
- 현재 단계에서 SendOrder, KiwoomOrderExecutor, order_executions.json 실제 생성, 상태값 코드 추가는 금지한다.

==================================================
1. 배경
==================================================

현재 주문 파이프라인은 아래 단계까지 설계/검증되었다.

PENDING
  ↓ Approval Engine
APPROVED / BLOCKED
  ↓ Operation Policy Gate
EXECUTABLE / BLOCKED_POLICY
  ↓ Real Preflight
REAL_READY / BLOCKED_REAL
  ↓ Adapter Request Preview
REAL_READY 유지
  ↓ ExecutionController, 향후
ORDER_QUEUED
  ↓ SendOrder, 향후
ORDER_SENT / ORDER_ACCEPTED / REJECTED

현재 ORDER_QUEUED 이후에는 실제 실행 요청 단위가 아직 정의되지 않았다.
따라서 order_queue의 order와 실제 키움 주문 요청 사이에 Execution Request 엔티티가 필요하다.

==================================================
2. Execution Request 정의
==================================================

Execution Request는 REAL_READY order를 실제 SendOrder 대상으로 올리는 실행 요청 단위이다.

의미:
- order 후보를 실제 주문 실행 파이프라인으로 넘긴 기록
- ORDER_QUEUED 이후 생성
- SendOrder 요청 파라미터, guard snapshot, lock 정보, 실행 시각을 보관
- Kiwoom 주문번호가 생기기 전까지 order와 실제 API 호출 사이의 연결 고리

Execution Request는 체결 결과가 아니다.
Execution Request는 주문 접수 완료도 아니다.
Execution Request는 “이 order를 실제 주문으로 요청하려 했다”는 실행 요청 기록이다.

==================================================
3. 생성 시점
==================================================

Execution Request는 아래 조건을 모두 만족할 때만 생성 가능하다.

- order.status == REAL_READY
- execution_enabled == true
- operator_confirmed == true
- real_trade_enabled == true
- kiwoom_logged_in == true
- account_selected == true
- account_no 존재
- order_type 확정
- hoga 확정
- quantity > 0
- order_intent.unresolved == false
- order_lock 획득 성공
- Adapter Request 생성 성공
- ExecutionController의 명시 호출 존재

생성 위치:
- REAL_READY -> ORDER_QUEUED 전환 시점
- 또는 ORDER_QUEUED 생성 직후

금지:
- PENDING/APPROVED/EXECUTABLE에서 생성 금지
- Adapter Preview만으로 생성 금지
- Timer 자동 생성 금지
- GUI 직접 생성 금지, Controller 경유 필요

==================================================
5. 주요 필드
==================================================

execution_id
- 실행 요청 단위 ID.
- order_id와 별도로 생성.
- SendOrder 시도/요청 기록을 추적하기 위한 핵심 ID.

order_id
- order_queue.orders[].id 참조.

source_signal_id
- routine_signals.json의 signal id 참조.

lock_id
- order_locks.json의 lock_id 참조, 향후.
- 중복 실행 방지 lock과 연결.

status
- Execution Request 자체 상태.
- 현재 코드에는 추가하지 않는다.
- 후보:
  - REQUEST_PREPARED
  - SENDORDER_CALLED
  - ACCEPTED
  - REJECTED
  - ERROR
- 상태값 도입은 별도 승인 필요.

created_at
- Execution Request 생성 시각.

requested_at
- SendOrder 호출 시각.

account_no
- 실행 시점 계좌번호.

code / side / quantity / price
- 실행 요청의 핵심 주문 정보.

order_type / hoga
- SendOrder 입력에 필요한 주문유형/호가구분.
- 아직 미확정이므로 Execution Request 구현 전 hoga/order_type 설계 필요.

request_preview
- Adapter Request Preview 결과 snapshot.

request_hash
- 동일 요청 중복 실행 방지를 위한 hash.

guard_snapshot
- 실행 직전 real_trade_guard snapshot.

operator_confirmed
- 실행 시점 operator_confirmed 값.

execution_enabled
- 실행 시점 order.execution_enabled 값.

kiwoom_order_no
- SendOrder 접수 이후 키움 주문번호.
- 생성 직후에는 null.

api_result_code / api_message
- SendOrder 반환 결과 또는 오류 메시지.

error
- 실행 요청 오류 정보.

==================================================
6. order_queue와의 관계
==================================================

order_queue는 주문 후보 및 lifecycle 중심 파일이다.
Execution Request는 실제 실행 요청 기록이다.

관계:
- order_queue.orders[].id == order_executions.executions[].order_id
- order_queue.orders[].source_signal_id == order_executions.executions[].source_signal_id

정책:
- order_queue는 현재 order 상태를 가진다.
- order_executions는 실행 요청 이력을 가진다.
- order_queue에 execution_id 요약 필드를 둘 수 있다.
- 실행 이력 상세는 order_executions.json으로 분리하는 것이 안전하다.

권장:
- order_queue order에 latest_execution_id 또는 execution_ids 요약 필드 추가 가능, 향후.
- 단, 현재 코드 추가 금지.

==================================================
7. Kiwoom Order와의 관계
==================================================

SendOrder 이후 키움 주문번호가 생기면 다음 관계가 형성된다.

Execution Request
  ↓ kiwoom_order_no
Kiwoom Order
  ↓ Chejan/Event
Fill

관계:
- execution.kiwoom_order_no -> 키움 주문번호
- fill.kiwoom_order_no -> execution.kiwoom_order_no
- fill.execution_id -> execution.execution_id
- fill.order_id -> order_id

정책:
- SendOrder 반환값만으로 FILLED 처리 금지.
- 키움 주문번호가 없으면 체결 이벤트 매칭이 불안정하므로 검토관리 대상 가능.
- kiwoom_order_no 매칭 실패 시 ERROR 또는 Review Management 후보.

==================================================
8. Execution Request와 Lock 관계
==================================================

Execution Request 생성 전 lock이 필요하다.

흐름:
REAL_READY
  ↓ lock 획득
ORDER_QUEUED
  ↓ execution 생성
Execution Request
  ↓ SendOrder

관계:
- execution.lock_id -> order_locks.lock_id
- lock.order_id -> execution.order_id
- lock.source_signal_id -> execution.source_signal_id

정책:
- lock 없이 Execution Request 생성 금지.
- lock 없이 SendOrder 호출 금지.
- execution 생성 후 lock은 ORDER_SENT/ACCEPTED/FILLED/ERROR 처리까지 유지한다.
- 재시작 시 lock과 execution 관계를 복원해야 한다.

==================================================
9. Execution Request 상태와 Order Lifecycle 관계
==================================================

Order Lifecycle:
REAL_READY
  -> ORDER_QUEUED
  -> ORDER_SENT
  -> ORDER_ACCEPTED / REJECTED
  -> PARTIAL_FILLED / FILLED

Execution Request:
REQUEST_PREPARED
  -> SENDORDER_CALLED
  -> ACCEPTED / REJECTED / ERROR

관계:
- Order status는 운영자가 보는 주문 생명주기 상태.
- Execution status는 실제 SendOrder 요청 처리 상태.
- 둘은 1:1로 완전히 같지 않다.
- order_queue는 최신 상태 요약.
- order_executions는 실행 요청 상세 기록.

현재 단계에서는 Execution Request 상태값을 코드에 추가하지 않는다.

==================================================
10. 중복 실행 방지
==================================================

중복 실행 방지 기준:
- 같은 order_id로 활성 execution이 이미 있으면 새 execution 생성 금지.
- 같은 source_signal_id로 실행 중인 order가 있으면 재검토.
- request_hash가 같은 요청은 중복 실행 금지.
- lock이 active이면 동일 order 실행 금지.

중복 검출 시:
- SendOrder 호출 금지.
- order status 변경 금지 또는 ERROR/검토관리 후보, 정책 확정 후.
- audit log 기록, 향후.

==================================================
11. 복구/재시작 정책
==================================================

프로그램 재시작 시 확인 대상:
- order_queue의 ORDER_QUEUED/ORDER_SENT 계열 order
- order_executions의 REQUEST_PREPARED/SENDORDER_CALLED 계열 execution
- order_locks active lock
- Kiwoom 서버 미체결/체결/잔고 상태

정책:
- execution은 있는데 kiwoom_order_no가 없으면 SendOrder 호출 여부 불명확.
- SendOrder 호출 여부가 불명확하면 자동 재호출 금지.
- 키움 서버 조회 후 상태 확정.
- 불일치하면 검토관리.

==================================================
14. 최종 결론
==================================================

Execution Request는 order_queue의 REAL_READY order를 실제 SendOrder 요청으로 넘기기 위한 실행 단위이다.

order_queue는 후보와 lifecycle 중심 파일이고,
order_executions는 실행 요청 상세 이력 파일이다.

Execution Request 없이 SendOrder를 바로 호출하면 재시작/중복주문/체결매칭/감사로그 추적이 어려워진다.

따라서 SendOrder 구현 전 execution_id, lock_id, request_hash, guard_snapshot, kiwoom_order_no 관계를 먼저 확정해야 한다.
