-   이벤트 중복 발생

7.  구현 원칙

-   UI는 상태 표시 역할에 집중
-   엔진은 상태 변경 요청만 수행

2.  계층 흐름 UI ↓ 설정 데이터(Model) ↓ rules.json ↓ 루틴 엔진 ↓ 메인

-   설정 복원

-   BUY/SELL/CANCEL 판단

9.  검증 체크리스트 □ UI→Model □ Model→JSON □ JSON→Model □ Model→Engine

MASTER_SPEC 누락보강 38 주제 : 예외 처리 및 복구 정책

1.  목적 예상하지 못한 오류, API 이상, 데이터 불일치, 프로그램 재시작
    등의 상황에서 프로젝트가 일관된 방식으로 복구되도록 공통 정책을
    정의한다.

-   예외 상황에서는 기능 수행보다 데이터 무결성을 우선한다.
-   자동 복구가 불가능하면 안전한 상태로 전환한다.
-   모든 예외는 기록 가능해야 한다.

3.  예외 유형 ① OpenAPI 연결 오류 ② 주문 실패 ③ 체결 데이터 불일치 ④
    UI-내부상태 불일치 ⑤ JSON 손상 ⑥ 프로그램 재시작 ⑦ 긴급정지 ⑧ 런타임
    예외

4.  복구 절차 ① 예외 감지 ② 영향 범위 확인 ③ 정상 상태 보존 ④ 복구 가능
    여부 판단 ⑤ 자동 복구 또는 안전 정지 ⑥ 로그 기록 ⑦ 운영자 확인(필요
    시)

5.  프로그램 재시작

-   재시작은 신규 시작이 아닌 복구 절차로 취급한다.
-   보유, 미체결, 미수, 미도 상태를 우선 확인한다.
-   무결성 검증 후 정상 운영 여부를 결정한다.

6.  긴급정지

-   신규 주문 즉시 차단

-   진행 중인 상태 유지

-   복구 절차 완료 후 운영 재개

-   복구 전 자동 재시작 금지

-   예외 처리는 공통 계층에서 수행한다.

-   UI는 예외를 표시만 한다.

-   루틴은 복구 정책을 직접 수행하지 않는다.

8.  검증 항목 □ 예외 감지 □ 복구 성공 □ 상태 동기화 □ 로그 생성 □ 데이터
    무결성 □ 정상 운영 복귀

-   복구 시나리오
-   자동 복구 정책
-   장애 등급 분류
-   복구 이력 관리

10. 결론 모든 예외는 동일한 복구 원칙을 따르며, 데이터의 일관성과
    안전성을 최우선으로 유지한다.
