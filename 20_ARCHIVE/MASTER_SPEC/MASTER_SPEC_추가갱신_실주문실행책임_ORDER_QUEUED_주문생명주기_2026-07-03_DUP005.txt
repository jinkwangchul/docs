MASTER_SPEC_추가갱신_실주문실행책임_ORDER_QUEUED_주문생명주기_2026-07-03

작성 목적
- 본 문서는 주문 파이프라인 Preview 단계 이후, 실제 SendOrder로 넘어가기 전에 반드시 확정해야 하는 실행 책임, ORDER_QUEUED 의미, 중복주문 방지, 주문 생명주기 정책을 고정하기 위한 MASTER_SPEC 추가 갱신자료이다.
- 본 문서는 코드 구현 문서가 아니라 실주문 전 실행 철학과 상태 모델을 정의하는 기준 문서이다.
- 현재 단계에서 SendOrder, Executor, Adapter 실호출, Timer/GUI 자동 연결은 금지 상태로 유지한다.

==================================================
1. 현재 확정된 이전 단계
==================================================

현재 주문 파이프라인은 아래 단계까지 안전하게 고정되어 있다.

PENDING
  ↓ Approval Engine
APPROVED / BLOCKED
  ↓ Operation Policy Gate 단건
EXECUTABLE / BLOCKED_POLICY
  ↓ Real Preflight 단건
REAL_READY / BLOCKED_REAL
  ↓ Adapter Request Preview
REAL_READY 유지

현재 의미:
- PENDING: 루틴 신호 기반 주문 후보.
- APPROVED: 후보 품질 검토 통과. 실주문 허용 아님.
- EXECUTABLE: 운영정책 게이트 통과. Real Preflight 검토 대상. 실주문 허용 아님.
- REAL_READY: Real Preflight 통과. 그래도 SendOrder 아님.
- Adapter Request Preview: 키움 요청 dict를 메모리로 검토. 상태 변경 없음.

현재 금지:
- ADAPTER_READY 공식 상태 사용 금지.
- ORDER_QUEUED 자동 생성 금지.
- SendOrder 호출 금지.
- execution_enabled 자동 true 전환 금지.
- operator_confirmed 자동 true 전환 금지.
- Executor/Adapter 자동 연결 금지.

==================================================
2. execution_enabled 책임 정의
==================================================

2.1 기본 원칙

execution_enabled는 "실제 주문 실행 허용 여부"를 나타내는 order 단위 최종 실행 플래그이다.

정책:
- 기본값은 항상 false.
- 후보 생성, Approval, Operation Policy Gate, Real Preflight, Adapter Preview 단계에서는 자동으로 true가 되면 안 된다.
- execution_enabled=true는 실주문 직전 별도 승인 절차에서만 가능하다.
- execution_enabled=true는 루틴 신호가 아니라 운영자/최종 실행 컨트롤의 책임이다.

2.2 true 전환 주체

execution_enabled=true 전환 주체는 아래 중 하나로 제한한다.

허용 후보:
1. 운영자 수동 승인 UI
2. 명시적 최종 실행 함수
3. 실매매 모드 전환 후 개별 order 승인
4. 향후 별도 Approval + Guard + Lock을 모두 통과한 실행 컨트롤

금지:
- routine_signal_probe가 true로 변경 금지.
- routine_signal_consumer가 true로 변경 금지.
- order_approval_engine이 true로 변경 금지.
- operation_policy_gate가 true로 변경 금지.
- real_order_preflight가 true로 변경 금지.
- kiwoom_order_adapter preview가 true로 변경 금지.
- Timer Tick에서 자동 true 전환 금지.

2.3 true 전환 전 필수 조건

execution_enabled=true 전환 전 아래 조건을 모두 확인해야 한다.

- order.status == REAL_READY
- real_trade_guard.real_trade_enabled == true
- real_trade_guard.operator_confirmed == true
- real_trade_guard.kiwoom_logged_in == true
- real_trade_guard.account_selected == true
- real_trade_guard.account_no 존재
- quantity > 0
- side가 BUY 또는 SELL
- order_type 확정
- hoga 확정
- 중복 주문 방지 lock 통과
- 종목 상태가 정상 운영 가능
- 미수/미도/잔량 충돌 없음
- 검토관리 대상 아님
- 실행 버튼/명시 호출 등 최종 실행 주체가 존재

==================================================
3. operator_confirmed 책임 정의
==================================================

3.1 기본 원칙

operator_confirmed는 실주문을 운영자가 확인했는지 나타내는 전역 guard 값이다.

정책:
- operator_confirmed는 order별 상태가 아니라 real_trade_guard.json의 전역 guard 항목이다.
- APPROVED -> EXECUTABLE 단계에서는 변경하지 않는다.
- EXECUTABLE -> REAL_READY 단계의 preflight guard에서 확인한다.
- operator_confirmed=true 설정 UI/함수는 별도 설계 전까지 구현 금지이다.

3.2 execution_enabled와의 차이

operator_confirmed:
- 운영자가 실매매 실행 조건을 확인했는지 여부.
- 전역 guard 성격.

execution_enabled:
- 특정 order가 실제 실행 가능하도록 허용되었는지 여부.
- order 단위 실행 플래그.

둘 다 true여야 SendOrder 검토가 가능하다.

==================================================
4. ORDER_QUEUED 공식 정의
==================================================

4.1 의미

ORDER_QUEUED는 실제 SendOrder 호출 직전 또는 SendOrder 호출 요청이 등록된 상태이다.

정책:
- ORDER_QUEUED는 preview 상태가 아니다.
- ORDER_QUEUED는 adapter preview 상태가 아니다.
- ORDER_QUEUED는 실제 주문 실행 파이프라인에 진입했다는 의미이다.
- ORDER_QUEUED부터는 실주문 위험 구간이다.

4.2 생성 조건

ORDER_QUEUED는 아래 조건을 모두 만족할 때만 생성할 수 있다.

- order.status == REAL_READY
- execution_enabled == true
- operator_confirmed == true
- real_trade_enabled == true
- kiwoom_logged_in == true
- account_selected == true
- account_no 존재
- Adapter request 생성 성공
- order_type/hoga 확정
- 중복 주문 lock 획득 성공
- 최종 실행 함수/버튼에서 명시 호출

4.3 생성 금지 조건

아래 경우 ORDER_QUEUED 생성 금지.

- status가 REAL_READY가 아님
- execution_enabled=false
- operator_confirmed=false
- real_trade_enabled=false
- 계좌 미선택
- 로그인 미확인
- quantity <= 0
- hoga/order_type 미확정
- 중복 주문 lock 실패
- 검토관리 대상 종목
- BLOCKED/BLOCKED_POLICY/BLOCKED_REAL 상태
- Adapter Preview만 수행한 경우

==================================================
5. ORDER_QUEUED 이후 상태
==================================================

공식 후보 흐름:

ORDER_QUEUED
  ↓ SendOrder 호출 결과
DONE / ERROR

단, 실제 키움 OpenAPI에서는 SendOrder 반환값만으로 체결 완료를 의미하지 않는다.
따라서 DONE의 의미는 단계별로 재정의가 필요하다.

현재 1차 정의:
- ORDER_QUEUED: SendOrder 호출 요청 등록 또는 호출 직전.
- DONE: SendOrder 요청 성공 또는 주문 접수 확인 이후 상태로 사용할 수 있으나, 체결 완료와 동일시 금지.
- ERROR: SendOrder 요청 실패, adapter request 생성 실패, API 오류, guard 실패, lock 실패 등.

향후 추가 검토 필요:
- ORDER_SENT
- ORDER_ACCEPTED
- PARTIAL_FILLED
- FILLED
- CANCEL_REQUESTED
- CANCELLED
- MODIFY_REQUESTED
- REJECTED

현재 단계에서는 새 상태값을 추가하지 않는다.
다만 장기적으로 DONE 하나로 주문 접수/체결 완료를 모두 표현하는 것은 부정확하므로 후속 설계가 필요하다.

==================================================
6. 중복주문 방지 Lock 설계 기준
==================================================

6.1 목적

중복주문 방지 lock은 동일 order가 Timer 반복, GUI 중복 클릭, 재시도, 프로그램 재시작 등으로 여러 번 SendOrder 되는 것을 막기 위한 장치이다.

6.2 lock 기준 후보

필수 lock key 후보:
- order_id
- source_signal_id
- stock_code
- side
- routine_name
- created_at 또는 signal_time
- order_intent_hash

권장 1차 lock:
- order_id 단위 lock

보조 lock:
- source_signal_id 단위 중복 방지
- stock_code + side + routine_name + signal_time 조합 중복 방지

6.3 lock 저장 위치 후보

- runtime/order_locks.json
- order_queue.json 내부 order.lock 정보
- runtime/order_execution_log.json

권장:
- 별도 runtime/order_locks.json
- order_queue.json에는 lock 상태 요약만 기록

6.4 lock 상태 후보

현재 새 상태값 추가는 금지이므로 lock은 order status가 아니라 별도 메타데이터로 둔다.

예:
- lock_acquired: true/false
- lock_id
- lock_reason
- lock_created_at
- lock_owner
- duplicate_blocked: true/false

6.5 lock 획득 시점

ORDER_QUEUED 생성 직전 lock 획득.
SendOrder 호출 전 다시 확인.

6.6 lock 해제 시점

- ERROR 발생 후 재시도 정책에 따라 해제 가능.
- CANCELLED/EXPIRED 시 해제 가능.
- DONE 이후에는 재주문 방지를 위해 일정 시간 유지.
- 프로그램 재시작 후에도 lock 복원 필요.

==================================================
7. Adapter Request Preview와 실행 요청 분리
==================================================

Adapter Request Preview:
- REAL_READY에서 가능.
- 파일 변경 없음.
- status 변경 없음.
- SendOrder 없음.
- 검토용 dict만 반환.

Execution Request:
- REAL_READY + execution_enabled=true + guard 통과 + lock 획득 이후.
- ORDER_QUEUED 생성 가능.
- SendOrder 직전 단계.

정책:
- Preview helper와 Execution helper는 반드시 분리한다.
- Preview 함수는 절대 queue 상태를 변경하지 않는다.
- Execution 함수는 preview 결과를 재사용하더라도 guard와 lock을 다시 검사한다.

==================================================

SendOrder 호출 전 반드시 아래를 재검증한다.

3. execution_enabled == true
4. real_trade_guard.real_trade_enabled == true
5. real_trade_guard.operator_confirmed == true
6. real_trade_guard.kiwoom_logged_in == true
7. real_trade_guard.account_selected == true
8. real_trade_guard.account_no 존재
9. order.account_no와 guard.account_no 일치
10. side in BUY/SELL
11. quantity > 0
12. price 정책 정상
13. order_type 확정
14. hoga 확정
15. stock_code 존재
16. routine/source_signal 연결 정상
17. 중복 주문 lock 획득
18. 검토관리/정지/마감/청산 상태와 충돌 없음
19. 미수/미도/잔량 정책과 충돌 없음
20. 최종 실행 호출 주체 명확

하나라도 실패하면 SendOrder 호출 금지.

==================================================
11. 최종 결론
==================================================

현재 프로젝트는 Adapter Request Preview까지 안전하게 도달했다.

이후 실주문으로 넘어가기 위해서는 코드 구현보다 아래 정책 고정이 우선이다.

- execution_enabled true 전환 주체
- operator_confirmed 전역 guard 책임
- ORDER_QUEUED 공식 의미
- 중복주문 방지 lock
- hoga/order_type 매핑
- SendOrder 전 최종 체크리스트

ADAPTER_READY는 공식 상태로 사용하지 않는다.
Adapter Preview는 메모리 검토 결과로만 유지한다.
ORDER_QUEUED부터 실주문 위험 구간으로 본다.
SendOrder는 위 조건이 모두 확정될 때까지 계속 금지한다.
