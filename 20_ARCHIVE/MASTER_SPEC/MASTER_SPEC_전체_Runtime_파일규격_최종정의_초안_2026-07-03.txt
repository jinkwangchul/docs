MASTER_SPEC_전체_Runtime_파일규격_최종정의_초안_2026-07-03

작성 목적
- 본 문서는 키움 자동매매 프로젝트의 runtime 계열 JSON/JSONL 파일 규격을 하나의 기준으로 통합하기 위한 초안이다.
- 기존 설계 문서에서 분산 정의된 routine_signals, order_queue, real_trade_guard, order_locks, order_executions, fills, positions, review_items, audit_log 등의 역할과 필드, 생성 시점, 수정 주체를 통합한다.
- 현재 문서는 구현 문서가 아니라 Runtime 파일 규격 기준 문서이다.
- 현재 단계에서 새 runtime 파일 생성, 기존 runtime 파일 구조 변경, 코드 수정은 하지 않는다.

==================================================
1. Runtime 파일 관리 기본 원칙
==================================================

1. Runtime 파일은 현재 실행 상태와 운영 상태를 보존하기 위한 파일이다.
2. Runtime 파일은 MASTER SPEC에 정의된 생성 주체와 수정 주체만 변경할 수 있다.
3. Preview 함수는 Runtime 파일을 변경하지 않는다.
4. 상태 전이는 반드시 담당 Controller/Engine/Gate를 통해서만 반영한다.
5. Runtime 파일 변경은 향후 Audit Log 기록 대상이다.
6. Runtime 파일 손상/불일치/관계 끊김은 자동 정상 처리하지 않고 Recovery 또는 검토관리 대상이다.
7. Runtime 파일의 ID 관계는 보존되어야 한다.
8. 실주문 관련 Runtime 파일은 SendOrder 연결 전까지 구현 금지 상태를 유지한다.

4. runtime/routine_signals.json
==================================================

역할
- 루틴 평가 결과 생성된 BUY/SELL/CANCEL 등 신호를 저장한다.

- routine_signal_queue
- routine_signal_consumer, 기존 처리 상태 반영 범위
- 향후 SignalController

  "updated_at": "datetime, optional",
  "routine": "지표추종매매",
  "engine": "optional",
  "code": "003550",
  "name": "LG",
  "signal": "BUY|SELL|CANCEL",
  "reason": "string",
  "matched_groups": [],
  "details": [],
  "signal_index": 0,
  "delay_bar": 0,
  "tick_key": "string",
  "status": "PENDING|PREVIEWED|BLOCKED|...",
  "source": "routine_signal_probe|manual_verification",
  "execution_enabled": false

관계
- id -> order_queue.orders[].source_signal_id

금지
- SendOrder 관련 필드 저장 금지.
- order_id 직접 생성 금지.

5. runtime/order_queue.json
==================================================

역할
- Signal에서 생성된 주문 후보와 주문 생명주기 상태를 관리하는 중심 파일이다.
- 현재는 PENDING~REAL_READY~Adapter Preview 전 단계까지 사용한다.
- ORDER_QUEUED 이후 실주문 영역은 아직 구현 금지이다.

생성 주체
- order_queue
- 향후 OrderCandidateController

수정 주체
- order_approval_engine: PENDING -> APPROVED/BLOCKED
- operation_policy_gate: APPROVED -> EXECUTABLE/BLOCKED_POLICY
- real_order_preflight: EXECUTABLE -> REAL_READY/BLOCKED_REAL
- 향후 ExecutionController: REAL_READY -> ORDER_QUEUED
- 향후 FillEventController: 체결 상태 반영, 설계 후

주요 구조
{
  "version": 1,
  "updated_at": "datetime",
  "orders": []
}

  "id": "order id",
  "source_signal_id": "signal id",
  "created_at": "datetime",
  "updated_at": "datetime",
  "routine": "지표추종매매",
  "code": "003550",
  "name": "LG",
  "side": "BUY|SELL",
  "quantity": 0,
  "price": 0.0,
  "amount": 0.0,
  "status": "PENDING|APPROVED|BLOCKED|EXECUTABLE|BLOCKED_POLICY|REAL_READY|BLOCKED_REAL|ORDER_QUEUED...",
  "candidate_status": "CANDIDATE_READY|NO_HOLDING_QTY|NEED_BUDGET|...",
  "order_type": "UNDECIDED",

  "order_intent": {},

6. runtime/real_trade_guard.json
==================================================

역할
- 실주문 전역 guard 상태를 저장한다.
- Real Preflight와 Final Execution Guard의 필수 입력이다.

생성 주체
- 명시 guard 관리 함수, 향후
- 기존 ensure_default_real_trade_guard는 호출 시 기본 차단 파일을 만들 수 있으므로 사용 위치 주의

수정 주체
- 향후 Guard UI/운영자 확인 절차
- Recovery/로그인/계좌 선택 동기화 계층, 설계 후

주요 필드
{
  "real_trade_enabled": false,
  "kiwoom_logged_in": false,
  "account_selected": false,
  "operator_confirmed": false,
  "account_no": ""
}

정책
- 기본값은 모두 차단.
- operator_confirmed=true 자동 설정 금지.
- real_trade_enabled=true 자동 설정 금지.
- order별 실행 허가가 아니라 전역 guard이다.

18. 다음 구현 전 확인사항
==================================================

Runtime 파일을 실제 구현하기 전 확인해야 할 것:

1. 해당 파일이 현재 단계에 필요한가?
2. 생성 주체가 문서상 정의되어 있는가?
3. 수정 주체가 하나로 제한되어 있는가?
4. ID 관계가 명확한가?
5. Recovery 시 검증 방법이 있는가?
6. Audit Log 대상인가?
7. Review Management와 연결되는가?
8. 테스트를 TemporaryDirectory 기반으로 만들 수 있는가?

19. 최종 결론
==================================================

Runtime 파일 규격은 프로젝트의 데이터 안정성 기준이다.

현재 실제로 안정화된 Runtime 파일은 routine_signals.json, order_queue.json, real_trade_guard.json 계열이다.

order_locks, order_executions, fills, positions, review_items, audit_log, close_history는 설계상 필요하지만 아직 구현 금지 상태이다.

새 Runtime 파일은 반드시 해당 Controller/Manager/Engine 책임과 테스트가 먼저 확정된 뒤 도입해야 한다.
