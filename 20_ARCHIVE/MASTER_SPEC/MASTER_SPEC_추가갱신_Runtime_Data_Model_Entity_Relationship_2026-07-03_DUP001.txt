MASTER_SPEC_추가갱신_Runtime_Data_Model_Entity_Relationship_2026-07-03

작성 목적
- 본 문서는 키움 자동매매 프로젝트의 runtime JSON 파일들이 어떤 엔티티를 담고, 서로 어떤 ID로 연결되는지 정의하기 위한 MASTER_SPEC 추가 갱신자료이다.
- 지금까지는 주문 파이프라인의 Process Flow를 설계했다.
- 본 문서는 Process Flow와 짝을 이루는 Runtime Data Model / Entity Relationship 기준 문서이다.
- 현재 단계에서 코드 수정, 파일 구조 변경, 새 JSON 파일 생성은 하지 않는다.

==================================================
1. 현재 프로젝트 데이터 구조의 핵심 문제
==================================================

현재 프로젝트는 파일 기반 Runtime 구조를 사용한다.

대표 파일:
- runtime/routine_signals.json
- runtime/order_queue.json
- runtime/real_trade_guard.json
- runtime/orders.json
- runtime/state.json
- runtime/positions.json 또는 종목별 state/config 계열
- runtime/log 계열
- candles.json
- latest_price.json

현재는 각 파일이 기능별로 존재하지만, 장기적으로 다음 질문에 답할 수 있어야 한다.

- 이 order는 어떤 signal에서 왔는가?
- 이 signal은 어떤 routine이 만들었는가?
- 이 order는 어떤 execution으로 이어졌는가?
- 이 execution은 어떤 Kiwoom 주문번호와 연결되는가?
- 이 fill은 어떤 order의 일부인가?
- 이 position은 어떤 fill/order에서 생겼는가?
- 이 position은 어떤 close order로 종료되었는가?
- 오류/검토관리 항목은 어떤 signal/order/execution에서 유래했는가?

이 관계가 정의되지 않으면 재시작, 복구, 검토관리, 체결 추적, 로그 분석이 어려워진다.

==================================================
2. Runtime Entity 전체 개념도
==================================================

권장 엔티티 흐름:

Routine
  ↓ generates
Signal
  ↓ source_signal_id
Order Candidate
  ↓ order_id
Order Queue
  ↓ execution_id
Execution Request
  ↓ kiwoom_order_no
Kiwoom Order
  ↓ fill_id
Fill
  ↓ position_id
Position
  ↓ close_order_id
Close / Exit History

보조 흐름:

Order / Execution
  ↓ error_id / review_id
Review Management

Order / Execution / Fill
  ↓ log_id
Audit Log

==================================================
3. 주요 엔티티 정의
==================================================

3.1 Routine

의미:
- 매매 판단 로직 단위.
- 예: 지표추종매매.

주요 식별자:
- routine_name
- routine_id, 향후 가능
- routine_path
- rules_path
- engine

관계:
- Routine은 Signal을 생성한다.
- Signal은 routine/routine_name/engine을 통해 Routine과 연결된다.

현재 저장 위치 후보:
- routines/{루틴명}/routine.json
- routines/{루틴명}/rules.json
- routine registry

3.2 Signal

의미:
- 루틴 평가 결과 생성된 BUY/SELL/CANCEL 등 신호.
- 주문 후보의 출처.

현재 저장 위치:
- runtime/routine_signals.json

주요 필드:
- id
- created_at
- updated_at
- routine
- code
- name
- signal
- reason
- matched_groups
- details
- signal_index
- delay_bar
- tick_key
- status
- source
- execution_enabled

권장 관계 필드:
- id = signal_id
- routine
- engine, 향후 보존 권장
- code
- tick_key

연결:
- Order Candidate는 source_signal_id로 Signal에 연결된다.
- order_provenance.source_signal_id = Signal.id.

3.3 Order Candidate / Order Queue

의미:
- Signal을 기반으로 생성된 주문 후보.
- 아직 실주문이 아니다.

현재 저장 위치:
- runtime/order_queue.json

주요 필드:
- id 또는 order_id
- source_signal_id
- code
- name
- side
- quantity
- price
- amount
- status
- candidate_status
- execution_enabled
- order_type
- order_intent
- order_provenance

관계:
- source_signal_id -> routine_signals.json.id
- order_provenance.source_signal_id -> routine_signals.json.id
- order_intent는 주문방식/가격방식 의도 메타데이터
- order_provenance는 신호 출처 추적 메타데이터

상태 흐름:
- PENDING
- APPROVED / BLOCKED
- EXECUTABLE / BLOCKED_POLICY
- REAL_READY / BLOCKED_REAL
- ORDER_QUEUED 이후는 실주문 위험 구간

3.4 Execution Request

의미:
- REAL_READY order를 실제 SendOrder 호출 대상으로 올린 실행 요청.
- ORDER_QUEUED부터 Execution Request로 본다.

현재 상태:
- 아직 미구현.
- 설계 대상.

권장 저장 위치 후보:
- runtime/order_queue.json 내부 order의 execution 섹션
- runtime/order_executions.json 별도 파일
- runtime/order_execution_log.json

권장 식별자:
- execution_id
- order_id
- source_signal_id
- created_at
- requested_at
- lock_id
- account_no
- request_preview_hash
- send_order_request

관계:
- execution.order_id -> order_queue.orders[].id
- execution.source_signal_id -> routine_signals.json.id

3.5 Kiwoom Order

의미:
- 키움 API가 접수한 실제 주문.
- SendOrder 이후 키움 주문번호/접수번호와 연결된다.

현재 상태:
- 아직 미구현.

권장 필드:
- kiwoom_order_no
- original_order_no
- order_id
- execution_id
- account_no
- code
- side
- order_qty
- order_price
- hoga
- order_type
- accepted_at
- api_result_code
- api_message

관계:
- kiwoom_order.order_id -> order_queue.orders[].id
- kiwoom_order.execution_id -> Execution Request
- kiwoom_order.kiwoom_order_no -> Fill / Chejan Event 매칭 기준

3.6 Fill

의미:
- 실제 체결 정보.
- 부분체결/전량체결 모두 Fill 이벤트로 누적한다.

현재 상태:
- 아직 미구현.

권장 저장 위치:
- runtime/fills.json
- 또는 종목별 fill_history.json

권장 필드:
- fill_id
- kiwoom_order_no
- order_id
- execution_id
- code
- side
- fill_qty
- fill_price
- fill_amount
- remaining_qty
- fill_time
- event_source
- raw_chejan

관계:
- fill.kiwoom_order_no -> Kiwoom Order
- fill.order_id -> Order Queue
- fill.execution_id -> Execution Request
- fill.position_id -> Position, 향후

3.7 Position

의미:
- 현재 보유 상태.
- 여러 fill의 결과로 만들어질 수 있다.

현재 저장 위치 후보:
- 종목별 state/config
- runtime/positions.json, 향후 필요
- Kiwoom 잔고조회 결과

권장 필드:
- position_id
- code
- name
- holding_qty
- available_qty
- avg_price
- total_buy_amount
- realized_pnl
- unrealized_pnl
- source_order_ids
- source_fill_ids
- updated_at
- verified_by_kiwoom

관계:
- position.source_fill_ids -> fills.fill_id
- position.source_order_ids -> order_queue.orders[].id

3.8 Close / Exit History

의미:
- 포지션 종료, 청산, 마감, 매도 완료 이력.

권장 저장 위치:
- runtime/close_history.json
- 종목별 history 파일

권장 필드:
- close_history_id
- position_id
- close_order_id
- close_fill_ids
- code
- reason
- close_type
- requested_at
- completed_at
- pnl
- status

관계:
- close_history.position_id -> Position
- close_history.close_order_id -> Order Queue
- close_history.close_fill_ids -> Fill

3.9 Review Management

의미:
- 불일치/오류/검토 필요 상태를 관리하는 엔티티.

현재 프로젝트 개념:
- 검토관리
- 미수/미도/보유/잔량 불일치
- 서버 정보와 내부 정보 불일치
- 재시작/긴급정지 후 복구 검토

권장 관계:
- review_id
- related_signal_id
- related_order_id
- related_execution_id
- related_position_id
- related_fill_id
- reason
- severity
- created_at
- resolved_at

정책:
- 불명확한 실주문/체결/잔량 상태는 자동 해결하지 않고 검토관리로 보낸다.

3.10 Audit Log

의미:
- 상태 전이, 파일 변경, API 호출, 사용자 승인, 에러를 기록하는 감사 로그.

권장 저장 위치:
- runtime/audit_log.jsonl
- logs/order_pipeline.log

권장 필드:
- log_id
- timestamp
- actor
- action
- entity_type
- entity_id
- from_status
- to_status
- reason
- details
- file_path

==================================================
4. 핵심 ID 연결 규칙
==================================================

4.1 signal_id

정의:
- routine_signals.json의 id.

사용처:
- order_queue.source_signal_id
- order_provenance.source_signal_id
- execution.source_signal_id
- audit_log.entity_id, 필요 시

규칙:
- 한 signal은 0개 또는 1개 이상의 order 후보를 만들 수 있다.
- 중복 후보 생성 방지를 위해 source_signal_id 기준 추적 필요.

4.2 order_id

정의:
- order_queue.orders[].id.

사용처:
- execution.order_id
- fill.order_id
- position.source_order_ids
- close_history.close_order_id
- review.related_order_id
- audit_log.entity_id

규칙:
- order_id는 주문 후보부터 lifecycle 전체에서 유지되는 핵심 ID이다.
- order_id 없이 SendOrder 금지.

4.3 execution_id

정의:
- 실제 실행 요청 단위 ID.
- ORDER_QUEUED 이후 생성.

사용처:
- SendOrder request
- Kiwoom Order
- Fill
- Audit Log

규칙:
- order_id 하나가 여러 execution_id를 가질 수 있는지는 향후 재시도 정책에서 결정한다.
- 1차 정책은 order_id 1개당 execution_id 1개가 안전하다.

4.4 kiwoom_order_no

정의:
- 키움 서버 주문번호/접수번호.

사용처:
- Chejan/Event 매칭
- Fill
- Cancel/Modify

규칙:
- Kiwoom 체결 이벤트는 kiwoom_order_no 기준으로 order/execution에 매핑한다.
- kiwoom_order_no 매칭 실패 시 검토관리 대상.

4.5 fill_id

정의:
- 체결 이벤트 단위 ID.

사용처:
- Position source_fill_ids
- Close History close_fill_ids

규칙:
- 부분체결마다 별도 fill_id를 가진다.
- 전량체결도 하나 이상의 fill 이벤트로 구성될 수 있다.

4.6 position_id

정의:
- 종목별 보유 포지션 단위 ID.

사용처:
- Close History
- Review Management
- Audit Log

규칙:
- position은 Kiwoom 잔고와 내부 fill 누적 결과를 비교하여 관리한다.
- 불일치 시 검토관리 대상.

5. 파일별 역할과 관계
==================================================

runtime/routine_signals.json
- Signal 엔티티 저장.
- order_queue의 source_signal_id가 참조.

runtime/order_queue.json
- Order Candidate / Order Lifecycle의 중심 파일.
- order_id, source_signal_id, order_intent, order_provenance 포함.
- 실주문 전후 lifecycle 상태 관리 후보.

runtime/real_trade_guard.json
- 실주문 전역 guard.
- operator_confirmed, real_trade_enabled, 로그인/계좌 확인 등.
- order_queue와 직접 부모자식 관계는 아니지만 preflight/execution의 필수 조건.

runtime/order_locks.json, 향후
- 중복주문 방지 lock 저장 후보.
- order_id/source_signal_id/execution_id와 연결.

runtime/order_executions.json, 향후
- ORDER_QUEUED 이후 실행 요청 저장 후보.
- order_id, execution_id 연결.

runtime/fills.json, 향후
- 체결 이벤트 저장 후보.
- kiwoom_order_no, order_id, execution_id 연결.

runtime/positions.json, 향후
- 보유 포지션 저장 후보.
- fill_id/order_id 기반 또는 Kiwoom 잔고조회 기반.

runtime/review_items.json, 향후
- 검토관리 항목 저장 후보.
- signal/order/execution/fill/position과 연결.

logs/order_pipeline.log 또는 runtime/audit_log.jsonl, 향후
- 상태 전이 감사 로그.

candles.json
- 루틴 평가 입력 데이터.
- 향후 source_candle_time/source_candle_snapshot을 signal/order_provenance에 연결 가능.

latest_price.json
- order_candidate_engine의 price_basis 근거.
- order_intent.price_basis에 반영 가능.

6. Runtime 관계도
==================================================

Routine
  └─ routine_name / engine
      ↓
Signal
  └─ signal_id
      ↓ source_signal_id
Order Queue
  └─ order_id
      ↓ execution_id
Execution Request
  └─ execution_id
      ↓ kiwoom_order_no
Kiwoom Order
  └─ kiwoom_order_no
      ↓ fill_id
Fill
  └─ fill_id
      ↓ position_id
Position
  └─ position_id
      ↓ close_history_id
Close / Exit History

검토관리:
Signal / Order / Execution / Fill / Position
  ↓ related_*_id
Review Management

감사로그:
Any Entity
  ↓ entity_type + entity_id
Audit Log

7. 현재 확정된 메타데이터
==================================================

order_intent
- 주문 후보 산출 의도.
- hoga/order_type/UI source 미확정 진단.
- unresolved=true 기본.

order_provenance
- 주문 생성 이력.
- signal_id, routine, matched_groups, details, reason, signal_index 등 추적.
- source_ui_path/rule_path/setting_set은 현재 null.
- unresolved=true 기본.

두 필드는 order_queue.json의 order에 포함된다.

==================================================
9. 복구/재시작 기준
==================================================

프로그램 재시작 또는 긴급정지 해제 시 Runtime Data Model을 기준으로 관계를 재검증해야 한다.

검증 후보:
1. routine_signals.json의 PENDING/BLOCKED 신호
2. order_queue.json의 미완료 order
3. ORDER_QUEUED/ORDER_SENT 계열 주문, 향후
4. order_locks.json lock, 향후
5. Kiwoom 서버 미체결/잔고 조회
6. 내부 positions와 Kiwoom 잔고 비교
7. 매칭되지 않는 fill/order 검토관리 이동

원칙:
- 불명확한 관계는 자동 정상 처리하지 않는다.
- 내부 상태와 Kiwoom 서버 상태가 불일치하면 검토관리 또는 운영정지 우선.

==================================================
12. 최종 결론
==================================================

Runtime Data Model은 주문 파이프라인의 데이터 관계 기준이다.

Process Flow가 “무엇이 어떤 순서로 실행되는가”를 설명한다면,
Runtime Data Model은 “각 데이터가 어떤 ID로 연결되는가”를 설명한다.

현재 프로젝트가 실주문/체결/복구/검토관리로 확장되려면 signal_id, order_id, execution_id, kiwoom_order_no, fill_id, position_id의 관계를 먼저 고정해야 한다.

현재 단계에서는 문서 기준만 고정하고, 새 파일/상태/실주문 구현은 하지 않는다.
