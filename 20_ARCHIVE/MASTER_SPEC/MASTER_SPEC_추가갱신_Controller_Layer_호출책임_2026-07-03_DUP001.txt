MASTER_SPEC_추가갱신_Controller_Layer_호출책임_2026-07-03

작성 목적
- 본 문서는 주문 파이프라인 Preview 단계 이후, 각 Engine/Queue/Policy/Preflight/Adapter 모듈의 호출 책임을 분리하기 위한 Controller Layer 설계를 MASTER_SPEC에 반영하기 위한 추가 갱신자료이다.
- 본 문서는 코드 구현 문서가 아니라, 프로젝트 전체의 호출 책임(Orchestration)과 모듈 책임 분리를 정의하는 기준 문서이다.
- 현재 단계에서 Controller 구현, SendOrder 연결, Execution 연결, GUI/Timer 자동 연결은 금지한다.

==================================================
1. 현재 구조 요약
==================================================

현재 프로젝트는 다음 계층으로 분리되어 있다.

Layer 1. Routine Engine
- 루틴 평가
- BUY/SELL/CANCEL 신호 생성

Layer 2. Signal Pipeline
- routine_signals.json
- signal enqueue
- signal status 관리

Layer 3. Order Pipeline
- order_queue 후보 생성
- Approval Engine
- Operation Policy Gate
- Real Preflight
- Adapter Request Preview

Layer 4. Order Metadata
- order_intent
- order_provenance

현재 상태:
- 각 모듈의 단건 함수/검증 함수는 많이 정리되었다.
- 하지만 “누가 다음 단계를 호출하는가”라는 호출 책임이 아직 명확히 고정되지 않았다.

==================================================
2. Controller Layer 도입 목적
==================================================

Controller Layer는 새로운 판단 로직을 만드는 계층이 아니다.

목적:
- 각 모듈 호출 순서를 관리한다.
- 상태 전이 주체를 명확히 한다.
- 자동 실행과 수동 실행 경계를 분리한다.
- Timer/GUI/CLI가 직접 Engine을 막 호출하지 않도록 한다.
- 향후 SendOrder, 체결 이벤트, 취소/정정, 재시도까지 일관된 구조로 확장할 수 있게 한다.

Controller는 “무엇을 판단할지”를 결정하지 않는다.
판단은 기존 Engine/Policy/Preflight 모듈이 한다.

Controller는 “언제 어떤 순서로 호출할지”만 책임진다.

==================================================
3. Controller Layer 권장 구조
==================================================

권장 Controller 후보:

1. SignalController
2. OrderCandidateController
3. ApprovalController
4. OperationPolicyController
5. RealPreflightController
6. AdapterPreviewController
7. ExecutionController
8. FillEventController
9. CancelModifyController
10. RecoveryController

현재 구현 대상은 아니다.
우선 설계 기준으로만 고정한다.

==================================================
4. SignalController
==================================================

책임:
- Timer 또는 수동 호출에서 routine_signal_probe 실행을 조율한다.
- routine_signals.json에 PENDING 신호가 생성되는 흐름을 관리한다.
- signal_probe_only 조건을 확인한다.

호출 대상:
- routine_signal_probe
- routine_signal_queue

허용 전이:
- 없음. 신호 생성/등록만 담당한다.

금지:
- order_queue 생성 금지.
- Approval 호출 금지.
- Preflight 호출 금지.
- SendOrder 호출 금지.
- execution_enabled 변경 금지.

==================================================
5. OrderCandidateController
==================================================

책임:
- PENDING signal을 order_queue 후보로 변환하는 흐름을 조율한다.
- order_candidate_engine / order_queue를 호출한다.
- order_intent / order_provenance가 붙은 후보를 생성한다.

호출 대상:
- order_queue.signal_to_order_candidate()
- order_candidate_engine.build_order_candidate()

허용 전이:
- signal PENDING 기반 order PENDING 후보 생성.

금지:
- Approval 결과를 임의 결정 금지.
- EXECUTABLE/REAL_READY 생성 금지.
- hoga/order_type 확정 금지.
- SendOrder 호출 금지.
- execution_enabled=true 변경 금지.

==================================================
6. ApprovalController
==================================================

책임:
- order_queue의 PENDING order에 대해 Approval Engine을 호출한다.
- 후보 품질 검토 결과를 APPROVED/BLOCKED로 반영한다.

호출 대상:
- order_approval_engine.apply_order_approval_to_queue()

허용 전이:
- PENDING -> APPROVED
- PENDING -> BLOCKED

금지:
- APPROVED -> EXECUTABLE 전이 금지.
- Real Preflight 호출 금지.
- ORDER_QUEUED 생성 금지.
- SendOrder 호출 금지.
- execution_enabled 변경 금지.

==================================================
7. OperationPolicyController
==================================================

책임:
- APPROVED order를 운영정책 기준으로 Real Preflight 검토 대상으로 승격할지 결정하는 호출 흐름을 관리한다.
- 단건 수동 승격이 기본이다.

호출 대상:
- operation_policy_gate.apply_operation_policy_gate_for_order()

허용 전이:
- APPROVED -> EXECUTABLE
- APPROVED -> BLOCKED_POLICY

금지:
- 일괄 승격 금지.
- EXECUTABLE 이후 자동 Preflight 호출 금지.
- REAL_READY 생성 금지.
- execution_enabled=true 변경 금지.
- SendOrder 호출 금지.

==================================================
8. RealPreflightController
==================================================

책임:
- EXECUTABLE order에 대해 Real Preflight 단건 검사를 호출한다.
- real_trade_guard와 order 상태를 확인한 뒤 REAL_READY/BLOCKED_REAL 전이를 반영한다.

호출 대상:
- real_order_preflight.apply_real_order_preflight_for_order()

허용 전이:
- EXECUTABLE -> REAL_READY
- EXECUTABLE -> BLOCKED_REAL

금지:
- REAL_READY 이후 Adapter/Executor 자동 호출 금지.
- SendOrder 호출 금지.
- execution_enabled=true 변경 금지.
- operator_confirmed=true 변경 금지.
- ORDER_QUEUED 생성 금지.

==================================================
9. AdapterPreviewController
==================================================

책임:
- REAL_READY order에 대해 키움 주문 요청 preview dict를 생성한다.
- 파일 상태를 변경하지 않는다.

호출 대상:
- kiwoom_order_adapter.build_kiwoom_order_request_preview_for_order()

허용 결과:
- request_preview 메모리 dict 생성.
- status 변경 없음.
- REAL_READY 유지.

금지:
- ADAPTER_READY 생성 금지.
- ORDER_QUEUED 생성 금지.
- send_order_stub 호출 금지.
- SendOrder 호출 금지.
- queue 파일 수정 금지.

==================================================
10. ExecutionController
==================================================

책임:
- REAL_READY order를 실제 실행 파이프라인에 올릴지 최종 판단하는 계층.
- ORDER_QUEUED 생성의 유일한 주체가 되어야 한다.
- 중복주문 lock, execution_enabled, operator_confirmed, guard, hoga/order_type을 모두 확인한다.

현재 상태:
- 설계만 존재.
- 구현 금지.

향후 호출 대상 후보:
- order_lock_manager
- final_execution_guard
- kiwoom_order_adapter request builder
- KiwoomOrderExecutor

허용 전이:
- REAL_READY -> ORDER_QUEUED

단, 아래 조건 모두 필요:
- execution_enabled == true
- operator_confirmed == true
- real_trade_enabled == true
- kiwoom_logged_in == true
- account_selected == true
- account_no 존재
- hoga/order_type 확정
- order_intent.unresolved == false
- 중복주문 lock 획득
- 최종 실행 호출 주체 존재

금지:
- 현재 구현 금지.
- SendOrder 직접 구현 금지.
- Timer 자동 연결 금지.
- execution_enabled 자동 true 전환 금지.

==================================================
11. FillEventController
==================================================

책임:
- 키움 체결/잔량/주문접수 이벤트를 받아 order lifecycle에 반영한다.
- PARTIAL_FILLED/FILLED/CANCELLED/MODIFIED 등 체결 이후 상태를 관리한다.

현재 상태:
- 설계만 존재.
- 구현 금지.

향후 허용 전이:
- ORDER_SENT -> ORDER_ACCEPTED
- ORDER_ACCEPTED -> PARTIAL_FILLED
- PARTIAL_FILLED -> FILLED
- ORDER_ACCEPTED -> FILLED
- CANCEL_REQUESTED -> CANCELLED
- MODIFY_REQUESTED -> MODIFIED

금지:
- SendOrder 반환값만으로 FILLED 처리 금지.
- 이벤트 없이 체결 상태 변경 금지.

==================================================
12. CancelModifyController
==================================================

책임:
- 주문 취소/정정 요청 흐름을 관리한다.
- 실제 취소/정정 완료는 키움 이벤트 또는 조회 확인 후 반영한다.

현재 상태:
- 설계만 존재.
- 구현 금지.

향후 허용 전이:
- ORDER_ACCEPTED/PARTIAL_FILLED -> CANCEL_REQUESTED
- ORDER_ACCEPTED/PARTIAL_FILLED -> MODIFY_REQUESTED
- CANCEL_REQUESTED -> CANCELLED/CANCEL_REJECTED
- MODIFY_REQUESTED -> MODIFIED/MODIFY_REJECTED

금지:
- 취소 요청 직후 CANCELLED 처리 금지.
- 정정 요청 직후 MODIFIED 처리 금지.

==================================================
13. RecoveryController
==================================================

책임:
- 프로그램 재시작, 긴급정지 해제, 오류 복구 시 order_queue/order_locks/체결 상태를 재검토한다.
- 미완료 주문이나 불명확 상태를 검토관리로 보낼지 판단한다.

현재 상태:
- 설계만 존재.
- 구현 금지.

향후 역할:
- ORDER_QUEUED/ORDER_SENT 상태 복구
- lock 복원
- 미체결 주문 조회
- 주문 상태 불일치 감지
- 검토관리 이동 후보 식별

금지:
- 불명확 주문을 자동 DONE 처리 금지.
- 키움 상태 확인 없이 FILLED/CANCELLED 처리 금지.

==================================================
14. Timer/GUI/CLI와 Controller 관계
==================================================

원칙:
- Timer/GUI/CLI는 Engine을 직접 호출하지 않는 방향으로 점진 전환한다.
- Timer/GUI/CLI는 Controller를 호출하고, Controller가 Engine/Policy/Preflight를 호출한다.

현재는 기존 구조가 있으므로 즉시 전환하지 않는다.
신규 실주문 관련 흐름부터 Controller 중심으로 설계한다.

권장:
- Timer: SignalController까지만 자동 호출.
- signal_probe_only: OrderCandidate/Approval까지만 자동 호출 가능.
- OperationPolicy/RealPreflight 이후는 수동 또는 명시 호출.
- ExecutionController는 자동 Timer 연결 금지.
- GUI는 후보 목록/검토/승인 흐름을 Controller에 위임.

==================================================
17. 최종 결론
==================================================

Controller Layer는 새로운 판단 로직이 아니라 호출 책임을 분리하는 계층이다.

현재 프로젝트는 각 모듈의 단건 기능은 많이 정리되었으나, 다음 단계를 누가 호출하는지에 대한 Orchestration 기준이 부족하다.

앞으로 실주문, 체결, 취소, 정정, 복구 기능을 안정적으로 붙이려면 Controller Layer 설계를 먼저 고정해야 한다.

특히 ORDER_QUEUED 생성은 향후 ExecutionController만 담당해야 하며, Timer/Adapter Preview/Preflight가 자동으로 생성하면 안 된다.
