[핵심 운영 철학]
- 안정성 최우선
- 상태확인 없는 자동주문 금지
- 상태확인 없는 자동청산 금지
- 자동복귀 금지
- 문제 종목은 검토관리로 격리
- 계좌 단위 문제는 긴급정지
- 루틴은 신호 생성기
- 메인엔진은 실행 가능 여부 최종판정 + 주문집행 담당

[최신 상태 체계]
- 감시/대기
- 매수/매도
- 감시/매도
- 조기마감 또는 자동마감
- 긴급정지
- 검토관리/검토종목

[검토관리]
- 검토종목은 자동매매설정창 표시 금지
- 검토관리창 전용 관리
- 검토관리 컬럼: 코드 / 종목 / 위치 / 상태 / 사유 / 검출 / 보유 / 미수 / 미도 / 발생시간
- 임시 복귀 버튼 유지
- 자동복귀 금지

[적색상태]
- 내부 데이터 불일치
- 키움 서버 정보와 내부 정보 불일치
- 데이터 신뢰 불가
- 자동 검토관리 이동 금지
- 운영자 판단 후 안정성검사 수행

[재시작 정책]
프로그램 재시작 = 긴급정지 해제 = 매매시작 초기복구

보유/미수/미도 존재:
→ 검토관리

없음:
→ 종료상태
→ 시작 OFF

[표시 정책]
시작 OFF:
→ 상태 비활성
→ 방식 비활성

시작 ON + 감시/대기:
→ 방식 비활성
→ 청산 비활성

시작 ON + 매수/매도:
→ 방식 활성
→ 청산 활성

[현황 색상]
- 녹색: 정상 운영 가능
- 주황: 정상이나 다음 절차 진행 대상 없음
- 회색: 정지/비활성
- 빨강: 서버/프로그램 데이터 불일치 또는 데이터 신뢰 불가
- 선택행 하이라이트 색상은 현황 색상으로 해석하지 말 것

정규장 시간:
→ 매수/매도

장전 ATS 시간:

→ 조기마감/청산 정책 검사

장후 ATS + 조기마감 존재:
→ 감시/대기

장후 ATS + 청산정책 존재:
→ 감시/대기

장후 ATS + 차단정책 없음:
→ 매수/매도

표시:
- 수동: 보라
- 수동+ATS 전역설정: 보라
- 수동+ATS 개별설정: 주황

# MASTER_SPEC v1.1 대비 v1.2 변경점

## 목적

본 문서는 `MASTER_SPEC v1.1 Windows GUI Edition`과 `MASTER_SPEC v1.2 Structure Phase 2`의 차이를 정리한다.

v1.1은 원본 보존용 Legacy Reference이고, v1.2는 최신 구조개선 정책을 반영한 Current Master Spec이다.

---

# 1. 문서 지위 변경

## v1.1

- Windows GUI 기반 최초 확정 설계서.
- 기존 폴더 구조, 파일 구조, GUI 화면, 기본 자동매매 규칙 중심.

## v1.2

- 구조개선 2차 정책을 반영한 최신 기준 문서.
- 상태체계, 조기마감, 검토종목, 무결성 검사, 익일이월 정책을 재정립.

## 변경 의미

v1.1은 삭제하지 않고 보존한다.

앞으로 정책 판단과 코드 구조개선은 v1.2 기준으로 진행한다.

---

# 2. 상태체계 변경

## v1.1

- 기존 상태값과 GUI 표시가 혼재.
- 정지, 일시정지, 매도 홀딩, 상태 복구 등 여러 개념이 섞여 있음.

## v1.2

최종 상태를 6개로 정리.

- 감시/대기
- 매수/매도
- 감시/매도
- 조기마감
- 긴급정지
- 검토종목

## 폐기

- 정지
- 일시정지
- 전체대기
- 저강도 긴급정지
- 중강도 긴급정지
- 고강도 긴급정지

## 변경 의미

상태명이 운영자 기준으로 명확해졌고, 구버전 상태표시는 단계적으로 제거한다.

---

# 3. 긴급정지 정책 변경

## v1.1

- 긴급정지 버튼 중심.
- 전체 자동매매 정지 성격이 강함.

## v1.2

- 긴급정지를 단일 비상 상태로 정리.
- 다단계 긴급정지 폐기.
- 자동복귀 금지.
- 해제 시 무결성 검사 후 현재조건 재판정.

## 변경 의미

긴급정지는 단순 정지 버튼이 아니라 계좌 단위 위험을 차단하는 안전상태가 됨.

---

# 4. 검토종목 도입

## v1.1

- 문제 종목 격리 개념이 약함.
- 상태 불일치 발생 시 처리 기준이 충분히 분리되지 않음.

## v1.2

검토종목을 정식 상태로 도입.

검토종목은 자동매매 신뢰성이 훼손된 종목의 격리구역이다.

자동복귀 금지.

복귀는 수동 무결성 검사 후 현재조건 재판정으로만 가능.

## 변경 의미

A 종목 문제로 B 종목까지 멈추지 않게 하며, 문제 종목만 격리한다.

---

# 5. 검토위치 / 상세원인 분리

## v1.1

- 오류 사유나 로그 메시지 중심.

## v1.2

`진입사유` 대신 아래 두 값을 분리.

- 검토위치 = 문제 유형
- 상세원인 = 발생 원인

예:

```text
검토위치: 수량불일치
상세원인: HTS 수동매도
```

```text
검토위치: 주문불일치
상세원인: HTS 수동취소
```

## 변경 의미

운영자가 문제 위치와 원인을 빠르게 구분할 수 있다.

---

# 6. 감시/매도와 조기마감 분리

## v1.1

- 시간 종료, 정지, 매도전용 상태가 혼재할 수 있음.

## v1.2

감시/매도와 조기마감을 분리.

감시/매도:

- 일반 시간운영 종료 상태.
- 신규매수 금지.
- 루틴 매도정책 유지.

조기마감:

- 운영자가 명시적으로 실행한 예외적 정리 상태.
- 루틴 유지 + 시간조건 제거 + 즉시평가.

## 변경 의미

운영자는 일반 시간종료인지, 강제 조기정리인지 화면에서 바로 구분 가능하다.

---

# 7. 조기마감 정책 변경

## v1.1

- 장마감 또는 청산 중심 개념.
- 조기마감의 기본 동작이 명확히 분리되지 않음.

## v1.2

조기마감 기본값:

```text
루틴 유지
+ 시간조건 제거
+ 즉시평가
```

즉, 시장가 강제청산이 기본값이 아니다.

추가 옵션 후보:

- 현재가 청산
- 시장가 청산
- 지정가 청산
- 익절 N% 이상 청산
- 손절 N% 이하 청산
- 익일이월

## 변경 의미

조기마감은 루틴을 깨는 기능이 아니라 루틴을 가속하는 기능이다.

---

# 8. 익일이월 정책 변경

## v1.1

- 익일이월 후 재개 흐름이 명확하지 않음.

## v1.2

익일이월 발생 시 무조건 검토종목으로 이동.

```text
장마감 또는 조기마감
→ 익일이월
→ 검토종목
→ 수동 무결성 검사
→ 현재조건 재판정
```

자동복귀 금지.

## 변경 의미

익일이월 종목이 다음날 자동으로 정상 매매에 복귀하는 위험을 제거한다.

---

# 9. 무결성 검사 체계 변경

## v1.1

- 무결성검증 창 개념 존재.
- config/state/orders 중심 검증.

## v1.2

무결성 검사를 3종류로 재정의.

1. 자동 무결성 검사
2. 개별 무결성 검사
3. 전체 무결성 검사

공통 내부 단계:

```text
구조 무결성
→ 종목 무결성
→ 계좌 무결성
```

## 변경 의미

HTS/계좌 불일치뿐 아니라 파일/폴더 구조 변경, JSON 손상, 루틴 참조 누락까지 검사 범위에 포함한다.

---

# 10. 종목 등록 정책 변경

## v1.1

- 등록과 검증이 분리될 수 있음.

## v1.2

종목 등록 시 자동 무결성 검사를 내부 로직으로 수행.

검사:

- 보유수량 0
- 미체결 매수 0
- 미체결 매도 0
- 계좌조회 정상

종목등록창에는 별도 무결성 검사 버튼을 두지 않는다.

이상 발견 시 검토종목으로 이동 또는 검토종목 등록.

## 변경 의미

위험 종목이 정상 운영으로 들어오는 것을 등록 단계에서 차단한다.

---

# 11. 무결성 검사 버튼 위치 변경

## v1.1

- 무결성검증 창이 독립 기능으로 존재.

## v1.2

버튼 위치를 목적별로 분리.

- 자동검사: 종목 등록 / 프로그램 재시작 내부 자동 수행
- 개별검사: 검토종목 관리창
- 전체검사: 관제센터 도구 메뉴

## 변경 의미

사용자가 어떤 검사를 눌러야 하는지 헷갈리지 않도록 UI 흐름을 단순화한다.

---

# 12. 루틴과 메인엔진 책임 분리 강화

## v1.1

- 루틴 독립 운영 중심.
- 다중 루틴 가능성을 포함.

## v1.2

루틴은 신호 생성기.

메인엔진은 실행판정 및 주문집행 담당.

루틴은 주문을 직접 실행하지 않는다.

루틴은 시간판정, 긴급정지, 검토종목, 장마감 정책을 직접 처리하지 않는다.

## 변경 의미

루틴 로직과 안전 통제 로직을 분리하여 충돌 가능성을 줄인다.

---

# 13. 루틴 매도조건 확장

## v1.1

- MACD 매매 규칙 중심.

## v1.2

루틴은 아래와 같은 매매조건 조합을 허용한다.

예:


## [프로젝트 목표]

키움 OpenAPI를 이용한 Windows GUI 기반 자동매매 시스템 구축.

자동매매 루틴을 독립적으로 운영 가능하도록 설계한다.

동일 종목에 여러 자동매매 루틴을 동시 적용할 수 있어야 한다.

시스템 종료 후 재시작 시 자동 복구가 가능해야 한다.

모든 자동매매 루틴은 종목별 설정, 상태, 주문, 로그를 독립적으로 관리해야 한다.

사용자는 콘솔 명령어가 아니라 Windows 창에서 자동매매 상태를 확인하고 제어할 수 있어야 한다.

## [구현 UI 원칙]

1. 기본 UI는 Windows GUI 방식이다.

2. 콘솔 입력 방식은 개발자 디버그 용도로만 허용한다.

3. 일반 사용자는 버튼, 목록, 입력창, 확인창을 통해 기능을 실행한다.

4. 실계좌 실행, 종목 삭제, 초기화, 전체 자동매매 정지는 반드시 확인창을 표시한다.

5. 긴급 정지 버튼은 메인 윈도우에서 항상 접근 가능해야 한다.

6. 실행 중인 자동매매 종목은 표 형태로 표시한다.

7. 오류 발생 시 팝업 알림과 system_error.log 기록을 동시에 수행한다.

8. 자동매매 시작, 정지, 종목 삭제, 환경설정 변경은 PROJECT_CHANGELOG.txt 에 기록한다.

9. GUI는 내부 데이터 파일을 직접 수정하지 않고 관리자 기능 함수를 통해서만 수정한다.

10. GUI 표시값과 실제 파일 상태가 불일치할 경우 파일 상태를 기준으로 다시 로딩한다.

## [추천 GUI 프레임워크]

Python 기반 Windows 프로그램으로 구현한다.

추천 프레임워크 :

1순위 : PySide6

2순위 : PyQt5

3순위 : tkinter

추천 기준 :

PySide6는 현대적인 Windows GUI 구현에 적합하고 라이선스 측면에서도 비교적 안정적이다.

단, 키움 OpenAPI의 ActiveX 연동 제약이 있을 경우 PyQt5 사용을 허용한다.

최종 선택은 키움 OpenAPI 연동 테스트 결과에 따른다.

## [자동매매 루틴 규칙]

자동매매 루틴 폴더는 "_" 로 시작한다.

예)

_MACD매매루틴

_RSI매매루틴

_이격도매매루틴

프로그램 시작 시 자동 탐색한다.

GUI 출력 시 "_" 는 제거한다.

루틴 폴더명은 실제 루틴 식별값으로 사용한다.

단, 기초종목.txt 에 기록되는 루틴명은 사용자 표시용 명칭을 사용한다.

예)

폴더명 : _MACD매매루틴

표시명 : MACD매매루틴

기초종목.txt 기록명 : MACD

## [기초종목.txt]

역할 :

전체 종목 관리용 마스터 데이터

형식 :

종목코드,종목명,등록루틴1,등록루틴2,...

예)

005930,삼성전자,MACD

000660,SK하이닉스,MACD,RSI

930000,가상종목,MACD,이격도

규칙 :

1. 동일 종목코드 중복 등록 금지.

2. 동일 종목명 중복 등록 금지.

3. 동일 종목의 다중 루틴 등록 허용.

4. 동일 종목의 동일 루틴 중복 등록 금지.

5. 자동매매 루틴은 기초종목.txt 를 직접 수정할 수 없다.

6. 기초종목.txt 수정은 관리자 GUI 기능을 통해서만 가능하다.

7. 기초종목.txt 는 루틴 등록 현황의 기준 데이터이다.

8. 루틴 폴더와 기초종목.txt 의 정보가 충돌할 경우 기초종목.txt 를 우선 기준으로 삼는다.

---

## [종목별 저장 구조]

원본 기획의 코드_종목명.txt 단일 파일 방식은 사용하지 않는다.

대신 종목별 폴더 구조를 사용한다.

형식 :

_루틴명/종목코드_종목명/

예)

_MACD매매루틴/005930_삼성전자/

종목별 폴더 내부 구조 :

config.json

state.json

orders.json

logs/

규칙 :

1. 설정값은 config.json 에 저장한다.

2. 실행 상태와 복구 상태는 state.json 에 저장한다.

3. 주문 상태는 orders.json 에 저장한다.

4. 로그는 logs 폴더에 일별로 저장한다.

5. 설정, 상태, 주문, 로그를 하나의 파일에 혼합 저장하지 않는다.

---

## [config.json]

역할 :

종목별 자동매매 설정 저장

기본 구조 :

## [config.json 검증 규칙]

1. buy_amount 는 0보다 커야 한다.

2. buy_qty 는 0 이상이어야 한다.

3. trade_amount_type 이 AMOUNT 이면 buy_amount 를 사용한다.

4. trade_amount_type 이 QTY 이면 buy_qty 를 사용한다.

5. max_buy_count 는 1 이상이어야 한다.

6. buy_signal_bar 는 1 이상이어야 한다.

7. sell_signal_bar 는 1 이상이어야 한다.

8. daily_loss_limit 은 0 이하 값이어야 한다.

9. start_time 은 end_buy_time 보다 빨라야 한다.

10. timeframe 은 허용값만 사용할 수 있다.

11. budget_limit 은 0보다 커야 한다.

12. buy_amount_mode 가 CUSTOM 이면 buy_amount_custom_steps 는 비어 있으면 안 된다.

13. profit_hold_enabled 가 true 이면 profit_hold_percent 는 0 이상이어야 한다.

14. resell_condition 이 AVG_PRICE_PROFIT 이면 resell_profit_percent 는 0보다 커야 한다.

15. 검증 실패 시 해당 종목의 자동매매는 시작하지 않는다.

16. 검증 실패 내역은 GUI 팝업으로 표시하고 system_error.log 에 기록한다.

}

status 허용값 :

RUNNING

PAUSED

EMERGENCY_STOPPED

trade_set_status 허용값 :

3. state.json 은 보조 복구 데이터로 사용한다.

4. 실제 계좌 정보와 state.json 이 불일치하면 실제 계좌 정보를 우선한다.

5. 불일치 내역은 system_error.log 에 기록한다.

6. 불일치 발생 시 GUI 상태표시 영역에 경고를 표시한다.

## [budget.json]

역할 :

루틴 단위 예산 관리

위치 :

_루틴명/budget.json

기본 구조 :

{
  "routine": "MACD",
  "total_budget": 1000000,
  "used_budget": 0,
  "available_budget": 1000000,
  "reserved_order_budget": 0,
  "daily_realized_pnl": 0,
  "daily_loss_limit_percent": -3,
  "updated_at": "2026-05-31 09:00:00"
}

규칙 :

1. 예산은 루틴 단위로 관리한다.

2. 동일 루틴에 등록된 종목 전체가 해당 루틴 예산을 공유한다.

3. 주문 요청 중인 금액은 reserved_order_budget 으로 임시 차감한다.

4. 체결 완료 시 reserved_order_budget 에서 used_budget 으로 반영한다.

5. 주문 취소 또는 거부 시 reserved_order_budget 을 복원한다.

6. 예산 부족 시 신규 매수를 거부한다.

7. 예산 부족 메시지를 GUI 팝업으로 출력한다.

8. 예산 부족 내역은 로그에 기록한다.

9. 루틴별 예산은 메인 윈도우 루틴 목록에 표시한다.

## [검색식 등록 정책]

1. 키움 HTS에 사용자가 미리 생성한 "자동매매" 검색식을 호출한다.

2. 검색식 결과 종목을 기초종목.txt 에 등록한다.

3. 이미 등록된 종목은 중복 등록하지 않는다.

4. 종목코드와 종목명이 유효하지 않은 경우 등록하지 않는다.

5. 등록 완료 종목 수를 GUI 팝업으로 출력한다.

6. 중복 제외 종목 수를 GUI 팝업으로 출력한다.

7. 오류 종목 수를 GUI 팝업으로 출력한다.

8. 등록 결과는 PROJECT_CHANGELOG.txt 에 기록한다.

---

## [수동등록 정책]

1. 사용자는 종목코드와 종목명을 GUI 입력창에 직접 입력할 수 있다.

2. 입력 형식은 종목코드, 종목명이다.

3. 여러 종목은 등록 예정 목록에 추가 후 일괄 등록할 수 있다.

4. 동일 종목코드가 기초종목.txt 에 이미 존재하면 등록하지 않는다.

5. 동일 종목명이 기초종목.txt 에 이미 존재하면 등록하지 않는다.

6. 중복 항목은 "중복항목입니다" 팝업을 표시한다.

7. 등록 결과는 PROJECT_CHANGELOG.txt 에 기록한다.

---

## [매매루틴 지정 정책]

1. 기초종목.txt 에 등록된 종목만 매매루틴에 지정할 수 있다.

2. 동일 종목은 여러 매매루틴에 등록할 수 있다.

3. 동일 종목이 동일 매매루틴에 중복 등록되는 것은 금지한다.

4. 매매루틴 지정 시 기초종목.txt 의 해당 종목 행에 루틴명을 추가한다.

5. 동시에 해당 루틴 폴더 아래에 종목별 폴더를 생성한다.

6. 종목별 폴더명은 종목코드_종목명 형식으로 한다.

7. 이미 등록된 루틴은 GUI에서 체크된 상태로 표시한다.

8. 종목별 폴더 생성 시 config.json, state.json, orders.json, logs 폴더를 함께 생성한다.

9. 루틴 지정 결과는 PROJECT_CHANGELOG.txt 에 기록한다.

---

## [무결성 검증 정책]

1. 기초종목.txt 의 종목코드와 종목명을 키움 API 기준 실제 종목 정보와 비교한다.

2. 루틴 폴더 내 종목 폴더와 기초종목.txt 의 루틴 등록 정보를 비교한다.

3. 불일치 항목을 즉시 삭제하지 않는다.

4. 먼저 불일치 목록을 GUI 표로 출력한다.

5. invalid_items.log 에 기록한다.

6. 사용자 확인 후 삭제 또는 격리한다.

7. 삭제 또는 격리 결과를 PROJECT_CHANGELOG.txt 에 기록한다.

검증 대상 :

1. 기초종목.txt 중복 종목

2. 기초종목.txt 종목코드 오류

3. 기초종목.txt 종목명 오류

4. 루틴 폴더에는 있으나 기초종목.txt 에 없는 종목

5. 기초종목.txt 에는 있으나 루틴 폴더에 없는 종목

6. 종목 폴더명 형식 오류

7. 필수 파일 누락

필수 파일 :

config.json

state.json

orders.json

logs

## [중복 주문 방지 정책]

1. 동일 종목, 동일 루틴, 동일 봉에서는 매수 주문을 1회만 허용한다.

2. 동일 종목, 동일 루틴, 동일 봉에서는 매도 주문을 1회만 허용한다.

3. 주문 요청 후 체결, 취소, 거부, 실패 중 하나가 확정되기 전까지 추가 주문을 금지한다.

4. pending_order 가 true 인 경우 신규 주문을 발생시키지 않는다.

5. 마지막 신호 발생 봉 시간은 state.json 의 last_signal_candle_time 에 기록한다.

6. 마지막 주문 발생 봉 시간은 state.json 의 last_order_candle_time 에 기록한다.

7. 중복 주문 차단 내역은 로그에 기록한다.

8. 중복 주문 차단이 반복 발생하면 GUI 상태에 경고 표시한다.

## [MACD 매매 규칙]

0봉 정의 :

MACD 오실레이터 증가 또는 감소가 시작된 첫 번째 봉.

최저점 또는 최고점 자체가 아니다.

모든 계산은 봉 마감 후 수행한다.

## [MACD 계산 정책]

기본값 :

macd_fast_period = 12

macd_slow_period = 26

macd_signal_period = 9

min_candle_count = 100

규칙 :

1. MACD 계산에는 최소 100개 이상의 봉 데이터를 확보한다.

2. 데이터가 부족하면 매매 판단을 하지 않는다.

3. 불완전 봉은 계산에서 제외한다.

4. 모든 매수 / 매도 판단은 봉 마감 후 수행한다.

5. timeframe 은 config.json 설정값을 따른다.

6. 데이터 부족 상태는 GUI에 표시한다.

## [추가매수 제한 정책]

1. 동일 매매 세트 내 추가 매수 신호 발생 시 현재가를 직전 매수가와 비교한다.

2. 현재가가 직전 매수가보다 높으면 추가매수하지 않는다.

3. 기본값은 추가매수 금지이다.

4. config.json 의 allow_higher_rebuy 값이 true 인 경우에만 예외적으로 허용한다.

5. allow_higher_rebuy 기본값은 false 이다.

6. 추가매수 차단 내역은 로그에 기록한다.

---

## [매매 세트 상태 정책]

상태값 :

WAIT_BUY

BUY_ACTIVE

WAIT_SELL

SELL_DONE

흐름 :

WAIT_BUY → BUY_ACTIVE → WAIT_SELL → SELL_DONE → WAIT_BUY

규칙 :

1. 보유수량이 없는 상태에서는 매도신호를 무시한다.

2. 매도 완료 후 다음 매수신호가 나오기 전까지 매도신호를 무시한다.

3. 매수 발생 시 새로운 매매 세트를 시작한다.

4. 매도 발생 시 현재 매매 세트를 종료한다.

5. 현재 매매 세트 번호는 state.json 의 current_set_no 에 기록한다.

6. 매도신호 무시 상태는 state.json 의 ignore_sell_until_next_buy 에 기록한다.

7. 매매 세트 상태는 자동매매설정 창에 표시한다.

## [매수 회차]

최대 매수 회차는 사용자 설정값 max_buy_count 를 사용한다.

예)

1회

3회

5회

10회

설정 가능.

매수 회차 증가 방식은 buy_amount_mode 를 따른다.

ADD :

기준 금액 또는 수량에 지정값을 더한다.

MULTIPLY :

기준 금액 또는 수량에 지정 배수를 곱한다.

FIBONACCI :

피보나치 수열 기준으로 증가한다.

CUSTOM :

buy_amount_custom_steps 에 입력된 사용자 지정값을 사용한다.

CUSTOM 규칙 :

1. 입력값은 증가 연산자와 숫자 목록으로 구성한다.

2. 예: +1,2,5,8,9

3. 설정된 증가값 개수가 max_buy_count 보다 적으면 마지막 값을 반복 적용한다.

4. 설정된 증가값 개수가 max_buy_count 보다 많으면 max_buy_count 까지만 적용한다.

---

## [매도 홀딩 정책]

profit_hold_enabled 가 true 인 경우 적용한다.

규칙 :

1. 매도 신호 발생 시 예상 매도 손익을 계산한다.

2. 매수 평단에서 거래세 및 매도 비용을 제외하고 profit_hold_percent 이하이면 매도하지 않는다.

3. 매도하지 않은 경우 HOLD 상태로 기록한다.

4. 이후 재매도 조건은 resell_condition 을 따른다.

resell_condition :

NEXT_SELL_SIGNAL :

다음 매도 신호에서 다시 매도 판단한다.

AVG_PRICE_PROFIT :

평단 대비 resell_profit_percent 이상 상승 시 매도한다.

## [부분체결 정책]

부분체결 발생 시 미체결 수량 자동 취소.

체결 수량만 관리.

예)

10주 주문

4주 체결

6주 미체결

↓

6주 자동 취소

↓

4주만 관리

규칙 :

1. 부분체결 발생 시 orders.json 의 status 를 PARTIAL_FILLED 로 변경한다.

2. 미체결 수량 취소 요청 시 CANCEL_REQUESTED 로 변경한다.

3. 취소 완료 시 CANCELLED 로 변경한다.

4. 체결 수량만 state.json 에 반영한다.

5. 미체결 취소 실패 시 system_error.log 에 기록한다.

6. 미체결 취소 실패 시 GUI 알림을 출력한다.

# 0. 문서 지위

본 문서는 기존 `MASTER_SPEC v1.1 Windows GUI Edition`을 대체하는 최신 기준 문서이다.

단, v1.1 원본은 삭제하거나 직접 수정하지 않는다.

v1.1은 `Legacy Reference`로 보존한다.

v1.2는 구조개선 2차 정책 확정 내용을 반영한 `Current Master Spec`이다.

코드가 아직 v1.2를 완전히 반영하지 않았더라도, 이후 구조개선 및 OpenAPI 연결 전 정책 기준은 본 문서를 따른다.

---

# 1. 문서 목적

본 문서는 키움 OpenAPI 기반 자동매매 시스템의 최상위 기준 문서이다.

본 문서에 정의된 아래 항목은 구조개선 2차 이후의 기준으로 사용한다.

- 상태 체계
- 상태전이 규칙
- 시간운영 정책
- 수동운영 정책
- 조기마감 정책
- 장마감 / 익일이월 정책
- 검토종목 정책
- 긴급정지 정책
- 무결성 검사 체계
- 루틴과 메인엔진 책임 분리
- 파일 / 폴더 구조 방향
- GUI 관제 원칙
- 코드 반영 순서

기능 추가는 허용한다.

단, 본 문서의 상태 체계와 안전 정책을 깨는 변경은 금지한다.

---

# 2. 최상위 운영 철학

1. 안정성 최우선.
2. 상태확인 없는 자동주문 금지.
3. 상태확인 없는 자동청산 금지.
4. 상태확인 없는 자동복귀 금지.
5. 자동매매 신뢰성이 훼손된 종목은 검토종목으로 격리.
6. 계좌 단위 문제는 긴급정지.
7. 종목 단위 문제는 해당 종목만 격리.
8. 루틴은 신호 생성기이고, 메인엔진이 실행 가능 여부를 최종 판정한다.
9. 운영자는 GUI에서 상태와 문제 위치를 즉시 이해할 수 있어야 한다.
10. 기존 MASTER_SPEC v1.1은 원본 보존하고, v1.2부터 최신 정책을 반영한다.

---

# 3. v1.2에서 폐기하는 개념

아래 상태명 또는 개념은 최신 기준에서 폐기한다.

- 정지
- 일시정지
- 전체대기
- 저강도 긴급정지
- 중강도 긴급정지
- 고강도 긴급정지
- 긴급정지 해제 후 자동복귀
- 검토종목 자동복귀
- 익일이월 후 자동재개

주의:

예:

이 값들은 즉시 삭제하지 않고, 상태 매핑표와 영향 범위 검토 후 단계적으로 정리한다.

# 4. 최종 상태 체계

v1.2의 최종 상태는 아래 6개이다.

1. 감시/대기
2. 매수/매도
3. 감시/매도
4. 조기마감
5. 긴급정지
6. 검토종목

## 4.1 감시/대기

감시는 수행하지만 매수/매도 주문은 하지 않는 상태이다.

진입 예:

- 시작시간 이전
- 거래불가시간
- 보유수량 0
- 감시/매도 후 정리 완료
- 조기마감 후 전량 정리 완료

동작:

- 신규매수 금지
- 신규매도 금지
- 상태조회 가능
- 현재가 조회 가능
- 로그 확인 가능

이탈:

- 운영시간 시작 + 무결성 정상 + 검토종목 아님 + 긴급정지 아님 → 매수/매도

---

## 4.2 매수/매도

정상 자동매매 상태이다.

동작:

- 매수 가능
- 매도 가능
- 루틴 신호는 메인엔진의 최종 판정을 거쳐 실행

진입 조건:

- 운영시간 중
- 무결성 정상
- 검토종목 아님
- 긴급정지 아님
- 미체결 잠금 조건에 걸리지 않음

이탈:

- 운영시간 종료 → 감시/매도
- 조기마감 실행 → 조기마감
- 계좌 단위 문제 → 긴급정지
- 종목 단위 문제 → 검토종목

---

## 4.3 감시/매도

신규매수는 금지하고 매도만 허용하는 상태이다.

목적:

- 시간운영 종료 후 신규 진입을 막고, 보유 종목 정리만 허용

기본 동작:

- 매수신호 폐기
- 매도신호는 메인엔진 판정 후 실행 가능
- 기본 매도 판단은 루틴의 매도정책을 따른다
- +N% 익절, -N% 손절 등 루틴 기반 매도조건 허용

진입 예:

- 시간운영 종료
- 종료 후 정책이 감시/매도인 경우

이탈:

- 보유수량 0 → 감시/대기
- 조기마감 실행 → 조기마감
- 계좌 단위 문제 → 긴급정지
- 종목 단위 문제 → 검토종목

---

## 4.4 조기마감

운영자가 강제로 정리 절차를 시작한 상태 또는 표시상태이다.

조기마감은 감시/매도와 분리한다.

이유:

- 감시/매도는 일반 시간운영 종료 상태
- 조기마감은 운영자가 명시적으로 실행한 예외적 정리 상태

기본 동작:

- 신규매수 금지
- 루틴 유지
- 시간조건 제거
- 즉시 매도조건 평가

조기마감은 단순 시장가 강제청산이 아니다.

기본값:

```text
루틴 유지
+ 시간조건 제거
+ 즉시평가
```

예:

- 기존 루틴: 14:50 이후 매도 판단
- 조기마감 실행: 현재 시각 기준 즉시 매도 판단

추가 옵션 후보:

- 현재가 청산
- 시장가 청산
- 지정가 청산
- 익절 N% 이상 청산
- 손절 N% 이하 청산
- 익일이월

이탈:

- 전량 정리 완료 → 감시/대기
- 익일이월 → 검토종목
- 청산실패 → 검토종목
- 잔량발생 → 검토종목
- 계좌 단위 문제 → 긴급정지

---

## 4.5 긴급정지

계좌 단위 문제, 시스템 이상, API 이상, 운영자 강제중단 시 사용하는 비상 상태이다.

진입 예:

- 예수금 조회 실패
- 잔고 조회 실패
- 계좌 전체 조회 실패
- API 이상
- 주문 가능 상태 확인 실패
- 운영자 긴급정지

동작:

- 신규매수 금지
- 신규매도 금지
- 자동판단 중지
- 자동청산 중지
- 실시간 감시와 계좌조회는 가능하면 유지

해제:

```text
긴급정지 해제 요청
→ 무결성 검사
→ 현재조건 재판정
→ 복귀 또는 검토종목 이동 또는 긴급정지 유지
```

자동복귀:

- 금지

---

## 4.6 검토종목

자동매매 신뢰성이 훼손된 종목의 격리 상태이다.

검토종목은 자동매매 대상에서 제외한다.

진입 예:

- 수량불일치
- 주문불일치
- 잔고불일치
- 청산실패
- 잔량발생
- 익일이월
- 무결성실패
- 파일구조이상
- 설정파일이상
- 루틴 참조 누락

허용 기능:

- 상태조회
- 로그조회
- 미체결 취소
- 현재가 매도
- 시장가 매도
- 수동 무결성 검사
- 검토종목 해제 후보 처리

금지 기능:

- 자동매수
- 자동매도
- 루틴신호 자동실행
- 자동복귀
- 신규 루틴 자동연결

복귀:

```text
운영자 확인
→ 문제 해결
→ 수동 무결성 검사
→ 통과
→ 현재조건 재판정
→ 감시/대기 또는 매수/매도 또는 감시/매도
```

자동복귀:

- 금지

# 6. 루틴과 메인엔진 책임 분리

## 6.1 루틴 역할

루틴은 신호 생성기이다.

담당:

- 매수신호 생성
- 매도신호 생성
- 보유 또는 무신호 판단
- +N% 익절 조건 판단
- -N% 손절 조건 판단
- MACD 등 기술적 신호 판단
- 조기마감 시 시간조건 제거 후 즉시 평가

루틴은 주문을 직접 실행하지 않는다.

루틴은 시간판정, 긴급정지, 장마감 정책, 검토종목 정책을 직접 처리하지 않는다.

---

## 6.2 메인엔진 역할

메인엔진은 통합 통제기이다.

담당:

- 현재시간 판정
- 운영방식 판정
- 상태 판정
- 긴급정지 판정
- 검토종목 여부 판정
- 장마감 정책
- 조기마감 정책
- 이월 정책
- 미체결 주문 정책
- 계좌 무결성 검사
- 주문 실행 가능 여부 최종 결정
- 실제 주문 실행

원칙:

```text
루틴 = 신호 생성
메인엔진 = 실행 가능 여부 최종판정 + 주문집행
```

---

# 7. 루틴 매매조건 정책

루틴은 매수조건과 매도조건을 독립적으로 가질 수 있다.

예:

```text
매수 = MACD 조건
매도 = 매수가 대비 +N% 익절
매도 = 매수가 대비 -N% 손절
```

이 구조는 v1.2 상태체계와 충돌하지 않는다.

이유:

- 감시/매도는 매수만 금지하고 매도는 허용한다.
- 조기마감은 루틴 매도조건을 유지하되 시간조건만 제거한다.
- 긴급정지와 검토종목에서는 메인엔진이 주문 실행을 차단한다.

필수 입력:

- 매수가
- 현재가
- 수익률
- 보유수량
- 미체결 상태

---

# 8. 시간운영 정책

시간운영은 종목 또는 루틴에 설정된 운영시간을 기준으로 상태를 산출한다.

기본 흐름:

```text
시작시간 이전 → 감시/대기
운영시간 중 → 매수/매도
종료시간 이후 → 감시/매도
```

종료 후 기본 정책:

- 감시/매도

정지 표시명은 사용하지 않는다.

시간운영 종료 후 감시/매도 상태에서는 신규매수는 금지하고, 매도는 루틴의 매도정책을 따른다.

---

# 9. 수동운영 정책

수동운영은 시간운영 전역설정 영향을 직접 받지 않는다.

수동운영은 실제 거래 가능 시간 여부만 확인한다.

거래 가능 시간:

- 매수/매도 가능

거래 불가 시간:

- 감시/대기

거래구간 후보:

- 정규장
- 장전 시간외
- 장후 시간외
- 사용자 정의 구간

실제 주문 가능 여부는 키움 OpenAPI 또는 HTS의 거래 가능 상태를 우선한다.

---

# 10. 조기마감 정책

조기마감은 일반 감시/매도와 구분한다.

실행 위치:

- 상태 컬럼 우클릭 메뉴

좌클릭 정책:

- 수동 컬럼 클릭 → 수동운영 설정
- 시간 컬럼 클릭 → 시간운영 설정

우클릭 정책:

- 상태 컬럼 우클릭 → 조기마감, 긴급정지, 무결성 검사, 검토종목 이동 등 운영 명령

조기마감 기본값:

```text
루틴 유지
+ 시간조건 제거
+ 즉시평가
```

조기마감 후 상태 표시:

- 조기마감

감시/매도와 조기마감은 표시를 분리한다.

---

# 11. 장마감 / 청산정책

장마감 또는 조기마감 시 보유잔량을 확인한다.

청산정책 후보:

- 루틴 유지 + 시간조건 제거 + 즉시평가
- 현재가 청산
- 시장가 청산
- 지정가 청산
- 익절 N% 이상 청산
- 손절 N% 이하 청산
- 익일이월

청산 실패:

```text
청산실패
→ 검토종목
```

잔량 발생:

```text
잔량발생
→ 검토종목
```

익일이월:

```text
익일이월
→ 검토종목
```

# 12. 검토종목 정책

## 12.1 목적

검토종목은 자동매매 신뢰성이 훼손되었거나 운영자 확인이 필요한 종목을 자동운영에서 분리하여 관리하는 격리 영역이다.

---

## 12.2 검토위치와 상세원인

v1.2에서는 `진입사유`라는 단일 표현을 사용하지 않는다.

대신 아래 두 값을 분리한다.

```text
검토위치 = 문제 유형
상세원인 = 발생 원인
```

검토위치 예:

- 수량불일치
- 주문불일치
- 잔고불일치
- 청산실패
- 잔량발생
- 익일이월
- 무결성실패
- 파일구조이상
- 설정파일이상
- 루틴참조이상
- 기타

상세원인 예:

- HTS 수동매도
- HTS 수동매수
- HTS 수동취소
- API 조회 실패
- 프로그램 재시작
- 파일 누락
- JSON 손상
- 루틴 폴더 삭제
- 종목 폴더명 변경

HTS 수동개입은 검토위치가 아니라 상세원인으로 기록하는 것을 기본으로 한다.

예:

```text
검토위치: 수량불일치
상세원인: HTS 수동매도
```

```text
검토위치: 주문불일치
상세원인: HTS 수동취소
```

---

## 12.3 검토종목 필수 기록값

- 종목명
- 검토위치

# 13. 긴급정지 정책

긴급정지는 단일 체계로 운영한다.

다단계 긴급정지는 사용하지 않는다.

긴급정지 동작:

- 신규매수 금지
- 신규매도 금지
- 자동판단 중지
- 자동청산 중지
- 실시간 감시 유지
- 계좌조회 유지

긴급정지 해제:

```text
운영자 해제 요청
→ 무결성 검사
→ 현재조건 재판정
```

자동복귀:

- 금지

---

# 14. 무결성 검사 체계

무결성 검사는 3종류로 구분한다.

1. 자동 무결성 검사
2. 개별 무결성 검사
3. 전체 무결성 검사

공통 검사 순서:

```text
구조 무결성
→ 종목 무결성
→ 계좌 무결성
→ 최종판정
```

버튼은 1개로 유지하고 내부적으로 3단계를 순차 수행한다.

---

## 14.1 자동 무결성 검사

실행 시점:

- 종목 등록 시
- 프로그램 재시작 시

목적:

- 위험 종목이 정상 운영 상태로 진입하는 것을 차단

종목 등록 시 검사 항목:

- 보유수량 0 여부
- 미체결 매수 0 여부
- 미체결 매도 0 여부
- 계좌조회 정상 여부

판정:

- 정상 → 일반 등록 가능
- 이상 → 검토종목 이동

UI 원칙:

- 종목등록창에는 별도 무결성 검사 버튼을 두지 않는다.
- 등록 과정에서 내부 로직으로 자동 수행한다.

## 14.2 개별 무결성 검사

실행 위치:

- 검토종목 관리창

대상:

- 선택된 검토종목

목적:

- 검토종목이 정상 운영으로 복귀 가능한지 판정

흐름:

```text
검토종목 선택
→ 무결성 검사
→ 구조 무결성
→ 종목 무결성
→ 계좌 무결성
→ 통과 시 현재조건 재판정
→ 복귀 가능
```

실패 시:

- 검토종목 유지
- 실패 단계 기록
- 상세원인 기록

v1.2에서는 종목데이터 중앙집중화 방향을 채택한다.

목표 구조:

```text
kiwoom_auto/

├─ gui_routine_service.py
├─ gui_routine_guard.py
├─ gui_review_utils.py
├─ data/
│  └─ stocks/
│     └─ 005930_삼성전자/
│        ├─ state.json
│        ├─ orders.json
│        ├─ config.json
│        └─ stock_log.txt
├─ routines/
│  └─ 루틴명/
│     ├─ routine_config.json
│     └─ routine_logic.py
├─ logs/
│  ├─ operation.log
│  ├─ policy.log

   ├─ spec_archive/
   │  └─ MASTER_SPEC_v1.1_윈도우창버전_키움자동매매.txt
   └─ MASTER_SPEC_v1.2_structure_phase2.md
```

원칙:

- 종목별 상태, 주문, 설정은 종목데이터 쪽에 단일화한다.
- 루틴폴더는 루틴 설정과 신호 생성에 필요한 자료만 보유한다.
- `기초종목.txt`는 현재 루틴 지정 또는 종목 마스터 목록 역할만 담당한다.
- 실제 상태 판단은 중복된 루틴폴더 state가 아니라 중앙 종목데이터를 기준으로 한다.

주의:

- 기존 폴더 구조는 코드 영향 범위 검토 후 단계적으로 이관한다.
- 즉시 전체 이관하지 않는다.

# 16. 미체결 정책

현재 확정:

```text
동일 종목 미체결 존재 시 신규주문 금지
```

미체결 매수 존재:

- 신규매수 금지

미체결 매도 존재:

- 신규매도 금지 또는 기존 매도 주문 유지
- 세부정책은 주문정책 구현 단계에서 확정

보류:

- 장시간 미체결 자동취소
- 재주문 정책
- 부분체결 세부규칙
- 가격 허용범위

# 17. 상태 우선순위

상태 판정 우선순위는 아래 순서를 따른다.

1. 검토종목
2. 긴급정지
3. 계좌 무결성
4. 종목 무결성
5. 조기마감 / 청산정책
6. 운영방식
7. 루틴신호

원칙:

- 검토종목은 어떤 루틴신호보다 우선한다.
- 긴급정지는 일반 운영방식보다 우선한다.
- 계좌 단위 문제는 전체 긴급정지로 처리한다.
- 종목 단위 문제는 해당 종목만 검토종목으로 격리한다.

6. 루틴은 신호만 만들고 메인엔진이 실행 가능 여부를 판정한다.
7. 파일/폴더 구조 이상도 무결성 검사 대상에 포함한다.
8. MASTER_SPEC v1.1은 원본 보존하고 v1.2를 최신 기준으로 사용한다.

### 2.3 프로그램 재시작 정책 강화

재시작 시 기존 상태를 그대로 복구하지 않는다.

재시작 시:
- 현재시간
- 보유수량
- 미체결 매수
- 미체결 매도
- 검토종목 여부
- 긴급정지 여부
- 설정파일 상태

위 항목을 확인하고 현재조건을 재판정한다.

잔량/미수/미도 존재 시 검토종목 이동.

---

### 2.4 긴급정지 후 복구 정책

긴급정지 후 복구는 프로그램 재시작과 같은 레벨의 재판정 프로세스로 처리한다.

자동복귀 금지.

무결성 검사 후 현재조건 재판정.

---

### 2.5 익일이월 정책

익일이월은 자동재개하지 않는다.

익일이월 발생 시 검토종목 이동.
