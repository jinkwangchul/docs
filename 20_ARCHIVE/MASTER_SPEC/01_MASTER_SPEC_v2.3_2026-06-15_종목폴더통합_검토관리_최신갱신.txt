1. 현재 작업의 큰 흐름

이번 창의 핵심 작업은 “기초종목.txt 및 루틴폴더 내부 종목폴더 중심 구조”에서 “중앙 stocks/ 종목폴더 중심 구조”로 종목관리 기준을 통합하는 것이었다.

확정 방향:
- 종목 원본은 중앙 stocks/ 아래 종목폴더로 일원화한다.
- 루틴폴더는 루틴 정의와 예산 파일을 보관하는 역할만 유지한다.
- 루틴폴더 내부에 005930_삼성전자 같은 종목폴더를 다시 만들면 안 된다.
- 종목 등록/삭제와 루틴 지정/해제는 용어와 기능을 분리한다.
- 검토관리도 구형 루틴폴더가 아니라 중앙 stocks/state.json 기준으로 수집해야 한다.

2. 용어 정리 확정

종목관리 용어:
- 종목 등록: 중앙 stocks/ 종목관리 라이브러리에 종목을 추가한다.
- 종목 삭제: 중앙 stocks/ 종목관리 라이브러리에서 종목을 제거하거나 archive로 이동한다.
- “등록해제”라는 표현은 종목관리 문맥에서 사용하지 않는다.

루틴관리 용어:
- 루틴 지정: 등록된 종목에 MACD매매루틴 같은 자동매매 루틴을 연결한다.
- 루틴 해제: 종목은 유지하고 루틴 연결만 제거한다.

검토관리 용어:
- 검토관리 이동: 문제 종목을 자동매매 운영대상에서 제외하고 검토관리창에서 관리한다.
- 검토관리 복귀: 문제 원인 해소 후 운영자가 명시적으로 원래 운영 흐름으로 되돌린다.
- 복귀는 단순 플래그 제거가 아니다. 보유/미수/미도/평단/주문잔량/서버불일치 등 문제가 남아 있으면 복귀되어서는 안 된다.

3. 중앙 stocks 구조 관련 완료 사항

완료 또는 확인된 내용:
- 중앙 stocks/ 종목폴더 기준으로 종목 등록이 가능하다.
- 수동등록창에서 종목 등록이 가능하다.
- 수동등록창 헤더 정렬 기능을 추가했다.
- 수동등록창 우클릭 메뉴를 추가했다.
  - 전체 선택
  - 전체 해제
  - 선택 등록
- 매매루틴지정창에서 루틴 지정/해제가 가능하다.
- 루틴 지정 시 더 이상 _MACD매매루틴/종목폴더가 새로 생성되지 않도록 패치했다.

- 검토관리창은 중앙 stocks/state.json 기준으로 REVIEW_REQUIRED 또는 review_required=True 종목을 표시하도록 수정했다.
- 검토관리 버튼 카운트와 검토관리창 내부 목록이 일치하도록 load_review_items() 내부 직접 중앙 수집 방식을 추가했다.

4. 루틴폴더 관련 정리

루틴폴더 자체는 당장 삭제하지 않는다.
이유:
- _MACD매매루틴/
- _등록확인폴더/
같은 루틴폴더 안에 budget.json이 존재하며, 루틴 정의 또는 예산 정보 파일로 사용될 수 있다.

정리 기준:
- 루틴폴더 자체는 유지한다.
- budget.json은 유지한다.
- 루틴폴더 내부 종목폴더는 구형 구조 잔재로 보고 제거/archive 대상이다.
- 루틴폴더 내부 txt/zip 파일은 실제 운영 참조가 없으면 제거 가능하다.
- 사용자가 일부 잔재 파일을 직접 삭제했다.
- 삭제 후 프로그램이 정상 동작하면 해당 파일은 죽은 파일로 판정 가능하다.

주의:
- 루틴 지정 후 루틴폴더 내부에 새 종목폴더가 다시 생기면 아직 구형 생성 로직이 남은 것이다.
- 해당 버그는 ensure_stock_runtime_files(selected_routine_dir, code, name) 호출 경로를 제거하면서 해결했다.
- 이후에도 재발하면 gui_routine_assign_window.py, gui_config_utils.py, gui_stock_data.py에서 stock_runtime_dir_for_routine, ensure_stock_runtime_files, mkdir, makedirs, f"{code}_{name}" 계열을 재검색해야 한다.

7. 검토관리 관련 최신 판정

- 위치는 MACD매매루틴으로 표시된다.
- 상태는 미해결로 표시된다.
- 사유는 보유수량 있음 + 현재가 확인 불가 등으로 표시된다.
- 보유수량도 표시된다.

중요한 남은 버그/정책 확인:
- 검토관리 복귀 버튼이 문제 원인 검증 없이 review_required를 해제하면 안 된다.

- 테스트 중 사용자가 임의 입력 데이터를 삭제했기 때문에 해당 케이스는 다시 만들어 검증해야 한다.

- 재시작/검토/마감/청산 메타
는 자동매매설정창, 매매루틴지정창, 검토관리창 표시 및 판정의 기준이다.

orders.json 기준:
- 미체결/주문잔량 확인에 사용한다.
- 검토관리 복귀/삭제/미지정 가능 여부 판단에서 orders.json도 함께 봐야 한다.

검토관리 복귀 정책 보강:
- 복귀 버튼은 검토상태 해제 버튼이 아니다.
- 복귀 버튼은 현재 상태를 재판정한 뒤 문제가 없을 때만 검토상태를 해제해야 한다.
- 보유수량이 있으면 복귀 불가.
- 보유수량 0인데 평단 또는 보유금액이 남아 있으면 복귀 불가.
- 매수 미체결 또는 매도 미체결이 있으면 복귀 불가.
- 미수 또는 미도가 있으면 복귀 불가.
- 현재가 확인 불가가 복귀 불가 사유로 남아 있는 경우 복귀 불가.
- 서버/프로그램 정보 불일치가 있으면 복귀 불가.
- 복귀 가능 조건을 만족하지 못하면 검토관리창에서 계속 유지해야 한다.

핵심 철학:

- 상태 확인 없는 자동주문 금지.
- 상태 확인 없는 자동청산 금지.

- 자금관제는 운영자의 자금 재배치 판단을 돕는 시스템이지, 자동 재분배 시스템이 아니다.

- 긴급정지 해제
- 검토관리 복귀
- 조기마감/자동마감 최종 실행
- 청산 실행 가능 여부
- 예산/완충 상태 판단
- 보유/미수/미도 불일치 판단
- 서버/내부 데이터 불일치 판단

최종 실행 여부는 메인엔진과 상태/정책 계층에서 판단한다.

3. 현재 프로젝트 단계
============================================================

현재 프로젝트 단계는 다음과 같이 판정한다.

1. 개념 정립: 기존 운영정책은 1차 완료였으나, 이번 대화에서 마감/예산/완충 정책이 크게 보강되었다.
2. 정책 정립: 조기마감/자동마감/자금관제/완충복구 정책은 신규 확정 단계이다.
3. 구조개선: 1차 사실상 완료.
4. 운영정책 실전검증: 일부 미룸. 현재는 기능 구현 전 핵심 정책 갱신 단계.
5. 키움 OpenAPI 실연동 안정성 검증: 미진입 또는 대기 단계.

다음 창에서 즉시 할 일은 구조개선이 아니라 다음 순서이다.
1. 새 문서 기준으로 조기/자동마감 로직 분석.
2. 기존 코드가 “추가매수 금지 + 매도만” 전제로 되어 있는지 확인.
3. 조기/자동마감 로직을 “마감상태 진입 후 루틴 신호 정상 수용 + 다음 매도/설정 정책에 따른 종료” 구조로 수정.
4. 이후 메인 관제창 자금운영/예산/완충 영역을 구현.

4. 창별 역할 재정의

4.1 자동매매설정창

자동매매설정창은 종목 운영 설정센터이다.
담당 범위:
- 루틴 지정/해제
- 종목별 운영방식
- 자동/수동/ATS
- 조기마감
- 자동마감
- 청산정책
- 이월
- 검토관리 이동
- 개별 종목 정책 수정

자동매매설정창은 “종목이 어떤 방식으로 운영될 것인가”를 정한다.

4.2 메인 관제창

메인 관제창은 계좌/자금/성과/위험 관제센터이다.
담당 범위:
- 전체 예산
- 가용예산/완충예산 비율
- 예산 소진율
- 완충진입 상태
- 루틴별 사용금액
- 루틴별 매수한도
- 종목별 매수한도
- 실현손익/평가손익
- 수익성 신호등
- 종목 추세 신호등
- 미체결/주문대기 자금
- 검토관리 종목 수
- 긴급정지/전체정지/전체마감 등 주요 운영 명령

관제창은 별도 환경설정창을 늘리는 방향이 아니라, 화면에서 직접 클릭하여 수정할 수 있는 직관적 구조를 지향한다.

관제창의 성격:
- 정보 확인
- 즉시 개입
- 즉시 수정
- 자금 재배치 판단 보조

자동매매설정창이 설계실이라면, 메인 관제창은 운영실이다.

4.3 루틴

루틴은 신호 생성기이다.
담당 범위:
- 매수 조건
- 매도 조건
- 진입/이탈 타이밍 후보

루틴이 하면 안 되는 것:
- 예산 배정
- 주문수량 최종 결정
- 금액/주수 운영 최종 판단
- 계좌 위험 판단
- 미수/미도 처리
- 주문 가능 여부 최종 판단

4.4 메인엔진

메인엔진은 최종 판단과 주문 집행을 담당한다.
담당 범위:
- 루틴 신호 수신
- 예산/가용/완충 상태 확인
- 전체/루틴/종목 매수한도 확인
- 금액/주수 주문정책 적용
- 주문 가능 여부 최종 판단
- 주문 실행
- 주문/체결/미체결 상태 반영


============================================================
5. 상태 체계
============================================================

운영상태는 운영자가 이해 가능한 한국어 표시를 기준으로 한다. 내부 status 값은 영문일 수 있으나 GUI 표시는 아래 기준을 따른다.

주요 상태:

1. 감시/대기
- 매매시작 전 또는 현재 시간/운영방식상 주문 실행 대기 상태.
- 시작 OFF이면 회색.
- 시작 ON이어도 현재 시간이 매수/매도 가능 구간이 아니면 감시/대기로 표시될 수 있다.

2. 매수/매도
- 현재 운영방식과 시간정책상 매수/매도 신호를 처리할 수 있는 상태.
- 보유 유무만으로 매수/매도 여부를 결정하지 않는다.

3. 감시/매도
- 신규 매수는 막고 매도 감시만 유지하는 정책 상태.
- 단, 이번 v2.2 기준에서 조기마감/자동마감을 무조건 감시/매도로 해석하지 않는다.

4. 조기마감
- 운영자가 명시적으로 실행하는 운영 종료 절차이다.
- 조기마감은 청산과 같은 말이 아니다.
- v2.2부터 조기마감은 “추가매수 금지”가 아니라 “마감상태 진입”이다.
- 조기마감 상태에서도 루틴의 매수신호와 매도신호는 정상 수용될 수 있다.
- 다만 마감 상태의 목적은 해당 종목의 운영을 끝내는 것이므로, 매도신호 또는 설정된 조기마감/청산 정책에 따라 종료 방향으로 진행한다.

5. 자동마감
- 환경설정 또는 시간정책에 의해 자동으로 마감상태에 진입하는 절차이다.
- 자동마감도 청산과 동일하지 않다.
- 조기마감과 자동마감의 차이는 운영자가 직접 개입했는지, 미리 설정한 값에 따라 자동 진입했는지이다.
- 자동마감도 조기마감과 동일한 마감 철학을 따른다.

6. 청산
- 보유를 없애는 절차이다.
- 마감은 운영 종료 절차이고, 청산은 보유 제거 절차이다.

7. 긴급정지
- 계좌 단위 또는 시스템 단위 위험 차단 상태.
- 자동복귀 금지.
- 해제 시 재시작과 같은 수준의 안전 판정을 수행해야 한다.

8. 검토관리/검토종목
- 자동매매설정창에서 제거하고 검토관리창에서만 관리하는 격리 상태.
- 자동복귀 금지.
- 안정성검사 및 운영자 판단 후 복귀 가능.

9. 완충진입
- 자금관제 상태이며 종목 운영상태 그 자체는 아니다.
- 예산 내부의 가용구간을 넘어 완충예산을 사용하기 시작한 상태이다.
- 완충진입은 운영자가 경고구간에서 개입하지 못했거나, 동시체결/통신지연/반영지연 등으로 예산 통제가 후행한 결과로 본다.


============================================================
6. 현황 색상 정책
============================================================

현황 컬럼의 점 색상은 상태 텍스트와 같은 개념이 아니다.

색상 기준:

1. 녹색
- 정상 운영 가능.
- 매매시작 ON이고 운영방식/시간정책에 따라 정상적으로 움직일 수 있는 상태.
- 조기마감/자동마감 중이라도 처리 대상이 있으면 녹색이다.

2. 주황
- 정상이지만 다음 절차 진행 대상이 없음.
- 조기마감/자동마감 상태라는 이유만으로 주황이 아니다.
- 보유/미도 등 처리 대상이 있으면 주황이 아니다.

3. 회색
- 정지/비활성.
- 매매시작 OFF 또는 운영자 작동 대기.

4. 빨강
- 데이터 신뢰 불가.
- 서버 정보와 내부 정보 불일치.
- 내부 데이터 이상.
- 빨강은 자동 검토관리 이동이 아니라 즉시 운영정지 후 안정성검사 및 운영자 판단 대상이다.

주의:
- 선택행 하이라이트 색상은 현황 색상이 아니다.
- 검정/흰색처럼 보이는 선택색을 상태 이상으로 오판하지 않는다.


============================================================
7. 재시작 정책
============================================================

프로그램 재시작은 단순 UI 재실행이 아니라 안전초기화 이벤트이다.

확정 공식:
프로그램 재시작 = 긴급정지 해제 = 매매시작 초기복구

재시작 시 판단 기준:
- 보유 존재
- 미수 존재
- 미도 존재
- 이월 흔적 존재
- 데이터 불일치
- 파일/폴더 구조 이상
- 루틴 참조 이상

처리:
1. 보유/미수/미도/이월/불일치가 있으면 검토관리.
2. 문제가 없으면 종료상태 + 시작 OFF.
3. 자동으로 매수/매도 상태를 복원하지 않는다.
4. 주황 상태를 재시작 후 복원하지 않는다.
5. 재시작 후 운영자가 매매시작을 눌렀을 때 현재 시간/운영방식 기준으로 재판정한다.

재시작은 과거 state.json 상태를 그대로 살리는 동작이 아니다.


============================================================
8. 긴급정지 정책
============================================================

긴급정지는 계좌 단위 위험 차단 상태이다.

긴급정지 시:
- 신규 매수 중지.
- 실시간 감시 중지 또는 제한.
- 보유 종목 자동 매도 금지.
- 미체결 주문 확인 필요.
- 상태 저장.
- 로그 기록.

긴급정지 해제 시:
- 재시작과 동일한 판정으로 본다.
- 보유/미수/미도/이월/불일치가 있으면 검토관리.
- 정상인 종목만 종료상태/시작 OFF로 돌아갈 수 있다.
- 이전 RUNNING 상태를 그대로 복원하지 않는다.

주의:
- 긴급정지는 단순 정지 버튼이 아니다.
- 긴급정지 해제는 자동운영 복귀 버튼이 아니다.


============================================================
9. 검토관리 정책
============================================================

검토관리 대상은 자동매매설정창에서 표시하지 않는다.
검토관리창 전용으로 관리한다.

검토관리 진입 사유:
- 재시작 시 보유 존재
- 재시작 시 미수 존재
- 재시작 시 미도 존재
- 재시작 시 이월 존재
- 긴급정지 해제 시 잔여 문제 존재
- 마감 진행 중 미수/매수 미체결 존재
- 서버/내부 불일치 후 운영자가 분리 판단
- 파일/폴더 구조 문제
- 루틴 참조 문제
- 안정성검사 실패

검토관리 컬럼:
- 코드
- 종목
- 위치
- 상태
- 사유
- 검출
- 보유
- 미수
- 미도
- 발생시간

검토관리 버튼:
- 복귀
- 미지정
- 삭제
- 새로고침
- 닫기

검토관리창 컬럼은 현재 구조가 적당한 것으로 본다. 실서버 연결 후 실제로 어떤 불일치/지연/예외가 나오는지 확인한 뒤 필요한 경우 보강한다.

복귀 원칙:
- 자동복귀 금지.
- 새로고침 또는 안정성검사로 현재 상태를 다시 확인한다.
- 복귀/미지정은 문제 해소 후 운영자가 최종 처리하는 버튼이다.
- 복귀 자체가 판정 버튼처럼 동작하면 안 된다.
- 복귀 시 현재 조건 재판정 필요.
- 복귀 후 곧바로 매수/매도 상태가 되는지 여부는 현재 시간/운영방식/안정성검사 결과에 따라 달라진다.

실서버 연동 후 주의:
- 주문 직후, 체결 직후, 잔고 반영 지연, 미체결 변경 직후에는 서버와 내부 정보가 잠시 어긋날 수 있다.
- 이 경우 즉시 검토관리로 단정하지 않고 유예/재확인 개념이 필요할 수 있다.
- 다만 현재 단계에서는 상상으로 과도한 구조를 만들지 않고, 실서버 테스트 결과를 보고 보강한다.


============================================================
10. 조기마감 정책 v2.2
============================================================

조기마감은 운영자가 명시적으로 실행하는 운영 종료 절차이다.
청산과 혼용하면 안 된다.

v2.1 이전 개념:
- 조기마감 진입 후 추가 매수 금지.
- 매도만 수행.

v2.2 수정 개념:
- 조기마감은 추가 매수 금지가 아니라 마감상태 진입이다.
- 조기마감 상태에서도 루틴의 매수신호와 매도신호는 정상 수용될 수 있다.
- 마감상태는 루틴의 정상 매매 사이클을 강제로 깨는 것이 아니라, 매도신호 또는 설정된 마감/청산 정책을 통해 운영 종료 방향으로 진행하는 상태이다.
- 매수횟수 제한 옵션은 기본적으로 두지 않는다.
- 매수횟수 제한을 두면 종목이 온전한 매수→매도 세트를 마치지 못하고 마지막 세트가 손절처럼 왜곡될 수 있다.
- 따라서 마감상태에서 매수 제한은 두지 않고, 여러 번 매수가 진행되는 경우 관제창에서 운영자가 알 수 있도록 표시하는 방향을 택한다.

조기마감 옵션 후보:
- 루틴매도신호
- 시장가
- 현재가
- 지정가
- 익절 N%
- 손절 N%
- 이월

확정 정책:
1. 조기마감 상태 자체는 주황 사유가 아니다.
2. 조기마감 + 보유 있음 = 처리 대상 있음.
3. 조기마감 + 보유 있음 + 시장가/현재가 등 = 청산 또는 매도 절차 진행 가능.
4. 조기마감 + 이월 = 청산 실행 금지.
5. 조기마감 + 이월 + 보유 있음 = 보유 유지.
6. 조기마감 + 이월은 청산 컬럼도 이월로 표시해야 한다.
7. 조기마감 + 이월 후 종료/재시작/다음 시작점에서는 검토관리 대상이다.
8. 조기마감 실행 후 대상 없음이면 주황.
9. 완충복구로 인해 조기마감에 편입된 경우 조기마감의 이월은 사용할 수 없다.
10. 완충복구 목적의 조기마감은 운영자금 확보와 완충 해소 목적이므로 보유 유지 선택과 충돌한다.

조기마감과 이월:
- 조기마감 이월은 운영자의 적극 개입 상태에서 의미가 있다.
- 운영자가 상황을 직접 보고 보유를 유지하겠다고 판단한 경우의 선택이다.
- 기본 설정을 이월로 해두는 것은 일반적이지 않다.
- 완충복구 상태에서는 이월을 허용하지 않는다.

주의:
- 조기마감 시간과 청산 시간대가 겹쳐도 조기마감 방식이 이월이면 이월이 우선한다.
- 단, 완충복구로 조기마감에 진입한 경우에는 이월이 비활성이다.
- 청산 시간대라는 이유로 이월을 무시하고 시장가/현재가 청산하면 안 된다.


============================================================
11. 자동마감 정책 v2.2
============================================================

자동마감은 환경설정 또는 시간정책에 의해 실행되는 운영 종료 절차이다.
자동마감도 조기마감과 마찬가지로 청산과 같은 말이 아니다.

조기마감과 자동마감의 차이:
- 조기마감: 운영자가 적극 개입하여 지금 마감상태로 들어가는 것.
- 자동마감: 운영자가 미리 설정한 값에 따라 특정 조건/시간에 자동으로 마감상태로 들어가는 것.

본질은 같다.
둘 다 마감상태 진입이며, v2.2 기준으로 “추가매수 금지 + 매도만”이라는 단순한 의미가 아니다.

확정 정책:
1. 자동마감 상태 자체는 주황 사유가 아니다.
2. 자동마감 + 보유 있음 = 처리 대상 있음.
3. 자동마감 + 이월 = 청산 실행 금지.
4. 자동마감 + 이월 + 보유 있음 = 보유 유지.
5. 자동마감 + 이월 후 종료/재시작/다음 시작점에서는 검토관리 대상이다.
6. 자동마감 실행 후 대상 없음이면 주황.
7. 자동마감도 조기마감과 같은 마감상태 철학을 따른다.
8. 자동마감 진입 후에도 루틴 매수/매도 신호는 정책상 수용 가능하다.
9. 다만 설정된 마감/청산 정책에 따라 운영 종료 방향으로 진행한다.

자동마감 정책은 장기 테스트가 필요하다.
단기적으로 완전 종료 판정하지 않는다.


============================================================
12. 청산 정책
============================================================

청산은 보유를 없애는 절차이다.
마감은 운영 종료 절차이고, 청산은 보유 제거 절차이다.

청산 방식:
- 시장가
- 현재가
- 지정가
- 5분/시장가
- 10분/시장가
- 5분/현재가
- 10분/현재가
- 이월

이월 정책:
- 이월은 청산하지 않겠다는 명시적 선택이다.
- 조기마감/자동마감에서 이월이면 청산 실행 금지.
- 청산 시간대와 겹쳐도 이월이 우선한다.
- 이후 처분하려면 운영자가 이월을 시장가/현재가 등 다른 방식으로 변경해야 한다.
- 완충복구로 들어온 조기마감에서는 조기마감의 이월은 사용할 수 없다.
- 단, 청산정책의 이월 항목 자체는 별도 설정으로 존재할 수 있다. 다만 완충복구 목적에서는 자금회수가 목적이므로 조기마감 이월은 비활성이다.

미수 정책:
- 미수는 마감/청산 대상이 아니다.
- 마감 시작 시 미수가 발견되면 청산으로 넘기지 않고 검토관리 대상이다.

미도 정책:
- 미도는 매도 미체결로서 처리 대상이다.
- 재시작/긴급정지 해제 시 미도 존재는 검토관리 대상이다.

청산과 완충:
- 완충복구에서 선정된 종목은 기존 조기마감 정책을 사용한다.
- 조기마감 정책에 따라 이어지는 청산도 기존 청산정책을 따른다.
- 별도의 완충 전용 청산 엔진을 만들지 않는다.
- 청산 시간까지 도달한 상황에서는 이미 많은 종목이 매도 완료 또는 감시/대기 상태일 가능성이 높으므로, 완충복구의 의미가 약해진다.


============================================================
13. 예산/자금운영 정책
============================================================

13.1 기본 철학

자금운영은 메인 관제창의 핵심 기능이다.
자금운영은 운영자의 매매 스타일을 강제하는 것이 아니라, 운영자가 원하는 방식으로 자금을 운용할 수 있게 하면서 위험을 인지하고 대응할 수 있게 돕는 기능이다.

자금운영은 다음 3축으로 구성한다.
1. 예산관리
2. 매수한도관리
3. 주문정책관리

13.2 예산

예산은 총 운영자금이다.
예산은 가용예산과 완충예산으로 구성된다.

공식:
예산 = 가용예산 + 완충예산

예:
전체 예산 100,000,000원
가용/완충 비율 8:2
가용예산 80,000,000원
완충예산 20,000,000원

또는:
전체 예산 100,000,000원
가용/완충 비율 9:1
가용예산 90,000,000원
완충예산 10,000,000원

의미:
- 예산은 총 운영자금이다.
- 가용예산은 정상 매수 운영 구간이다.
- 완충예산은 비상 대응 구간이다.
- 완충은 예산 밖의 추가 자금이 아니다.
- 완충은 예산 내부에 포함된 비상 구간이다.

13.3 예산 설정 방식

예산은 금액으로 설정한다.
가용/완충은 금액 직접 입력보다 비율 선택으로 구성한다.

예:
- 9:1
- 8:2
- 7:3
- 6:4
- 직접 비율 입력 후보

관제창 표시:
- 전체 예산 금액
- 가용 비율 및 금액
- 완충 비율 및 금액
- 현재 사용금액
- 예산 소진율
- 완충 사용 여부

13.4 예산 사용금액 계산 기준

예산 사용금액은 다음을 기준으로 계산한다.
- 보유 총매입금액
- 매수주문대기금액

공식:
예산 사용금액 = 보유 총매입금액 + 매수주문대기금액

매도주문은 체결 전까지 자금 회수로 보지 않는다.
매도주문 대기 중이라도 실제 예수금으로 돌아오지 않았으면 사용중 자금으로 본다.

평가금액은 자금운영 기준이 아니다.
주가 상승/하락으로 평가금액이 변해도 실제 투입 원금은 총매입금액이다.
평가금액은 손익관제 영역에서 사용한다.

13.5 예산 상태

예산 상태는 3단계로 단순화한다.

1. 정상
- 예산 사용금액이 가용예산 경고구간에 도달하지 않은 상태.

2. 경고
- 운영자가 설정한 경고비율에 도달한 상태.
- 예: 70%, 80%, 90%, 95%.
- 경고 단계는 운영자가 개입해야 하는 구간이다.
- 텔레그램, 관제창, 로그 등으로 알림을 보낸다.

3. 완충진입
- 예산 사용금액이 가용예산을 초과하여 완충예산을 사용하기 시작한 상태.
- 완충진입은 정상운영 상태가 아니다.
- 완충진입은 운영자가 경고단계에서 개입하지 못했거나, 동시체결/통신지연/서버반영 지연 등으로 예산 통제가 후행한 결과일 수 있다.

13.6 완충소진 이후

완충까지 모두 소진되면 이후 대처가 매끄럽지 못할 수 있다.
예산도 없고 운영자 지시도 없고 자동복구도 실패한 상황은 프로그램이 완벽히 해결할 수 없다.
프로그램은 최대한 복구를 시도하지만, 운영자 개입이 없고 손실이 발생하는 경우 그 책임은 운영자 영역으로 본다.

14. 매수한도 정책
============================================================

14.1 매수한도 기본 개념

매수한도는 예산 배정이 아니다.
매수한도는 매수 상한선이다.
매수한도는 안전장치이며 사용/미사용을 선택할 수 있다.

계층:
전체 매수한도
↓
루틴 매수한도
↓
종목 매수한도

각 계층은 독립적으로 ON/OFF 가능하다.

14.2 전체 매수한도

전체 매수한도는 예산 내부에서 추가로 설정하는 전체 매수 제한이다.
사용하지 않을 수 있다.

14.3 루틴 매수한도

루틴 매수한도는 루틴 단위의 상한선이다.
루틴 매수한도를 설정하지 않은 경우, 해당 루틴은 상위 잔여자금 범위 내에서 자유롭게 사용 가능하다.

중요:
루틴 매수한도 OFF는 루틴 운영 종료가 아니다.
루틴 매수한도 OFF는 해당 루틴에 별도 한도를 걸지 않는다는 뜻이다.

루틴 매수한도 OFF의 의미:
- 상위 예산/전체 매수한도/종목 매수한도만 적용.
- 제한 없는 루틴들은 남은 가용자금을 공유한다.
- 제한 없는 루틴끼리는 사용금액에 따라 탄력적으로 상호작용한다.

예:
전체 예산 100,000,000원
A루틴 매수한도 10,000,000원, 사용 9,000,000원
B루틴 매수한도 OFF
C루틴 매수한도 OFF

이때 B/C는 남은 상위 가용 범위 안에서 경쟁적으로 사용할 수 있다.
B가 많이 사용하면 C의 실질 가용범위가 줄어든다.
C가 많이 사용하면 B의 실질 가용범위가 줄어든다.

14.4 종목 매수한도

종목 매수한도는 개별 위험종목에 거는 최후 안전핀이다.
종목 매수한도는 기본적으로 고정금액 중심으로 본다.

종목별 매수한도 사용 상황:
- 매우 위험한 종목
- 변동성이 큰 종목
- 테스트 성격이 있는 종목
- 하락을 감안하고 소액만 운영할 종목
- 특정 종목에 과도한 자금이 들어가지 않게 막고 싶은 경우

중요:
- 루틴 매수한도를 늘리거나 해제해도 종목 매수한도는 자동으로 늘어나거나 해제되지 않는다.
- 종목 매수한도는 운영자가 직접 해제해야만 풀린다.
- 루틴 제한을 푸는 것은 루틴 전체에 더 자금을 허용하는 것이지, 그 안의 위험 종목 제한까지 푼다는 뜻이 아니다.

14.5 매수한도 표시

관제창에서는 비율과 금액을 병기한다.
비율을 클릭하면 비율 기준으로 수정한다.
금액을 클릭하면 금액 기준으로 수정한다.
입력값은 서로 자동 환산되어 표시된다.

예:
A루틴 매수한도: 30% / 30,000,000원
B루틴 매수한도: 금액 / 20,000,000원
삼성전자 종목한도: 1,000,000원

종목한도는 비율로 입력해도 최종 저장은 고정금액 중심이 적합하다.
루틴 한도 변경으로 종목한도가 자동 증가하는 것은 위험하다.

14.6 제한 도달률

도달률은 매수한도 대비 사용 정도를 표시하는 보조지표이다.
단, 도달률은 예산 소진율과 구분한다.

예산 소진율:
- 전체 예산 대비 현재 사용금액.

제한 도달률:
- 특정 루틴/종목 매수한도 대비 현재 사용금액.

루틴/종목 관제에서는 도달률보다 사용금액, 잔여한도, 손익, 수익성 표시가 더 중요하다.
도달률은 운영자가 한도 확대/축소 판단을 할 때 보조로 사용한다.

15. 주문정책: 금액/주수
============================================================

금액 기준/주수 기준 주문수량 정책은 자동매매루틴이 아니라 메인 프로그램의 자금관리·주문관리 계층에 구현한다.

루틴:
- 살까 말까 신호.

메인 프로그램:
- 얼마나 살 수 있는지.
- 실제로 주문할 것인지.
- 금액 기준인지 주수 기준인지.
- 예산/가용/완충/매수한도에 걸리는지.

주문정책 후보:
- 금액 기준
- 주수 기준
- 비중 기준은 향후 확장 후보

이 기능은 현재 즉시 구현 대상은 아니며, 자금운영 시스템 설계와 주문엔진 구현 시점에 함께 반영한다.

16. 수익성 신호등 정책
============================================================

수익성 신호등은 운영자가 자금을 어디에 집중할지 판단하기 위한 성과 관제 지표이다.
운영 안정성 판정과 혼동하지 않는다.
운영 안정성은 검토관리/긴급정지/안정성검사가 담당한다.

수익성 신호등 기준:

1. 빨강
- 현재가 기준 일괄 매도 시 실질 손실.
- 세금, 수수료, 기타 거래비용을 반영한 순손익이 음수.

2. 노랑
- 표면상 수익이 있거나 손익분기 근처이지만, 세금/수수료/거래비용을 충분히 충당하지 못하는 구간.
- 키움 서버가 관련 정보를 제공하면 서버값을 우선 사용.
- 제공하지 않으면 프로그램 자체 산식으로 계산.

3. 녹색
- 세금, 수수료, 기타 거래비용을 반영하고도 명확한 실질 순이익 구간.

종목 수익성:
- 해당 종목을 현재가 기준으로 전량 처분한다고 가정하고 계산한다.

루틴 수익성:
- 소속 종목 중 수익난 종목 수로 판단하지 않는다.
- 루틴 전체 총매입금액, 전체 평가금액, 실현손익, 평가손익, 제반비용을 합산해 계산한다.
- 루틴 전체를 지금 청산한다고 가정했을 때의 순수익률을 기준으로 한다.
- 수익 종목이 많아도 큰 손실 종목 하나 때문에 전체 청산 시 손실이 날 수 있으므로 단순 개수 판정 금지.


============================================================
17. 종목 추세 신호등 정책
============================================================

추세 신호등은 종목에만 적용한다.
루틴 추세는 계산하지 않는다.

이유:
- 루틴은 여러 종목의 묶음이다.
- 종목마다 투입금액과 차트가 다르다.
- 루틴 단위 추세는 의미가 왜곡될 수 있다.
- 루틴은 손익/수익성/사용금액 중심으로 관제한다.

종목 추세 기준:
- 사용자가 선택한 이동평균선 하나를 기준으로 단순 판정한다.
- 예: 5이평, 10이평, 20이평 등.
- 정배열/역배열 복합 계산은 보류한다.
- 필요하면 향후 확장한다.

판정 예:
- 현재가가 선택 이평선 위: 녹색.
- 현재가가 선택 이평선 근처: 노랑.
- 현재가가 선택 이평선 아래: 빨강.

정확한 근접 범위는 구현 단계에서 조정한다.

18. 완충복구 정책
============================================================

18.1 완충복구의 의미

완충복구는 예산 가용구간을 넘어 완충구간에 진입했을 때, 프로그램이 최대한 상황 정상화를 시도하는 비상 대응 정책이다.
완충복구는 정상 운영전략이 아니다.
완충복구는 운영자가 경고단계에서 개입하지 못한 경우 또는 서버/통신/동시체결 특성상 예산 통제가 후행한 경우의 최악 대응 프로세스이다.

18.2 완충복구 트리거

완충상태에 진입했다는 사실만으로 계속 대상을 선정하지 않는다.
완충상태에서 신규 매수가 발생하고, 그 후에도 완충이 해소되지 않는 경우 복구정책을 실행한다.

공식:
완충상태 + 신규 매수 발생 + 완충 미해소 = 완충복구 정책 실행

18.3 복구대상 선정

복구대상은 “완충에 진입하게 만든 종목”으로 고정하지 않는다.
운영자가 선택한 복구대상 선정 정책에 따라 고른다.

선정 정책 후보:
- 수익률 낮은 종목 우선
- 최신 진입 종목 우선
- 최대 점유금액 종목 우선
- 최초 진입 종목 우선
- 기타 향후 확장

예:
운영자가 “수익률 낮은 종목 우선”을 선택한 경우.
완충상태에서 신규 매수가 발생하고 완충이 해소되지 않으면, 이미 조기마감/자동마감/청산 상태가 아닌 종목 중 수익률이 가장 낮은 종목을 선정한다.
그 다음에도 완충상태에서 신규 매수가 발생하면, 이미 마감/청산에 들어간 종목을 제외하고 다시 수익률이 가장 낮은 종목을 선정한다.

18.4 대상 제외

다음 종목은 완충복구 대상에서 제외한다.
- 이미 조기마감 진행중인 종목
- 이미 자동마감 진행중인 종목
- 이미 청산 진행중인 종목
- 검토관리 종목
- 정지/비활성 종목

이미 마감/청산 상태에 들어간 종목은 기존 정책을 그대로 수행한다.
완충복구가 같은 종목을 중복으로 다시 선정하지 않는다.

18.5 선정 후 처리

선정된 종목은 조기마감 상태로 전환한다.
단, 완충복구 목적의 조기마감에서는 이월을 선택할 수 없다.

처리:
1. 완충상태에서 신규 매수 발생.
2. 완충 미해소 확인.
3. 복구대상 선정정책에 따라 대상 종목 선정.
4. 대상 종목 조기마감 전환.
5. 기존 자동매매설정의 조기마감 정책 수행.
6. 이어지는 청산은 기존 청산정책을 따른다.
7. 조기마감의 이월은 비활성이다.

18.6 수동/자동/시간운영 관계

완충은 돈이 부족한 상황이므로 운영방식과 무관하게 적용된다.
자동운영, 수동운영, 시간운영, ATS 여부와 무관하게 완충복구 정책은 적용될 수 있다.
다만 완충복구 적용시간 조건을 만족해야 한다.

18.7 완충복구 적용시간

완충복구는 하루 종일 무조건 적용하지 않는다.
완충복구 적용시간을 둔다.

기본값:
- 기존 시간운영 설정값을 사용한다.
- 체크박스 형태로 “시간운영 설정값 사용”을 기본 ON으로 둔다.

옵션:
- 운영자가 별도 시간을 직접 설정할 수 있다.
- 관제창에서 완충복구 적용시간을 직접 클릭하여 수정할 수 있게 한다.

예:
[✓] 시간운영 설정값 사용
완충복구 적용시간: 09:00 ~ 13:30

체크 해제 시:
[ ] 시간운영 설정값 사용
완충복구 적용시간: 09:00 ~ 13:30

이유:
- 대부분은 기존 시간운영 설정값을 따르는 것이 자연스럽다.
- 그러나 특정 운용상 별도 시간이 필요할 수 있다.
- 별도 시간이 필요한 상황에서 로직 수정 없이 UI 설정만으로 대응하기 위해 옵션을 둔다.

18.8 완충복구와 이월

완충복구에서 조기마감 이월은 금지한다.
이월은 보유 유지이고, 완충복구는 자금 확보이다.
서로 목적이 충돌한다.

단, 일반 조기마감/자동마감에서 운영자가 직접 이월을 선택하는 것은 기존 정책대로 허용된다.
완충복구 상황에서만 조기마감의 이월이 비활성이다.

18.9 완충복구 한계

프로그램은 완충상태를 해소하기 위해 설정된 정책에 따라 최선을 다한다.
그러나 예산이 없고 운영자 개입도 없고 자동복구도 실패한 상황에서 발생하는 손실은 운영자 책임 영역으로 본다.
프로그램은 손실을 완벽히 막는 장치가 아니라, 경고/완충/복구 절차를 통해 대응 시간을 주고 피해를 줄이기 위한 장치이다.


============================================================
19. 관제창 자금운영 UI 정책
============================================================

19.1 기본 방향

관제창은 별도 환경설정창을 많이 만드는 방향이 아니다.
관제창은 직접 보고 직접 수정하는 방향으로 간다.

원칙:
- 환경설정창 최소화.
- 직접 클릭 수정 최대화.
- 대부분의 설정은 전체 적용 사항.
- 개별 조정은 루틴/종목 행에서 직접 클릭하여 수정.
- 설정값과 환산값을 병기.

19.2 상단 자금 패널

표시 후보:
- 전체 예산
- 가용/완충 비율
- 가용예산 금액
- 완충예산 금액
- 사용금액
- 예산 소진율
- 예산 상태: 정상/경고/완충진입
- 매수주문대기금액
- 예수금
- 실현손익
- 평가손익

19.3 루틴 관제표

표시 후보:
- 루틴명
- 운영상태
- 총매입금액
- 실현손익
- 평가손익
- 순수익률
- 수익성 신호등
- 루틴 매수한도
- 제한 도달률
- 소속 종목 수
- 검토관리 종목 수
- 마감/청산 진행 종목 수

루틴 추세는 표시하지 않는다.
루틴은 손익/수익성/사용금액 중심으로 관제한다.

19.4 종목 관제표

표시 후보:
- 루틴
- 종목명
- 운영상태
- 총매입금액
- 보유수량
- 평균단가
- 현재가
- 평가손익
- 수익성 신호등
- 추세 신호등
- 종목 매수한도
- 제한 도달률
- 조기마감/자동마감/청산 상태

19.5 직접 수정 방식

예산:
- 전체 예산 금액 클릭 → 수정.
- 가용/완충 비율 클릭 → 9:1, 8:2, 7:3, 6:4 등 선택 또는 직접 입력.
- 경고비율 클릭 → 70/80/90/95 등 수정.

완충복구:
- 완충복구 적용시간 클릭 → 수정.
- 시간운영 설정값 사용 체크박스 ON/OFF.
- 복구대상 선정정책 클릭 → 드롭다운 변경.

루틴 매수한도:
- 비율 클릭 → 비율 기준 수정.
- 금액 클릭 → 금액 기준 수정.
- OFF 클릭 → 제한 미사용.

종목 매수한도:
- 금액 클릭 → 고정금액 수정.
- OFF 클릭 → 제한 미사용.

19.6 슬라이더

슬라이더는 메인 조작수단으로 보지 않는다.
필요하면 상태 시각화 보조로만 사용한다.
정밀 설정은 비율/금액 직접 클릭 수정 방식이 더 적합하다.


============================================================
20. ATS 정책
============================================================

ATS는 독립 운영모드가 아니다.
수동운영 + 선택된 ATS 거래시간 확장 개념이다.

정책:
- 정규장 시간: 매수/매도.
- 장전 ATS 시간: 매수/매도.
- 장후 ATS 시간: 조기마감/청산 정책 검사.
- 장후 ATS + 조기마감 존재: 감시/대기.
- 장후 ATS + 청산정책 존재: 감시/대기.
- 장후 ATS + 차단정책 없음: 매수/매도.

표시:
- 수동: 보라.
- 수동+ATS 전역설정: 보라.
- 수동+ATS 개별설정: 주황.

ATS 관련 기능은 gui_auto_trade_ats_ops.py로 분리 완료.


============================================================
21. 루틴 정책
============================================================

종목당 활성 루틴은 1개만 허용한다.

루틴 지정 가능 종목:
- 미등록/미지정 종목만 상단 표시.
- 이미 루틴에 연결된 종목은 상단에 표시하지 않는다.
- 선택 루틴 연결 종목은 하단에서 관리.
- 동일 루틴 중복 지정 금지.
- 실행부에서도 중복 지정 방어.

RoutineAssignWindow는 gui_routine_assign_window.py로 분리 완료.
RoutineUnassignConfirmDialog도 gui_routine_assign_window.py에 위치한다.
CenteredCheckBoxDelegate는 gui_centered_checkbox_delegate.py로 분리 완료.

루틴별 종목관리는 향후 관제창 자금/성과 관제와 연결된다.
루틴별 자금 사용, 수익성, 매수한도, 종목 수, 검토관리 수가 관제창에서 보일 필요가 있다.


============================================================
22. 정렬/화면순서 정책
============================================================

자동매매설정창 하단 종목표는 헤더 정렬 후 사용자가 개별 종목 설정을 변경해도 행이 튀면 안 된다.

확정 정책:
1. 헤더 클릭 시 정렬을 수행한다.
2. 그 순간의 화면 순서를 _stock_visual_order로 저장한다.
3. 이후 설정 변경/조기마감/개별청산/자동갱신 시 기존 정렬 규칙을 재적용하지 않는다.
4. 화면은 정렬 당시의 순서를 유지한다.
5. 다시 헤더를 클릭할 때만 새 정렬을 적용한다.
6. 선택 복원 시 selectRow()로 스크롤이 튀지 않도록 selectionModel().select() 방식 사용.
7. 스크롤 위치는 마지막에 재적용한다.

해결된 문제:
- 정렬 후 운영방식 변경 시 종목이 원래 위치로 복귀하는 문제 해결.
- 선택 복원 중 스크롤 이동으로 행이 튀는 문제 해결.
