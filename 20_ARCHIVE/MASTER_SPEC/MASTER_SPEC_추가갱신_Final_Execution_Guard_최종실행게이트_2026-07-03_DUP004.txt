MASTER_SPEC_추가갱신_Final_Execution_Guard_최종실행게이트_2026-07-03

작성 목적
- 본 문서는 REAL_READY 이후 ORDER_QUEUED로 넘어가기 직전, 실주문 실행을 허용할지 최종 판정하는 Final Execution Guard 정책을 정의하기 위한 MASTER_SPEC 추가 갱신자료이다.
- 본 문서는 코드 구현 문서가 아니라, SendOrder 직전 최종 차단 조건과 책임 분리를 정의하는 기준 문서이다.
- 현재 단계에서 SendOrder, ExecutionController 구현, order_locks.json 생성, order_executions.json 생성, GUI/Timer 연결은 금지한다.

==================================================
1. Final Execution Guard의 위치
==================================================

공식 위치:

REAL_READY
  ↓ Adapter Request Preview
REAL_READY 유지
  ↓ Final Execution Guard
ORDER_QUEUED
  ↓ KiwoomOrderExecutor, 향후
ORDER_SENT / ORDER_ACCEPTED / REJECTED

Final Execution Guard는 REAL_READY order가 ORDER_QUEUED로 넘어가기 직전에만 호출된다.

==================================================
2. Final Execution Guard의 목적
==================================================

Final Execution Guard는 실주문 직전의 마지막 차단 게이트이다.

목적:
- 실수로 SendOrder가 호출되는 것을 방지한다.
- 중복 주문을 방지한다.
- 미확정 hoga/order_type 상태를 차단한다.
- 운영자 승인 없는 주문을 차단한다.
- 계좌/로그인/실매매 guard 불충족 주문을 차단한다.
- 검토관리/정지/마감/청산 상태와 충돌하는 주문을 차단한다.

Final Execution Guard는 주문을 보내지 않는다.
Final Execution Guard는 ORDER_QUEUED 생성 가능 여부만 판정한다.

==================================================
3. Final Execution Guard 호출 주체
==================================================

허용 주체:
- ExecutionController, 향후.

금지 주체:
- Timer
- GUI 직접 호출
- Adapter Preview
- Real Preflight
- Operation Policy Gate
- Approval Engine
- order_queue
- order_candidate_engine
- routine_signal_consumer

정책:
- GUI가 최종 실행 버튼을 제공하더라도 GUI는 ExecutionController를 호출해야 한다.
- Timer는 Final Execution Guard를 자동 호출하면 안 된다.
- signal_probe_only 흐름에서는 Final Execution Guard 호출 금지.

==================================================
4. 필수 입력
==================================================

Final Execution Guard 입력 후보:

1. order
- order_queue의 REAL_READY order 1건.

2. guard
- real_trade_guard.json의 현재 snapshot.

3. order_intent
- order.order_intent.
- resolved 여부 확인.

4. order_provenance
- order.order_provenance.
- source_signal_id/routine/code 추적 확인.

5. order_lock 상태
- 동일 order/source_signal 중복 실행 여부.

6. adapter request preview
- SendOrder에 필요한 파라미터 생성 가능 여부.

7. operation status
- 종목 상태, 검토관리, 마감/청산/정지 상태와 충돌 여부, 향후.

==================================================
5. 필수 통과 조건
==================================================

Final Execution Guard는 아래 조건이 모두 true일 때만 통과한다.

1. order.status == REAL_READY
2. order.execution_enabled == true
3. guard.real_trade_enabled == true
4. guard.operator_confirmed == true
5. guard.kiwoom_logged_in == true
6. guard.account_selected == true
7. guard.account_no 존재
8. order.account_no가 있으면 guard.account_no와 일치
9. order.side in BUY/SELL
10. order.quantity > 0
11. order.price 정책 정상
12. order_type 확정
13. hoga 확정
14. order_intent 존재
15. order_intent.unresolved == false
16. order_provenance 존재
17. source_signal_id 존재
18. order_id 존재
19. 중복주문 lock 획득 가능
20. 동일 source_signal_id 실행 중복 없음
21. 동일 order_id active execution 없음
22. Adapter Request Preview 생성 가능
23. request_hash 생성 가능
24. 종목 상태가 정상 운영 가능
25. 검토관리 대상 아님
26. 청산/마감/정지 상태와 충돌 없음
27. 최종 실행 호출 주체가 명확함
28. 사용자 또는 운영자 승인 시각 기록 가능

하나라도 실패하면 ORDER_QUEUED 생성 금지.

==================================================
6. 차단 결과
==================================================

Final Execution Guard 실패 시 기본 정책:

- SendOrder 호출 금지.
- ORDER_QUEUED 생성 금지.
- order status 변경은 기본 금지.
- 실패 사유 summary만 반환.
- 필요 시 향후 BLOCKED_EXECUTION 같은 상태를 검토할 수 있으나 현재 새 상태값 추가 금지.
- 심각한 불일치/위험 조건은 검토관리 후보.

현재 단계에서는 새 상태값을 만들지 않는다.

권장 반환 구조, 향후:

{
  "ok": false,
  "order_id": "...",
  "blocked": true,
  "reasons": [
    "execution_enabled is false",
    "hoga is unresolved"
  ],
  "status_changed": false,
  "send_order_called": false
}

==================================================
7. 통과 결과
==================================================

Final Execution Guard 통과 시 허용 가능한 다음 작업:

- order lock 획득.
- Execution Request 생성.
- order status를 ORDER_QUEUED로 전환.
- request_hash 기록.
- guard snapshot 기록.
- Adapter request snapshot 기록.

단, 현재 단계에서는 구현하지 않는다.

향후 통과 반환 후보:

{
  "ok": true,
  "order_id": "...",
  "ready_for_order_queued": true,
  "lock_required": true,
  "execution_request_required": true,
  "send_order_called": false
}

==================================================
8. execution_enabled 정책
==================================================

execution_enabled는 Final Execution Guard의 핵심 조건이다.

정책:
- false이면 무조건 차단.
- Guard는 execution_enabled를 true로 바꾸지 않는다.
- true 전환은 별도 수동 승인/실행 컨트롤에서만 가능하다.
- execution_enabled=true는 order 단위 최종 실행 허가이다.
- true가 되어도 다른 guard 조건이 실패하면 차단된다.

금지:
- Preflight에서 true 전환.
- Adapter Preview에서 true 전환.
- Timer에서 true 전환.
- Approval/Policy에서 true 전환.

==================================================
9. operator_confirmed 정책
==================================================

operator_confirmed는 전역 실주문 확인 플래그이다.

정책:
- false이면 무조건 차단.
- Final Execution Guard는 값을 읽기만 한다.
- true 전환은 별도 guard UI/운영자 확인 절차에서만 가능하다.
- operator_confirmed=true만으로 SendOrder 허용 아님.
- order.execution_enabled도 true여야 한다.

==================================================
10. order_intent resolved 조건
==================================================

Final Execution Guard는 order_intent.unresolved == true인 order를 차단한다.

필수:
- order_intent 존재
- source_ui_path 또는 명확한 정책 출처 존재, 향후
- order_type 확정
- hoga 확정
- price_mode 확정
- method_type 확정
- multi_hoga 정보 확정, 해당 시

현재 order_intent는 unresolved=true가 기본이므로 현재 운영 흐름에서는 ORDER_QUEUED로 갈 수 없다.
이것이 안전한 상태이다.

==================================================
11. order_provenance 조건
==================================================

Final Execution Guard는 order_provenance 존재를 요구한다.

이유:
- 실주문 직전 주문 출처를 추적할 수 있어야 한다.
- source_signal_id 없이 SendOrder 금지.
- routine/code/signal/reason 추적 가능해야 한다.

필수:
- order_provenance.source_signal_id 존재
- order_provenance.routine 존재
- order_provenance.signal 존재
- order_provenance.code 또는 order.code 존재

단, order_provenance.unresolved가 true라고 해서 무조건 차단할지는 향후 정책이다.
현재는 order_intent.unresolved가 더 직접적인 차단 조건이다.

==================================================
12. Lock 조건
==================================================

Final Execution Guard는 중복주문 lock 획득 가능성을 확인해야 한다.

필수:
- order_id 기준 active lock 없음.
- source_signal_id 기준 중복 실행 없음.
- 동일 request_hash 중복 없음.
- lock 생성 주체는 ExecutionController.
- Lock 없이 ORDER_QUEUED 생성 금지.
- Lock 없이 SendOrder 호출 금지.

==================================================
13. Adapter Request 조건
==================================================

Final Execution Guard는 Adapter Request Preview가 생성 가능한지 확인해야 한다.

필수:
- side 정상
- code 정상
- quantity > 0
- price 정책 정상
- account_no 정상
- hoga/order_type 확정
- send_order_enabled는 여전히 false일 수 있음, preview 기준
- 실제 SendOrder enabled 여부는 ExecutionController/KiwoomOrderExecutor에서 별도 관리

Adapter Preview 실패 시 ORDER_QUEUED 금지.

==================================================
14. 검토관리/운영상태 조건
==================================================

향후 Final Execution Guard는 운영상태와도 연결되어야 한다.

차단 후보:
- 종목이 검토관리 대상
- 프로그램 긴급정지 상태
- 자동마감/청산 중 충돌
- 미수/미도/잔량 불일치
- Kiwoom 서버 정보와 내부 정보 불일치
- 상태 색상 빨강
- 계좌/종목 운영정지

현재 단계에서는 이 항목을 설계 기준으로만 둔다.

==================================================
18. 최종 결론
==================================================

Final Execution Guard는 실주문 직전의 마지막 방어선이다.

현재 프로젝트는 Adapter Request Preview까지 도달했지만, 아직 Final Execution Guard를 통과할 수 있는 order는 없어야 한다.

이유:
- order_intent.unresolved=true
- hoga/order_type 미확정
- execution_enabled=false
- operator_confirmed=false 기본
- lock 미구현
- execution request 미구현

따라서 현재 상태는 안전하다.

향후 SendOrder 구현은 Final Execution Guard가 완성된 뒤에만 검토한다.
