1. Recovery Prerequisite Boundary

- Missing global Production Recovery context is a request-level precondition
  failure.
- Expected global prerequisite failures do not create or update a stock-level
  REVIEW_REQUIRED state.
- The expected prerequisite set includes no login session, no selected
  account, Recovery not started, and Recovery still in progress.
- These conditions remain fail-closed: the requested operation does not run.
- A stock-level REVIEW_REQUIRED transition remains reserved for an existing
  official writer path with stock-specific evidence that requires operator
  review.

2. State Preservation On Fail Closed

When Production Recovery blocks early close, immediate liquidation,
individual liquidation, or time-policy automatic close:

- the stock Runtime state is not changed
- the stock status is not changed to REVIEW_REQUIRED solely because the
  global Recovery prerequisite is missing
- no operation mutation is committed
- no operation command is created by the blocked request
- no execution queue item is created
- SendOrder and Chejan paths are not entered

The Recovery Gate remains before mutation and execution boundaries.

3. Expected And Investigative Diagnostics

- Expected prerequisite blocks are presented to the operator through the
  existing user-facing Toast path.
- Expected prerequisite blocks do not emit warning diagnostics to the console
  or logger.
- Unknown reason codes, Registry read errors, and Recovery Gate exceptions
  remain investigative conditions and retain diagnostic logging.
- Internal reason codes remain diagnostic data and are not used as the
  user-facing explanation when an official user message is available.

4. Immediate Liquidation Command Boundary

- Immediate liquidation remains a one-shot command request.
- The persisted command meaning stops at REQUESTED until the existing command
  lifecycle advances it.
- An immediate liquidation request does not create a persistent operation
  mode.
- A duplicate request with the same command identity remains idempotent.
- The request contract does not add Queue, SendOrder, or Chejan fields and
  does not bypass their existing production gates.

7. Durable Snapshot Failure Evidence

- A failed broker snapshot keeps the normalized CommRqData result code in the
  existing `production_recovery_reviews[].broker_evidence.result` field.
- A repeated OPEN record with the same Recovery dedupe identity may enrich its
  existing broker/runtime evidence without adding another history row.
- Later RESOLVED processing preserves the original failure evidence, including
  the broker result code; resolution adds success evidence without deleting the
  failed history.

8. Completed Snapshot Process-Local Handoff

- Only a complete immutable `BrokerAccountSnapshot` whose account, trading
  day, login session, Recovery session, and final account status all match a
  `COMPLETED` Recovery may be retained as a process-local MainWindow handoff.
- The handoff is not a persistent SoT and is cleared by a new/failed Recovery,
  account or login lifecycle change, trading-day change, disconnect, or
  MainWindow shutdown.
- Recovery completion never repairs stock position state automatically. The
  handoff is read only by the explicit Review Management position
  reconciliation action, whose service boundary repeats all identity and
  stale-state checks fail-closed.
