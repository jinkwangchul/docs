1. 매도 실행 구조 갱신
================================================================================

1.1 SELL 신호와 매도방식의 역할
- 메인 SELL 신호는 최초 매도 트리거다.
- SELL 신호가 발생하면 매도방식 설정을 사용하여 최초 1회 매도계획을 생성한다.
- 최초 매도방식은 메인 신호에 의해 1회만 실행되는 것이 원칙이다.
- 이후 미체결 취소, 잔량 재매도, 완료 처리는 메인 SELL 신호 재검출 없이 별도 흐름으로 진행할 수 있다.

1.2 미체결 이후 재매도 흐름
- 최초 매도주문 후 미체결정책에 의해 미체결 주문이 취소될 수 있다.
- 취소 후 잔량이 남으면 재매도 또는 완료정책이 실행된다.
- 재매도는 메인 SELL 신호와 별개로 수행된다.
- 재매도 또는 완료정책에서 나온 주문도 다시 미체결정책 적용 대상이다.
- 이 흐름은 다음과 같다.

SELL 신호 발생
→ 매도방식 실행
→ 미체결정책 적용
→ 잔량 없음: 완료
→ 잔량 있음: 완료정책/재매도정책 실행
→ 미체결정책 재적용
→ 잔량 있으면 반복
→ 마지막회/반복한도/시간한도/검토관리 조건에 따라 종료

1.3 완료정책의 재정의
- 완료정책은 단순 완료 판정이 아니라 “잔량 재매도 정책”에 가깝다.
- 명칭은 당장은 완료정책으로 유지하되, 문서상 의미는 다음과 같이 정의한다.
  완료정책 = 최초 매도 이후 남은 잔량을 어떻게 매도 완료할지 결정하는 재매도 전략 영역
- 차후 UI 명칭은 “잔량매도정책”, “재매도정책”으로 변경 검토 가능하다.

1.4 매도방식과 완료정책의 재사용 관계
- 매도방식과 완료정책은 동일한 매도 실행 폼을 재사용할 수 있다.
- 단, 설정값은 반드시 분리한다.
- 구현 코드는 하나의 SellExecutionPolicy 공통 컴포넌트를 사용할 수 있으나, UI 인스턴스와 저장 데이터는 분리한다.
- 예:
  main_sell_policy: 메인 SELL 신호 최초 매도 설정
  retry_sell_policy: 미체결/잔량 재매도 설정
- 이 구조를 통해 최초 매도에서는 시장가를 사용하지 않고, 재매도에서는 마지막회 시장가를 사용하는 등 유연성을 확보한다.

2. 매도방식 UI 갱신
================================================================================

2.1 매도방식 기본 구조
매도방식은 다음 항목으로 구성한다.
- 단일호가
- 다중호가
- 다중지점

단일호가와 다중호가는 상호배타로 동작한다.
다중지점 내부의 시간 기준과 가격/평단 기준도 상호배타로 동작한다.

2.2 다중호가
표시 형식:
- 상향 [4] 호가 / 기준 1호가 / 하향 [2] 호가 | 합계 [7]호가

합계 계산:
- 상향 수 + 기준 1호가 + 하향 수
- 예: 4 + 1 + 2 = 7호가

2.3 다중지점 시간 기준
표시 형식:
- 시간 [30][분/초/봉][이내/간격][3]회 [주문가/현재가]

SELL 매도방식에서는 시장가를 시간 기준 주문 콤보에 넣지 않는 방향이었다.
BUY 매수방식에서는 시장가가 단일호가에서만 가능하도록 제한하는 로직이 있었다.
시장가 사용 가능 여부는 추후 메인 주문 정책과 충돌하지 않게 재검토한다.

2.4 다중지점 가격 기준
표시 형식:
- [주문가/현재가/평단가] 대비 [주문가/현재가/평단가] [상향/하향/상하] [0.15]% [이상/이하/이내/이탈] / [3]회

중요 변경:
- 기존 “에” 표현은 “대비”로 변경한다.
- 예: “주문가에 평단가” → “주문가 대비 평단가”
- 방향에 따라 비교 콤보 표시 옵션을 제한한다.
  상향/하향: 이상/이하
  상하: 이내/이탈

2.5 마지막회 주문 타입
기존:
- 마지막회 시장가 매도

변경:
- 마지막회 [시장가/현재가]

의미:
- 다중지점 설정의 하위 항목이다.
- 다중지점 시간/가격 조건 중 하나가 활성화되어야 선택 가능하다.
- 마지막회 주문을 시장가로 할지 현재가로 할지 선택한다.
- 이 설정은 최초 매도방식과 완료정책에서 독립적으로 가져갈 수 있어야 한다.

3. 미체결정책 UI 갱신
================================================================================

3.1 미체결정책의 기본 역할
- 미체결정책은 매수/매도 주문 후 미체결 주문을 어떤 기준으로 취소할지 결정한다.
- 최초 주문뿐 아니라 재매도/완료정책에서 나온 주문에도 공통 적용될 수 있다.
- 미체결정책은 주문 실행 엔진이 아니라 취소 판단 정책이다.

3.2 시간 기준 취소 문구
SELL:
- 매도 미체결 발생 시 [매회/일괄] 기준 [20][분/초/봉] 후 주문취소

BUY:
- 매수 미체결 발생 시 [매회/일괄] 기준 [20][분/초/봉] 후 주문취소

콤보 순서:
- 분/초/봉

기본값:
- 현재 UI에서는 20초를 기준으로 쓰는 화면이 많았다.
- 단, 콤보 아이템 순서는 분/초/봉으로 유지한다.

3.3 매회/일괄 정의
매회:
- 각 주문별 미체결 발생 기준.
- 각 주문마다 개별 타이머를 적용한다.
- 해당 주문이 지정 시간 동안 미체결이면 그 주문을 취소한다.

일괄:
- 메인 신호에 따른 매도방식 1세트 종료 시점 기준.
- 세트가 끝난 뒤 지정 시간 경과 후 남은 미체결 주문을 일괄 취소한다.
- 개별 주문마다 지정시간을 재는 방식이 아니다.

3.4 가격조건 취소 1줄 추가
미체결정책에 다음 1줄을 추가한다.

SELL:
- [주문가/현재가/평단가] 대비 [주문가/현재가/평단가] [상향/하향/상하] [0.15]% [이상/이하/이내/이탈] 매도주문취소

BUY:
- [주문가/현재가/평단가] 대비 [주문가/현재가/평단가] [상향/하향/상하] [0.15]% [이상/이하/이내/이탈] 매수주문취소

기본 체크:
- 기본값은 꺼짐(False)이 적절하다.
- 기존 시간 기준 취소는 켜짐(True) 유지 가능.

3.5 가격조건 비교 콤보 숨김 규칙
반드시 적용:
- 방향이 상향이면 비교 콤보는 이상/이하만 표시.
- 방향이 하향이면 비교 콤보는 이상/이하만 표시.
- 방향이 상하이면 비교 콤보는 이내/이탈만 표시.
- 숨김 처리는 QComboBox view row hidden 방식으로 기존 공통폼과 동일하게 한다.
- 방향 변경 시 현재 선택값이 보이는 옵션에 없으면 자동으로 적절한 기본값으로 바꾼다.
  상하: 이내
  상향/하향: 이하

3.6 기존 가격조건 3줄 폐기
기존 3줄:
- 주문가 대비 현재가 ...
- 현재가 대비 평단가 ...
- 평단가 대비 주문가 ...
이 3줄을 미체결정책에 그대로 두는 것은 폐기한다.
앞으로는 위의 가격조건 1줄만 추가한다.

4. 완료정책 UI 갱신
================================================================================

4.1 완료정책 첫 줄 삭제
삭제 대상:
- 마지막 주문 취소 이후 [3][분] 동안 수행

삭제 이유:
- 현재 완료정책 구조에서 이 항목의 의미가 불명확하다.
- 완료정책이 재매도 전략으로 재정의되는 상황에서 상단 실행시간 행은 혼란을 만든다.
- 사용자는 해당 행 삭제를 요청했다.

4.2 삭제 시 구현 주의사항
단순히 UI 행만 제거하면 안 된다.
해당 체크박스를 참조하는 내부 로직도 함께 정리해야 한다.

점검 대상 속성:
- complete_after_cancel_check
- sell_complete_after_cancel_check
- complete_after_cancel_line
- complete_after_cancel_unit_combo
- complete_after_cancel_tail_label
- sell_complete_after_cancel_line
- sell_complete_after_cancel_unit_combo
- sell_complete_after_cancel_tail_label

점검 대상 메서드:
- sync_detail_row_enabled
- sync_fill_ratio_enabled
- sync_complete_mode
- sync_after_cancel_by_multi_point
- toggled.connect 관련 구문

발생했던 오류:
- AttributeError: 'MacdRoutineSettingsDialog' object has no attribute 'complete_after_cancel_check'
- 원인은 삭제된 체크박스를 참조하는 로직이 남아 있었기 때문이다.

4.3 완료정책 남길 항목
완료정책에는 다음 항목을 남긴다.
- 단일호가
- 다중호가
- 다중지점
- 마지막회차 시장가 또는 향후 마지막회 [시장가/현재가] 구조

추후 완료정책도 매도방식과 같은 공통 SellExecutionPolicy UI를 재사용할 수 있다.
단, 현재 단계에서는 대규모 리팩토링 금지.

5. 신호검출조건 UI 갱신
================================================================================

5.1 조건 B 볼린저밴드 추가
매도 신호검출조건 B에 볼린저밴드를 가격박스와 같은 형태로 추가한다.

예:
- 가격박스 [하향] [0.1]% [이상]
- 볼린저밴드 [하향] [0.1]% [이상]
- [주문가/현재가/평단가] 대비 [주문가/현재가/평단가] ...

5.2 조건 C 가격필터 추가
매도 신호검출조건 C 상단에 가격필터를 추가한다.

예:
- [주문가/현재가/평단가] 대비 [주문가/현재가/평단가] [상하] [0.25]% [이내]
- MACD선 - 1.0 이하
- 배열 5 > 20 > 60

5.3 “대비” 용어 통일
신호검출조건 A/B/C, 매수방식, 매도방식, 완료정책, 미체결정책 등 가격 비교형 공통폼에서 “에”는 “대비”로 통일한다.
단, 범위 확인 없이 전체 문자열 치환하지 않는다.

6. 구현상 금지 및 주의
================================================================================

6.1 금지
- 파일 전체 리팩토링 금지
- 무단 ZIP 생성 금지
- 사용자가 요청하지 않은 저장 기능 구현 금지
- rules.json 저장 기능 구현 금지
- 실주문 연결 금지
- 주문취소 실제 실행 로직 구현 금지
- 신규 신호 개념 추가 금지
- HOLD 개념 추가 금지
- AND NOT, OR NOT 연산자 표현 금지

6.2 필수 검증
파일 수정 후:
- py_compile 실행
- 문자열 검색:
  - "마지막 주문 취소 이후"가 남아 있는지
  - complete_after_cancel_check 참조가 남아 있는지
  - sell_complete_after_cancel_check 참조가 남아 있는지
  - "QLabel(\"에\")"가 남아 있는지
  - 미체결정책 가격조건이 중복 추가되었는지
  - add_cancel_gap_row가 불필요하게 여러 번 호출되는지
- 가능하면 GUI 실행 테스트에서 루틴 설정창 열기까지 확인한다.

6.3 PyQt 주의
- py_compile 통과는 런타임 안전을 보장하지 않는다.
- 위젯 속성을 삭제하면 signal connect와 sync 함수에서 AttributeError가 발생할 수 있다.
- UI 삭제는 반드시 참조 제거까지 같이 해야 한다.
- 공통 함수 교체는 BUY/SELL 양쪽에 영향을 준다.

7. 마스터스펙 반영 결론
================================================================================

이번 갱신의 핵심 결론은 다음과 같다.

1) 매도방식은 메인 SELL 신호 발생 시 최초 1회 실행되는 매도계획이다.
2) 미체결정책은 최초 매도와 재매도 주문 모두에 공통 적용되는 취소정책이다.
3) 완료정책은 완료판정이 아니라 잔량 재매도 전략으로 재정의한다.
4) 매도방식과 완료정책은 같은 형태의 UI/엔진을 재사용할 수 있으나 설정값은 분리한다.
5) 미체결정책 시간 기준은 “매회/일괄 기준”으로 구분한다.
6) 미체결정책에는 가격 대비 취소 조건 1줄을 추가한다.
7) 가격 비교 표현은 “에”가 아니라 “대비”를 사용한다.
8) 방향 선택에 따라 비교 콤보는 이상/이하 또는 이내/이탈만 표시한다.
9) 완료정책 상단 “마지막 주문 취소 이후” 행은 삭제한다.
10) 삭제한 UI 위젯 참조가 남아 있으면 런타임 오류가 발생하므로 반드시 참조 로직까지 정리한다.
