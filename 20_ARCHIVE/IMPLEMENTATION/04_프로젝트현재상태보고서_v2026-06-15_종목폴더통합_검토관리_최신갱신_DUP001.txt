1. 현재 작업의 큰 흐름

이번 창의 핵심 작업은 “기초종목.txt 및 루틴폴더 내부 종목폴더 중심 구조”에서 “중앙 stocks/ 종목폴더 중심 구조”로 종목관리 기준을 통합하는 것이었다.

확정 방향:
- 종목 원본은 중앙 stocks/ 아래 종목폴더로 일원화한다.
- 루틴폴더는 루틴 정의와 예산 파일을 보관하는 역할만 유지한다.

- 종목 등록/삭제와 루틴 지정/해제는 용어와 기능을 분리한다.
- 검토관리도 구형 루틴폴더가 아니라 중앙 stocks/state.json 기준으로 수집해야 한다.

2. 용어 정리 확정

종목관리 용어:
- 종목 등록: 중앙 stocks/ 종목관리 라이브러리에 종목을 추가한다.
- 종목 삭제: 중앙 stocks/ 종목관리 라이브러리에서 종목을 제거하거나 archive로 이동한다.
- “등록해제”라는 표현은 종목관리 문맥에서 사용하지 않는다.

루틴관리 용어:
- 루틴 지정: 등록된 종목에 MACD매매루틴 같은 자동매매 루틴을 연결한다.
- 루틴 해제: 종목은 유지하고 루틴 연결만 제거한다.

검토관리 용어:
- 검토관리 이동: 문제 종목을 자동매매 운영대상에서 제외하고 검토관리창에서 관리한다.
- 검토관리 복귀: 문제 원인 해소 후 운영자가 명시적으로 원래 운영 흐름으로 되돌린다.
- 복귀는 단순 플래그 제거가 아니다. 보유/미수/미도/평단/주문잔량/서버불일치 등 문제가 남아 있으면 복귀되어서는 안 된다.

4. 루틴폴더 관련 정리

루틴폴더 자체는 당장 삭제하지 않는다.
이유:
- _MACD매매루틴/
- _등록확인폴더/
같은 루틴폴더 안에 budget.json이 존재하며, 루틴 정의 또는 예산 정보 파일로 사용될 수 있다.

정리 기준:
- 루틴폴더 자체는 유지한다.
- budget.json은 유지한다.
- 루틴폴더 내부 종목폴더는 구형 구조 잔재로 보고 제거/archive 대상이다.
- 루틴폴더 내부 txt/zip 파일은 실제 운영 참조가 없으면 제거 가능하다.
- 사용자가 일부 잔재 파일을 직접 삭제했다.
- 삭제 후 프로그램이 정상 동작하면 해당 파일은 죽은 파일로 판정 가능하다.

주의:
- 루틴 지정 후 루틴폴더 내부에 새 종목폴더가 다시 생기면 아직 구형 생성 로직이 남은 것이다.
- 해당 버그는 ensure_stock_runtime_files(selected_routine_dir, code, name) 호출 경로를 제거하면서 해결했다.
- 이후에도 재발하면 gui_routine_assign_window.py, gui_config_utils.py, gui_stock_data.py에서 stock_runtime_dir_for_routine, ensure_stock_runtime_files, mkdir, makedirs, f"{code}_{name}" 계열을 재검색해야 한다.

============================================================
5. 현재 정책상 큰 변경점
============================================================

5.1 조기/자동마감

기존 문서 기준으로는 조기/자동마감이 운영 종료 절차였고, 실제 구현/해석상 “추가매수 금지 + 매도만”에 가까웠다.
이번 갱신으로 다음처럼 수정한다.

- 조기마감/자동마감은 마감상태 진입.
- 마감상태에서도 루틴 매수신호와 매도신호 수용 가능.
- 매수횟수 제한은 두지 않음.
- 여러 번 매수가 진행되면 관제창에서 표시.
- 조기마감은 운영자 개입, 자동마감은 설정값에 따른 자동 진입.
- 본질은 동일한 마감상태.

5.2 예산/완충

- 예산은 총 운영자금.
- 예산 = 가용예산 + 완충예산.
- 완충은 예산 밖 추가 자금이 아니라 예산 내부 비상구간.
- 예산 상태는 정상/경고/완충진입 3단계.
- 경고는 운영자 개입 요구 구간.
- 완충진입은 비상복구 상태.

5.3 완충복구

- 완충상태에서 신규 매수가 발생하고 완충이 해소되지 않으면 복구정책 실행.
- 복구대상은 운영자가 설정한 선정정책에 따라 고름.
- 이미 조기마감/자동마감/청산/검토관리/정지 종목은 제외.
- 선정된 종목은 조기마감 상태로 전환.
- 기존 조기마감 정책과 청산정책 사용.
- 완충복구 목적의 조기마감에서는 이월 비활성.

5.4 관제창

- 관제창은 계좌/자금/성과/위험 관제센터.
- 별도 환경설정창보다 직접 클릭 수정 방식 지향.
- 예산, 가용/완충 비율, 경고비율, 완충복구 시간, 복구대상 정책, 루틴/종목 매수한도를 관제창에서 직접 수정 가능하게 설계.


============================================================
6. 남은 위험구간
============================================================

구조보다 정책이 위험한 단계이다.

기존 위험구간:
1. 프로그램 재시작 시 보유/미수/미도/이월 판정.
2. 긴급정지 해제 시 재시작과 동일한 판정 적용 여부.
3. 검토관리 복귀 시 현재 조건 재판정 여부.
4. 조기마감 + 이월 + 청산시간대 겹침.
5. 자동마감 + 이월 + 청산시간대 겹침.
6. 마감 진행 중 미수 발견 시 검토관리 이동.
7. 미도 존재 시 처리 대상 판정.
8. 빨강 데이터 불일치 발생 시 자동분류 금지 유지.
9. ATS 장후 시간과 청산/마감 정책 충돌.

신규 위험구간:
10. 조기마감/자동마감 상태에서 매수신호를 허용할 때 기존 로직과 충돌 여부.
11. 마감상태에서 여러 번 매수 후 매도/청산 흐름이 정상 종료되는지.
12. 완충상태에서 신규 매수 발생 후 복구대상 선정이 올바른지.
13. 이미 조기마감/자동마감/청산 종목이 완충복구 대상에서 제외되는지.
14. 완충복구로 조기마감에 편입된 종목에서 이월이 비활성화되는지.
15. 예산 사용금액이 총매입금액 + 매수주문대기금액 기준으로 계산되는지.
16. 매도주문 대기금액을 체결 전까지 회수금으로 보지 않는지.
17. 완충복구 적용시간이 시간운영 설정값 또는 별도 설정값에 따라 동작하는지.
18. 관제창 직접 클릭 수정 값이 즉시 반영되면서도 기존 자동매매설정과 충돌하지 않는지.
