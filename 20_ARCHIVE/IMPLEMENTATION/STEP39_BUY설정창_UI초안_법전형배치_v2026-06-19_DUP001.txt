STEP39_BUY설정창_UI초안_법전형배치_v2026-06-19

작성 목적:
본 문서는 MACD매매루틴 설정창의 BUY 영역을 실제 구현하기 전,
현재까지 정리된 BUY 법전 개념을 UI 배치 형태로 정리한 초안이다.

본 문서는 코드 패치가 아니다.
본 문서는 rules.json 저장 구조가 아니다.
본 문서는 BUY 로직 구현이 아니다.
본 문서는 화면 배치 검토용 설계 초안이다.

------------------------------------------------------------
1. 전제
------------------------------------------------------------

루틴의 본질:
- 루틴은 신호를 발생한다.
- 루틴은 BUY / SELL / CANCEL 신호를 낸다.
- 루틴은 주문 수량, 예산, 실제 주문 실행을 직접 담당하지 않는다.
- 실제 주문 실행과 자금 판단은 메인 엔진/자금관리/주문관리 계층이 담당한다.

BUY 원칙:
- 모든 매수는 BUY 신호 기준이다.
- 최초 BUY, 추가 BUY, 평단 BUY 같은 별도 신호는 만들지 않는다.
- BUY가 여러 번 발생한 것을 운영자가 결과적으로 2회차, 3회차 매수라고 부를 뿐이다.
- BUY 신호 자체는 모두 동등하다.

------------------------------------------------------------
2. BUY 설정창 전체 방향
------------------------------------------------------------

BUY 설정창은 다음 순서로 배치한다.

1. BUY 주신호
2. 적용필터
3. 매수방식
4. 평단관리
5. 미체결정책
6. 완료조건
7. 완료정책
8. 신호 충돌 규칙 표시

------------------------------------------------------------
3. BUY 주신호 영역
------------------------------------------------------------

역할:
- BUY 신호의 핵심 발생 조건을 표시/설정한다.
- 현재 MACD매매루틴 기준으로는 OCR 상승전환이 주신호이다.
- 주신호 다중구성은 현재 사용하지 않는다.

UI 초안:

[BUY 주신호]

BUY / OCR [ -1 ] [ 이하 ] [ 상승전환 ] [ 0 ] 봉

구성 요소:
- 지표: OCR
- 기준값: -1
- 비교: 이하
- 방향: 상승전환
- 판정봉: 0봉 / 1봉 / 2봉 ...

주의:
- -1은 봉 인덱스가 아니라 OCR 기준선 하향 인정선이다.
- 0봉은 판정봉이다.
- 주신호는 1개만 둔다.
- 주신호 다중구성 슬롯은 두지 않는다.

------------------------------------------------------------
4. 적용필터 영역
------------------------------------------------------------

역할:
- BUY 주신호에 추가 적용되는 필터를 설정한다.
- 필터는 주신호를 대체하지 않는다.
- 필터그룹 슬롯은 현재 두지 않는다.
- 각 필터의 끝에 AND / OR / NOT 선택을 둔다.

UI 초안:

[적용필터]

□ RSI              [ 45 ] [ 이하 ]                         [AND]
□ 20이평 대비      [ 5 ]봉 전 [ -0.2 ] %                    [NOT]
□ 시그널/MACD      [ 0 ] [ 이하 ]                           [NOT]
□ 이평배열          [5] [10] [20] 정배열                     [OR]
□ 주가 20이평      [ 이상 ]                                  [AND]

규칙:
- 필터는 필요 항목만 활성화한다.
- 활성 필터가 1개일 때도 해당 필터의 논리는 AND로 둔다.
- 여러 필터가 활성화되면 각 필터별 AND / OR / NOT로 작용방식을 지정한다.
- 필터그룹은 현재 보류/취소한다.

------------------------------------------------------------
5. 매수방식 영역
------------------------------------------------------------

역할:
- BUY 신호가 발생한 후 실제 매수 시도를 어떤 방식으로 전개할지 정한다.
- 매수방식은 가격축과 시간축으로 본다.
- 가격축과 시간축을 조합할 수 있다.

UI 초안:

[매수방식]

가격축
□ 단일호가
□ 다중호가     [ 3 ] 단계

시간축
□ 단일지점
□ 다중지점     [ 3 ] 회 / [ 30 ] 초 내

조합 표시:
- 단일호가 + 단일지점
- 단일호가 + 다중지점
- 다중호가 + 단일지점
- 다중호가 + 다중지점

주의:
- 다중호가는 가격축이다.
- 다중지점은 시간축이다.
- 분할매수는 현재 별도 항목으로 넣지 않는다.
- 모든 매수는 BUY 신호 기준이다.
- 다중지점 확장으로 분할매수 유사 효과를 검토할 수 있으나, 현재는 보류한다.

------------------------------------------------------------
6. 평단관리 영역
------------------------------------------------------------

역할:
- 동일한 BUY 신호들이 여러 번 발생하는 상황에서, 평단 관점의 매수 대응을 설정한다.
- 능동매수는 평단관리 영역에 속한다.
- 능동매수는 단독 사용도 가능하고, 회차증가 등과 조합 가능하다.
- 평단관리는 BUY 신호의 종류를 나누는 것이 아니다.

UI 초안:

[평단관리]

□ 회차증가       [ X2 / X3 / 사용자지정 ]
□ 금액기준       [ 사용 / 미사용 ]
□ 능동매수       [ 사용 / 미사용 ]
□ 근접비율       [     ] %

설명:
- 회차증가는 평단관리 및 제한적 수익률 상승 목적을 함께 가질 수 있다.
- 능동매수는 현재 평단/현재가/평단 개선효과를 기준으로 매수 필요성을 판단한다.
- 능동매수는 회차증가의 후처리일 수도 있고, 단독 수행일 수도 있다.
- 실제 테스트를 통해 유효성을 검증한다.

주의:
- 최초진입금액/수량은 루틴 설정이 아니다.
- 최초진입금액/수량은 메인 자금관리/주문관리 계층에서 다룬다.
- 루틴은 BUY 신호와 루틴 특성 조건을 제공한다.

------------------------------------------------------------
7. 미체결정책 영역
------------------------------------------------------------

역할:
- BUY 가공 과정에서 체결되지 않은 주문을 어떻게 기술적으로 처리할지 정의한다.
- CANCEL은 매수 여부를 판단하는 것이 아니다.
- CANCEL은 기술적 매수를 위한 준비 단계이다.
- CANCEL은 BUY/SELL 가공 과정의 일부로 들어간다.

UI 초안:

[미체결정책]

시간 캔슬
□ 주문 후 [ 20 ] [ 초 / 분 ] 이후 CANCEL

가격 이탈 캔슬
□ 주문가 대비 [ 3 ] % [ 상향 / 하향 / 상하 ] 이탈 시 CANCEL

설명:
- CANCEL은 주문 취소 자체와 동일한 개념이 아니다.
- 메인 엔진의 주문취소 로직과 루틴 CANCEL은 기능 목표가 다르다.
- BUY > CANCEL > BUY > CANCEL > BUY 구조는 포지셔닝 과정의 기술적 전개이다.
- CANCEL 시점의 미체결 수량/금액은 완료조건으로 넘어가 판단된다.

주의:
- CANCEL은 HOLD가 아니다.
- CANCEL은 매수 안함 신호가 아니다.
- CANCEL은 독립 사이클이 아니다.

------------------------------------------------------------
8. 완료조건 영역
------------------------------------------------------------

역할:
- 마지막 CANCEL 이후 또는 BUY 가공이 진행된 이후, 현재 포지셔닝을 완료로 볼지 판단한다.
- 완료조건은 출구전략이며 차악을 선택하는 과정의 기준이다.
- 완료조건 자체가 기준이다.
- 별도의 최초목표/재계산목표 같은 외부 기준을 추가하지 않는다.

UI 초안:

[완료조건] [ 3 ] 봉

□ 가격괴리율        [ 0.1 ] %                         [AND]
□ 수량충족률        [ 95 ] %                          [AND]
□ 20이평            [ 3 ]봉 전 대비 [ 0.5 ] % 상승      [OR]

판정 규칙:
- [3]봉은 체크박스 조건이 아니라 완료판정 발동 기간이다.
- 3봉 내에 조건 판정 로직이 작동한다.
- 완료조건은 판정기간 내 충족 이력을 기준으로 본다.
- 조건이 한 번 충족되면 이후 깨져도 해당 조건은 충족 이력으로 인정한다.
- 활성 조건 1개일 때는 기본 AND 고정이다.
- 활성 조건 2개 이상이면 각 조건 끝에 AND / OR / NOT을 설정한다.

조건 논리:
- AND: 판정기간 내 해당 조건 충족 이력이 필요하다.
- OR: 판정기간 내 하나라도 충족되면 완료 가능하다.
- NOT: 판정기간 내 해당 조건이 발생하면 완료 차단/실패 요소로 본다.

주의:
- 가격괴리율은 주가 파동 때문에 충족 후 다시 깨질 수 있다.
- 따라서 현재 상태가 아니라 판정기간 내 충족 이력을 본다.
- 수량충족률은 한 번 충족되면 동일 신호 처리 안에서 깨질 가능성이 낮다.

------------------------------------------------------------
9. 완료정책 영역
------------------------------------------------------------

역할:
- 완료조건이 미충족일 때 수행하는 정책이다.
- 완료조건이 충족되면 BUY 단계 완료로 본다.
- 완료조건이 미충족되면 완료정책을 수행한다.
- 완료정책 수행 후에도 제한 시간/신규 신호 전까지 완료조건 재판정을 받을 수 있다.

UI 초안:

[완료정책]

○ 능동매수
○ 매수안함

규칙:
- 완료조건 충족 → BUY 단계 완료
- 완료조건 미충족 → 완료정책 수행
- 완료정책은 능동매수 / 매수안함만 둔다.
- 현재 상태로 완료, 검토표시 등은 두지 않는다.
- 남은 리스크는 관제창에서 표시하고 운영자 개입 또는 마감/청산 계층에서 처리한다.

주의:
- 완료정책 실패 후 추가 정책 같은 무한구조를 만들지 않는다.
- 관제창, 마감정책, 청산정책이 뒤를 받는다.

------------------------------------------------------------
10. 신규 신호 우선 규칙
------------------------------------------------------------

역할:
- BUY 진행중 또는 완료조건/완료정책 진행중에 새로운 신호가 발생했을 때 처리한다.

UI 표시 초안:

[신호 충돌 규칙]

신규 BUY / SELL 신호 발생 시:
- 기존 BUY 가공 중단
- 기존 미체결/CANCEL 흐름 종료
- 기존 완료조건/완료정책 흐름 종료
- 후행 신호 우선 추종

설명:
- 신호와 신호 사이에 시간적 간격이 없을 때는 선행작업을 종료하고 후행신호를 우선한다.
- BUY 진행중 SELL 발생 시 기본적으로 SELL을 수행한다.
- 단, SELL 자체의 채택/무시/강도 판단은 SELL 법전에서 별도 논의한다.

12. 현재 보류 항목
------------------------------------------------------------

보류:
- 분할매수
- 주신호 다중구성
- 필터그룹
- 재진입정책
- 신호유지
- 주문수량정책
- HOLD

보류 이유:
- 분할매수는 다중지점 확장으로 대체 가능성 검토
- 주신호 다중구성은 현재 사용하지 않음
- 필터그룹은 필터별 AND/OR/NOT으로 충분
- 재진입정책/신호유지는 루틴 신호철학과 맞지 않음
- 주문수량정책은 메인 자금관리/주문관리 영역
- HOLD는 프로젝트에 존재하지 않는 신호

14. 최종 결론
------------------------------------------------------------

현재 BUY 법전은 개념 추가 단계가 아니라 UI 배치 단계로 넘어갈 수 있다.
추가 개념은 UI 구성 중 충돌이 발견될 때만 다시 논의한다.
