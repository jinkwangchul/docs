2. 확인된 주요 구조
------------------------------------------------------------

1) gui_routine_assign_window.py
- RoutineAssignWindow 존재
- 루틴 목록 테이블 존재
- 루틴 지정/해제 중심 창
- 루틴명 목록을 표시하고 종목에 루틴을 연결하는 역할
- 현재 구조상 루틴별 상세 설정창을 여는 버튼은 명확히 분리되어 있지 않음
- 루틴 선택/루틴명 표시 구조는 있으므로 향후 "설정" 버튼 추가 후보가 될 수 있음

2) gui_auto_trade_setting_window.py
- AutoTradeSettingWindow 존재
- 자동매매 설정창의 중심 파일
- 루틴 테이블, 종목 테이블, 운영/시간/청산/정책 관련 다수 기능 보유
- 이미 파일 크기와 책임이 큼
- 여기에 MACD 설정 UI 본체를 직접 넣으면 파일 비대화와 충돌 위험이 큼
- 단, 선택된 루틴의 설정창을 호출하는 연결 지점으로는 사용할 수 있음

3) gui_routine_condition_engine.py
- 루틴 조건 평가 공통 엔진
- GUI 창이 아니라 조건 평가 로직 파일
- 조건그룹 내부 AND, 그룹 간 OR 평가 구조
- UI 구현 대상이 아니라 조건 평가 재사용 대상
- MACD 설정 UI 본체를 여기에 넣으면 안 됨

4) gui_routine_registry.py
- routines/<루틴명>/routine.json 구조 우선 인식
- routine.py는 존재 여부만 확인하고 직접 실행하지 않는 구조
- 루틴 자동 인식/목록화 담당
- MACD 설정 UI가 루틴 디렉터리와 rules.json 경로를 찾을 때 참고 가능

5) gui_routine_service.py / gui_routine_policy.py
- 루틴 지정/해제, 정책 가드, 상태 보호와 관련
- 설정 UI 본체가 들어갈 위치는 아님
- 루틴 설정 변경 시 향후 정책 검증/보호와 연결될 가능성은 있음

6) routines/MACD매매루틴/routine.py
- rules.json 자동 로드 구조 존재
- context["routine_config"], context["rules"], rules.json, DEFAULT 순서의 로드 원칙과 연결됨
- STEP23 기준 context 전달 구조로 확장된 파일을 적용한 상태라면 평단 기반 SELL 평가 가능

7) routines/MACD매매루틴/rules.json
- 현재 rules_version 0.2.0 확인
- principle.signal_only true
- principle.execution_enabled false
- buy 구조 존재
- sell 구조 존재
- STEP23 실제 검증 후 v0.3 점검 문서는 작성됐지만 실제 rules.json 교체는 아직 하지 않음

8) engines/macd_signal_engine.py
- MACD 루틴 신호 평가 엔진
- STEP23 파일 적용 전 압축본 기준은 context 인자 미반영 가능
- 사용자 실행 결과상 STEP23 엔진 교체 후 테스트 통과 확인됨
- UI 구현 전 실제 작업 폴더의 최신 파일 기준 재확인이 필요함

3. MACD 설정 UI 본체 위치 후보
------------------------------------------------------------

후보 A:
gui_auto_trade_setting_window.py 내부에 직접 구현

장점:
- 자동매매설정창과 바로 연결 가능
- 선택된 루틴/종목 컨텍스트 접근이 쉬울 수 있음

단점:
- 파일이 이미 매우 큼
- 운영정책/시간정책/청산/상태관리와 섞일 위험
- MACD 설정 UI가 커지면 유지보수 악화
- 사용자 프로젝트의 구조분리 철학과 다소 충돌

판정:
- 본체 구현 위치로는 비추천
- 호출 버튼/연결 지점으로만 활용 권장

후보 B:
gui_routine_assign_window.py 내부에 직접 구현

장점:
- 루틴 목록과 가까움
- 루틴 선택 후 설정 버튼을 붙이기 쉬움

단점:
- 이 창의 본래 역할은 루틴 지정/해제
- 설정 UI 본체가 들어가면 지정창 책임이 커짐
- MACD 외 다른 루틴 설정 확장 시 복잡해짐

판정:
- 본체 구현 위치로는 비추천
- 루틴 선택 후 설정창 호출 지점으로는 후보 가능

후보 C:
신규 파일 생성
예:
- gui_macd_routine_settings_dialog.py

장점:
- MACD 설정 UI 책임 분리
- 기존 대형 GUI 파일 오염 최소화
- 향후 다른 루틴 설정창도 같은 패턴으로 확장 가능
- STEP27 B안 확장형 UI 구조를 독립적으로 구현 가능
- 저장 기능을 나중에 추가하기 쉬움
- 초기 읽기전용/미리보기 전용 구현이 안전함

단점:
- 호출 연결 코드가 별도로 필요
- 기존 창에 버튼 추가 필요

판정:
- 가장 안전한 후보

4. 권장 구조
------------------------------------------------------------

권장 신규 파일:
- gui_macd_routine_settings_dialog.py

역할:
- MACD매매루틴 rules.json 읽기
- 기본설정 / BUY / SELL / 확장예정 탭 표시
- 초기에는 저장 기능 비활성
- 읽기/미리보기 중심
- STEP23 완료된 SELL 항목 일부만 편집 가능 후보로 표시
- BUY/CANCEL/확장 항목은 잠금 표시

호출 위치 후보:
1. gui_routine_assign_window.py
- 루틴 목록에서 MACD매매루틴 선택 후 "설정" 버튼
- 루틴 자체 설정을 여는 흐름으로 자연스러움

2. gui_auto_trade_setting_window.py
- 자동매매설정창의 루틴 목록에서 선택 후 "루틴 설정" 버튼
- 운영 중 설정과 가까우나 초기에는 조심 필요

초기 권장:
- gui_routine_assign_window.py 쪽 호출이 더 안전
- 이유: 종목 운영 상태와 덜 결합되어 있고, 루틴 자체 설정 의미가 더 강함

다만 사용자 운용 흐름상 자동매매설정창에서 루틴 설정 접근이 더 편하면,
호출 버튼만 gui_auto_trade_setting_window.py에 추가하고 본체는 신규 파일로 분리하는 방식이 가능하다.

6. UI 연결 전 확인 필요 사항
------------------------------------------------------------

실제 코드 작성 전 확인해야 할 사항:

1. 설정창 접근 위치
- 루틴 지정창에서 열 것인가
- 자동매매설정창에서 열 것인가
- 둘 다 열 수 있게 할 것인가

2. 저장 기능
- 이번 단계에서는 없음/비활성으로 할 것인가
- 미리보기만 둘 것인가

3. 편집 허용
- SELL 항목도 이번에는 읽기 전용으로 시작할 것인가
- 아니면 signal_logic/profit_rate_sell 정도는 편집 가능하게 할 것인가

4. 파일 적용 방식
- 신규 파일만 먼저 제공할 것인가
- 기존 GUI 파일에 버튼 연결 패치까지 제공할 것인가

8. 최종 결론
------------------------------------------------------------

STEP28 결론:

- MACD 설정 UI 본체는 기존 대형 GUI 파일에 직접 넣지 않는다.
- 신규 파일 gui_macd_routine_settings_dialog.py로 분리하는 것이 안전하다.
- 기존 gui_auto_trade_setting_window.py 또는 gui_routine_assign_window.py는 호출 버튼만 담당하는 것이 맞다.
- 초기 구현은 읽기전용/미리보기 중심으로 한다.
- 저장 기능은 아직 넣지 않는다.
- 다음은 신규 다이얼로그 초안 생성이 적절하다.
