MASTER_SPEC_추가갱신_프로젝트_데이터계약카탈로그_Data_Contract_Catalog_2026-07-03

목적
- 프로젝트에서 교환되는 주요 데이터 객체의 계약(Contract)과 책임을 표준화한다.

==================================================
1. 데이터 계약 원칙
==================================================
- 데이터 구조는 명시적으로 정의한다.
- 필수 필드와 선택 필드를 구분한다.
- 하위 호환성을 우선 유지한다.
- 계약 변경 시 Runtime Specification을 함께 갱신한다.

==================================================
2. Signal Contract
==================================================
필수
- id
- routine
- code
- signal
- status
- created_at

선택
- reason
- matched_groups
- details
- signal_index
- delay_bar

==================================================
3. Order Candidate Contract
==================================================
필수
- id
- side
- quantity
- price
- candidate_status

선택
- order_intent
- order_provenance
- execution_enabled

==================================================
4. Execution Contract(예정)
==================================================
- request_id
- order_id
- request_hash
- sent_at
- execution_status

==================================================
5. Fill Contract(예정)
==================================================
- fill_id
- order_id
- filled_qty
- filled_price
- filled_at

==================================================
6. Position Contract(예정)
==================================================
- position_id
- code
- quantity
- average_price
- updated_at

==================================================
7. 계약 검증
==================================================
□ 필수 필드 존재
□ 타입 일관성
□ 상태값 유효성
□ 참조 무결성

최종 원칙
데이터 계약은 구현이 아니라 시스템 간 약속이며,
모든 변경은 추적 가능하고 하위 호환성을 고려해야 한다.
