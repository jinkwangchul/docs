2. 현재 BUY 계층 상태
------------------------------------------------------------

현재 구현 완료로 볼 수 있는 항목:
- BUY 신호 생성 가능
- rules.json 자동 로드 구조에서 BUY 조건 임시 강제 테스트 통과 이력 있음
- condition_engine 기반 조건 평가 사용 가능
- 조건그룹 내부 AND
- 그룹 간 OR
- delay_bar
- BUY / SELL / signal=None 원칙 유지

현재 점검상 BUY는 SELL처럼 다음 구조로 독립 신호 계층화가 아직 완료된 상태는 아니다.

SELL 쪽 최신 구조:
- sell.signal_logic
- sell.signals.macd_sell
- sell.signals.profit_rate_sell

BUY 쪽은 향후 이와 유사하게:
- buy.signal_logic
- buy.signals.macd_buy
- buy.signals.추가매수/평단기반/다중매수 계열
같은 형태로 확장 가능성이 있으나,
아직 사용자 확정 전이므로 구현 금지.

------------------------------------------------------------
3. BUY 구조를 바로 구현하면 위험한 이유
------------------------------------------------------------

BUY는 단순 진입 신호가 아니다.

현재 참조 문서와 대화 흐름 기준으로 BUY는 다음 철학과 연결되어 있다.

- 포지션 구축
- 평단 중심
- 지속매수
- 매수회차
- 단일매수
- 다중매수
- 다중호가매수
- 다중지점매수
- 향후 능동매수/평단괴리보정/포지션구축보정 가능성

따라서 BUY를 단순히 "macd_buy 조건 만족 시 BUY" 수준으로만 확장하면
향후 UI, 평단 기반 추매, 지속매수, CANCEL 신호 개념과 충돌할 수 있다.

------------------------------------------------------------
4. 현재 확정 가능 범위
------------------------------------------------------------

현재 확정 가능:
1. BUY는 공식 루틴 신호다.
2. BUY는 주문 직접 실행이 아니라 메인에 전달되는 신호/제안이다.
3. BUY 판단에는 rules.json 설정값과 context 상태값이 모두 필요해질 수 있다.
4. 설정값은 config/rules.json에 둔다.
5. 평단, 현재가, 보유수량, 누적투입금액 등 상태값은 context로 둔다.
6. config에 평단/현재가를 넣지 않는다.
7. HOLD는 어떤 경우에도 BUY의 반대 개념으로 넣지 않는다.

- 능동매수 구현

- BUY 실패/미완성/포지션 구축 실패 판정 공식 임의 생성

이 항목들은 UI 진입 또는 B안 진행 시 사용자와 개념 확정 후 구현해야 한다.

  enabled: true
  signal_logic: "OR"

      enabled: true

- 구조 예약도 사용자 승인 필요

- BUY 구조 구현 보류
- 먼저 UI에서 필요한 설정 항목을 확정
- 그 후 rules.json v0.3 또는 v0.4로 반영

장점:
- 프로젝트 철학 훼손 위험 최소
- 평단 중심 철학 반영 가능
- CANCEL/다중매수/지속매수와 함께 설계 가능

단점:
