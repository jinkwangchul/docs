A

C
NOT A
NOT B
NOT C
이런 별도 조건 개념이 아니다.

그냥 수식을 왼쪽부터 읽는다.

예:

A AND B NOT C
=

A 이고
B 이고
C 가 아닌 것
즉 사용자는

A
AND
B
NOT
C
를 순서대로 입력한다.

여기서

NOT
은 AND/OR와 같은 레벨의 토큰이다.

그래서 네 관점에서는

A AND B NOT C
정상.

반대로 내가 말한

A AND NOT B
같은 일반 프로그래밍 논리식 해석은 프로젝트 규칙과 다르다.

즉 현재 프로젝트 문법은:

A AND B NOT C
A OR B NOT C
A AND B OR C
(A AND B) NOT C
등을 허용할 수 있고,

중요한 건

NOT
을 특별 연산자로 해석하지 말고

사용자가 입력한 순서를 그대로 유지하는 것이다.

그래서 앞으로는

A
AND
B
NOT
C
를

(A) AND (B) AND (NOT C)
의 의미로 이해해야 한다.

내가 계속 일반 논리식 기준으로 해석해서 규칙을 엉뚱하게 잡고 있었다. 지금 설명한 규칙 기준으로 다시 보면 입력기 검증도 다시 정리해야 한다.

A AND B NOT C
의 의미를,

내가 일반 프로그래밍 논리식 기준으로 해석하면서 계속

A AND NOT B
not A
A and not B
같은 방향으로 설명을 끌고 갔다.

그 결과:

입력 규칙이 계속 바뀜

괄호 규칙도 꼬임

NOT 의미도 계속 바뀜

수정파일 여러 개가 서로 다른 규칙으로 생성됨

이건 네가 시간을 낭비했다고 느낄 만한 상황이다.

현재 내가 마지막으로 이해한 규칙은:

A = 조건
B = 조건
C = 조건

AND = 조건 연결
OR = 조건 연결
NOT = 뒤 조건 제외
예:

A AND B NOT C
=

A 만족
B 만족
C 제외
이 규칙을 기준으로 보면 내가 앞에서 말한 여러 해석은 맞지 않았다.
