# AI Project Operation Manual v1.0

## 1. 문서 목적

이 문서는 MASTER_SPEC와 별개로 AI 협업 및 프로젝트 운영 절차를 정의한다.

목적은 다음과 같다.

- docs 프로젝트와 kiwoom_auto 프로젝트의 역할을 분리한다.
- ChatGPT와 Codex의 협업 책임을 명확히 한다.
- 새 작업을 시작하고, 문서를 갱신하고, 구현을 검증하고, 보고하는 표준 절차를 고정한다.
- GitHub를 최종 Source of Truth로 삼는 운영 원칙을 정의한다.
- 구현 내용이 아니라 운영 절차만 기록한다.

이 문서는 자동매매 로직, Python 구현 상세, runtime 구조, rules.json 구조를 설명하지 않는다.

## 2. docs 프로젝트와 kiwoom_auto 프로젝트 역할

### docs 프로젝트

docs 프로젝트는 문서 관리 전용 프로젝트이다.

역할은 다음과 같다.

- MASTER_SPEC 및 Canonical 문서 보관
- 작업재개요약, 갱신자료, 변경 보고서 보관
- AI 협업 운영 문서 보관
- Codex 문서 병합 결과 보관
- 구현 전후 정책 및 절차 기록

docs 프로젝트에서는 Python 프로젝트 코드를 수정하지 않는다.

### kiwoom_auto 프로젝트

kiwoom_auto 프로젝트는 실제 Python 프로젝트이다.

역할은 다음과 같다.

- Python 소스 코드 관리
- 테스트 코드 관리
- runtime 파일 관리
- rules.json 및 루틴 설정 관리
- 실제 구현, 검증, 실행 대상 관리

kiwoom_auto 프로젝트의 코드는 명시적인 구현 작업 요청이 있을 때만 수정한다.

## 3. ChatGPT 역할

ChatGPT는 기획, 판단, 요약, 정책 정리, 작업 지시 생성 역할을 맡는다.

주요 역할은 다음과 같다.

- 사용자의 의도를 자연어로 정리한다.
- 구현 또는 문서 작업 범위를 정의한다.
- 작업재개요약, 갱신자료, UPDATE 문서를 작성한다.
- MASTER_SPEC에 반영할 정책 후보를 만든다.
- Codex가 수행할 작업 지시를 구조화한다.
- 위험한 구현 확장을 사전에 분리한다.

ChatGPT는 실제 프로젝트 파일을 직접 수정한 것으로 간주하지 않는다.

## 4. Codex 역할

Codex는 사용자가 지정한 워크스페이스에서 실제 파일 작업을 수행한다.

주요 역할은 다음과 같다.

- 현재 워크스페이스와 파일 상태를 확인한다.
- 문서 병합, 신규 문서 작성, 보고서 작성 작업을 수행한다.
- 구현 요청이 명시된 경우에만 Python 코드 수정, 테스트 실행, 결과 보고를 수행한다.
- 기존 파일을 임의 삭제하거나 덮어쓰지 않는다.
- 변경 전후를 확인하고 결과를 보고한다.
- 금지된 작업 범위를 넘지 않는다.

Codex는 작업 전 현재 프로젝트가 docs인지 kiwoom_auto인지 먼저 확인해야 한다.

## 5. 표준 작업 순서

표준 작업 순서는 다음과 같다.

1. 작업 대상 프로젝트 확인
2. 사용자 요청 범위 확인
3. 금지사항 확인
4. 관련 기준 문서 확인
5. 현재 파일 상태 확인
6. 필요한 경우 새 파일 생성 또는 기존 파일 수정
7. 테스트 또는 문서 검증 수행
8. 변경 파일 목록 확인
9. 결과 보고

문서 작업에서는 코드 테스트를 실행하지 않는다.

구현 작업에서는 관련 테스트를 가능한 범위에서 실행한다.

## 6. Git/GitHub 운영 규칙

Git 작업은 사용자가 명시적으로 요청한 경우에만 수행한다.

금지되는 기본 행동은 다음과 같다.

- 임의 commit 금지
- 임의 push 금지
- 임의 pull 금지
- 임의 branch 변경 금지
- 임의 reset 금지
- 임의 checkout 금지
- 임의 merge 금지
- 임의 rebase 금지

Git 작업이 필요한 경우 먼저 목적, 대상 branch, 포함 파일, 예상 결과를 확인한다.

## 7. GitHub를 Source of Truth로 사용하는 원칙

GitHub는 코드와 공식 변경 이력의 최종 Source of Truth이다.

운영 원칙은 다음과 같다.

- 로컬 작업 결과는 GitHub에 반영되기 전까지 임시 상태이다.
- 공식 구현 상태는 GitHub branch와 commit 기준으로 판단한다.
- 문서상 완료와 코드상 완료는 구분한다.
- Codex 보고는 로컬 작업 결과이며, GitHub 반영 여부를 별도로 명시한다.
- GitHub에 올라가지 않은 변경은 다음 작업자가 모를 수 있으므로 보고서에 남긴다.

docs 프로젝트의 Canonical 문서는 정책과 작업 기준의 Source of Truth이다.

kiwoom_auto 프로젝트의 GitHub 저장소는 실제 코드의 Source of Truth이다.

## 8. 새 대화 시작 절차

새 대화를 시작할 때는 다음 순서를 따른다.

1. 현재 작업 대상 프로젝트를 명시한다.
2. 기준 문서 또는 최신 Canonical 파일을 지정한다.
3. 최근 작업재개요약 또는 UPDATE 문서를 제공한다.
4. 이번 작업이 문서 작업인지 구현 작업인지 명시한다.
5. 금지사항을 명시한다.
6. 기대 산출물을 명시한다.
7. 테스트 또는 검증 범위를 명시한다.

새 대화에서 이전 맥락을 추정하지 않는다.

필요한 기준 문서는 명시적으로 제공하거나 파일 위치를 알려준다.

## 9. Codex 보고 형식

Codex 보고는 간결하고 검증 가능해야 한다.

기본 보고 형식은 다음과 같다.

- 수행한 작업
- 변경 파일 목록
- 변경 위치
- 실행한 검증
- 테스트 결과
- 수정하지 않은 항목
- 남은 위험 또는 누락 가능성

문서 작업 보고에는 생성 파일 경로와 포함 목차를 기록한다.

구현 작업 보고에는 변경 전후 동작과 테스트 결과를 기록한다.

## 10. ChatGPT 보고 형식

ChatGPT 보고는 판단과 작업 지시 중심으로 작성한다.

기본 보고 형식은 다음과 같다.

- 현재 상태 요약
- 완료된 범위
- 남은 작업
- Codex에게 넘길 작업 지시
- 금지사항
- 다음 대화 시작용 요약

ChatGPT 보고는 구현 완료를 과장하지 않는다.

구현되지 않은 내용은 예정, 후보, 정책, 설계로 구분해 쓴다.

## 11. Preview -> Approval -> Policy -> Commit -> Review -> Execution -> SendOrder 원칙

프로젝트 작업은 다음 흐름을 기본 원칙으로 삼는다.

```text
Preview
-> Approval
-> Policy
-> Commit
-> Review
-> Execution
-> SendOrder
```

각 단계의 의미는 다음과 같다.

- Preview: 실제 변경 없이 후보와 결과를 미리 계산한다.
- Approval: 사용자의 승인 또는 정책 승인 상태를 확인한다.
- Policy: 운영 정책, 안전 조건, 금지선을 적용한다.
- Commit: 명시된 대상에 실제 변경을 수행한다.
- Review: Commit 결과와 후속 상태를 검토한다.
- Execution: 실행 계층으로 넘긴다.
- SendOrder: 실제 주문 호출 계층이다.

Preview, Approval, Policy, Review 단계는 기본적으로 write를 수행하지 않는다.

Commit 단계만 명시된 조건에서 write를 수행할 수 있다.

Execution과 SendOrder는 가장 위험한 계층이므로 별도 정책과 검증이 필요하다.

## 12. 수정 금지 규칙

다음 작업은 명시 요청 없이는 수행하지 않는다.

- Python 코드 수정
- runtime 파일 수정
- rules.json 수정
- Git 작업
- 압축파일 생성
- 기존 Canonical 파일 덮어쓰기
- 기존 문서 임의 삭제
- 기존 문서 임의 축약
- 프로젝트 간 파일 임의 이동
- GUI 자동 연결
- SendOrder 연결

문서 작업 요청에서는 문서 파일만 생성 또는 수정한다.

구현 작업 요청에서는 지정된 코드 범위만 수정한다.

## 13. 테스트 규칙

테스트는 작업 유형에 따라 다르게 적용한다.

문서 작업:

- 문서 생성 여부 확인
- 파일 경로 확인
- 필수 목차 포함 여부 확인
- 기존 코드와 runtime 미수정 확인

구현 작업:

- 관련 파일 py_compile
- 관련 단위 테스트
- 가능한 경우 전체 unittest 또는 pytest
- runtime/rules.json 변경 여부 확인
- 금지된 파일 변경 여부 확인

테스트를 실행하지 못한 경우 이유를 보고한다.

## 14. MASTER_SPEC와 본 문서의 역할 차이

MASTER_SPEC는 프로젝트 기능, 정책, 구조, 구현 기준을 정의하는 Canonical 문서이다.

본 문서는 AI 협업 및 운영 절차를 정의하는 운영 지침 문서이다.

구분은 다음과 같다.

- MASTER_SPEC: 무엇을 만들고 어떻게 동작해야 하는가
- 본 문서: 누가 어떤 순서로 작업하고 어떻게 보고해야 하는가

본 문서는 MASTER_SPEC의 구현 내용을 반복하지 않는다.

MASTER_SPEC가 변경되더라도 운영 절차는 본 문서 기준으로 관리한다.

## 15. 향후 운영 규칙 확장 방법

운영 규칙을 확장할 때는 다음 원칙을 따른다.

1. 기존 문서를 임의 덮어쓰지 않는다.
2. 새 버전 파일을 만든다.
3. 변경 이유를 기록한다.
4. 변경된 절차와 금지사항을 명확히 쓴다.
5. MASTER_SPEC와 충돌하는지 확인한다.
6. docs 프로젝트와 kiwoom_auto 프로젝트의 역할 분리를 유지한다.
7. GitHub Source of Truth 원칙을 유지한다.

새 버전 예시는 다음과 같다.

```text
AI_PROJECT_OPERATION_MANUAL_v1.1.md
AI_PROJECT_OPERATION_MANUAL_v1.2.md
```

운영 규칙 변경은 구현 변경이 아니다.

운영 규칙 변경만으로 Python 코드, runtime, rules.json을 수정하지 않는다.
