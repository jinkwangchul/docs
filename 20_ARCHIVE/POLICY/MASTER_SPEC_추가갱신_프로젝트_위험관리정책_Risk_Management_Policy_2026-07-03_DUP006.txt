MASTER_SPEC_추가갱신_프로젝트_위험관리정책_Risk_Management_Policy_2026-07-03

목적
- 프로젝트 전반의 기술적·운영상 위험을 식별하고 대응 원칙을 정의한다.

1. 위험 분류
① 아키텍처 위험
② Runtime 데이터 위험
③ 상태 전이 위험
④ 실주문 위험
⑤ 복구 위험
⑥ 운영자 실수 위험

2. 주요 위험과 대응

[실주문 위험]
- 원인: 잘못된 SendOrder 연결
- 대응:
  - Preview 우선
  - Final Execution Guard
  - execution_enabled 기본 false
  - operator_confirmed 기본 false

[Runtime 위험]
- 원인: JSON 손상, 직접 수정
- 대응:
  - Runtime 규격 준수
  - Recovery 검증
  - Audit 추적

[상태 전이 위험]
- 원인: State Machine 우회
- 대응:
  - Controller만 상태 변경
  - 허용 전이만 사용

[복구 위험]
- 원인: 재시작 후 불일치
- 대응:
  - Recovery Controller
  - Review Management
  - 서버 검증 우선

3. 위험 우선순위
Critical
- 잘못된 실주문
- Position 불일치

High
- Runtime 손상
- 중복 주문

Medium
- Audit 누락
- Preview 오류

Low
- UI 표시 오류
- 로그 형식 오류

4. 대응 원칙
- 자동 처리보다 안전한 차단을 우선한다.
- 불확실한 상태는 Review 대상으로 보낸다.
- 위험을 숨기지 않고 기록한다.

5. 검증
모든 구조 변경은 다음을 확인한다.
□ 위험 증가 여부
□ Recovery 가능 여부
□ Runtime 영향
□ 회귀 테스트
□ 문서 갱신

최종 원칙
프로젝트는 기능 추가보다 위험 감소를 우선한다.
