5. Target band and condition
----------------------------

For user ratio n and stable reference R:

  U = R * (1 + n / 100)
  L = R * (1 - n / 100)

UP uses U. DOWN uses L. BOTH is the range [L, U], not a directional synonym.

- UP + >=: final average >= U
- UP + <=: final average <= U
- DOWN + >=: final average >= L
- DOWN + <=: final average <= L
- BOTH + WITHIN: L <= final average <= U
- BOTH + OUTSIDE: final average < L or final average > U

OUTSIDE uses a strict boundary.

6. Required quantity
--------------------

For current Q, current average A, actionable price P, and selected target T:

  x = Q * (A - T) / (T - P)

The policy converts the continuous solution to a whole-share candidate, then
checks the projected final average and finds the minimum integer quantity that
actually satisfies the selected comparator. A simple ceil without the final
condition check is not authoritative; strict OUTSIDE and floating-point edge
cases are explicitly rechecked.

Regression examples:

- Q=3, A=50,000, P=13,000, T=13,130 -> required quantity 851.
- Q=3, A=50,000, P=13,000, T=14,900 -> required quantity 56.

The numbers 851 and 56 are regression examples, not Production constants or
limits.

7. Calculation result states
----------------------------

READY:
The minimum additional whole-share quantity can be calculated and the projected
average satisfies the selected condition.

NO_BUY:
The current average already satisfies the target. No new order is needed. This
is not an error, does not advance a round, and does not require Review.

WAIT:
The condition cannot be reached with the current actionable P, or there is no
valid integer solution at that price. No order is created, no round advances,
and Review is not required solely for this outcome.

INVALID:
An authority or policy input is malformed or inconsistent. Processing fails
closed.

8. Lifecycle and generation integrity
--------------------------------------

An approved quantity is never edited in place immediately before dispatch.
When P, Q, or A changes and the required quantity changes, the old undispatched
generation is ended with BLOCKED / ACTIVE_BUY_PLAN_SUPERSEDED. A new
plan_generation is then built from the latest Q/A/R/P and returns through the
normal Candidate, Approval, Operation Policy, and execution pipeline. Approval
identity and hashes are not bypassed.

Pre-dispatch:

- If the required quantity is unchanged, the approved generation remains.
- If it changes, the old undispatched generation is superseded and generation
  + 1 is proposed through the normal approval path.
- NO_BUY or WAIT supersedes stale undispatched work without creating a new
  generation.

Broker-open order:

- ACTIVE_BUY does not cancel a broker-accepted order merely because price P
  changed. Generic unfilled price-change behavior belongs to Situation Response.
- If open remaining is greater than the newly required quantity, the excess
  creates overbuy risk: request cancel, wait for confirmed cancel effect,
  re-read Position, and replan only if still required.
- If open remaining is less than or equal to the newly required quantity, keep
  the unresolved obligation and wait. Do not dispatch a duplicate generation.

Partial fill:

- Confirmed Fill updates canonical Position.
- The lifecycle then re-reads Q and A, obtains a fresh actionable P, and runs
  the same minimum-quantity calculation.
- Old quantities are not reused.

Early target satisfaction:

- Stop creating new ACTIVE_BUY orders.
- Supersede undispatched children.
- Cancel any broker-open remainder through existing cancel authority.
- Wait for cancel-effect confirmation.
- Do not create another generation.

The above cancel is ACTIVE_BUY execution reconciliation. It is not the reserved
Situation Response CANCEL_BATCH user policy.

SEND_UNCERTAIN and reconciliation uncertainty:

- Blind retry: 0.
- Blind supersede: 0.
- New generation: 0.
- Wait for existing manual/broker reconciliation authority.

13. Ten-second operation timer is not signal cadence
-----------------------------------------------------

AutoTradeOperationHost owns a QTimer with a 10,000 ms interval. That timer keeps
durable operation lifecycle, state re-evaluation, pending-pipeline, and related
coordinators moving. It does not mean that BUY/SELL indicators are calculated
every ten seconds. New market-bar signal evaluation is triggered by the verified
canonical BAR_COMMITTED event.

  operation timer cadence != signal candle cadence

14. Meaning of a completed one-minute canonical bar
----------------------------------------------------

A one-minute bar is not authoritative merely because the wall clock crossed a
minute boundary. Production requires realtime ticks to complete the interval's
OHLCV, a canonical candle commit, commit/read-back and changed confirmation,
and a BAR_COMMITTED event. Only then is the bar sent toward operation evaluation.
The still-forming one-minute bar is not used directly as Production signal
authority, preventing transient pre-close conditions from being mistaken for a
durable decision.

15. Trigger timeframe versus Routine evaluation timeframe
----------------------------------------------------------

The market-data trigger is a completed one-minute canonical commit. The Routine
does not therefore always evaluate a one-minute candle set. In
routine_signal_probe, completed_timeframe_candles(raw_candles, instance_rules,
now=...) projects the canonical minute data into the completed timeframe chosen
by the Routine instance, such as three or five minutes, before evaluate(context)
is called.

  trigger = completed canonical one-minute commit
  evaluation input = completed configured-timeframe projection

No additional timing semantics are inferred by this checkpoint.
