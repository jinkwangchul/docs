FIRST PRINCIPLE
==================================================
Do not arbitrarily modify, delete, refactor, clean up, rename, restructure,
add implementation, change dependencies, or alter contracts outside the
explicitly authorized target.

EXISTING FUNCTIONALITY / BEHAVIOR IS A PROTECTED BASELINE.

Unless the user's latest explicit instruction specifically authorizes that exact change,
NEVER cause loss, disablement, omission, substitution, semantic drift, or behavioral
change of any existing function, feature, UI behavior, interaction, calculation,
indicator, signal, marker, period-selection behavior, data flow, persistence behavior,
runtime state transition, market/session contract, refresh behavior, order route, safety
gate, test-backed contract, or previously user-approved behavior.

This prohibition applies even inside an otherwise approved implementation scope.
"Performance optimization", "refactor", "cleanup", "restoration", "simplification",
"temporary workaround", "consistency fix", "migration", or "technical debt reduction"
is NEVER authority to remove, bypass, delay, weaken, replace, or reinterpret existing
functionality.

A restoration task is also not authority to overwrite or discard newer valid behavior.
When historical restoration and current valid behavior overlap, preserve both unless the
user explicitly chooses otherwise.

Before any mutation that can touch an existing behavior:
1. Identify the affected existing functions/contracts/observable behavior.
2. Establish the pre-change baseline from code, tests, runtime evidence, Canonical,
   restore points, Git history, or user-confirmed behavior as appropriate.
3. Design the change so the approved target changes while unrelated behavior remains
   semantically identical.
4. Add or run parity/regression tests for the protected behavior.
5. After implementation, independently verify that the protected behavior is unchanged.

For optimization/performance work, completion requires BOTH:
FUNCTIONAL_PARITY_PASS
PERFORMANCE_IMPROVED

Performance work may remove duplicated work or reduce implementation cost, but it must
not achieve speed by dropping updates, changing user-visible semantics, weakening
freshness, changing timing/cadence contracts, skipping calculations, reducing data,
coalescing/dropping events, or otherwise changing behavior unless that exact behavioral
change was explicitly approved by the user.

If functional parity cannot be proven, if a performance gain requires a behavioral
trade-off, or if existing behavior conflicts with the proposed implementation:
STOP -> USER_DECISION_REQUIRED.
Do not choose the trade-off on the user's behalf.

If a new contract, structural decision, scope expansion, or document conflict appears:
investigate -> establish evidence -> report -> obtain user decision.

Do not write code for the sake of code.
Do not destroy or normalize another conversation's dirty/untracked WIP.

IMPLEMENTATION-FIRST / SCOPE DISCIPLINE — USER DECISION 2026-10-20
==================================================
기능구현작업중심으로 프로젝트 진행하며 검증은 필수요소위주로 하며 원래 구현하려던 작업을 벗어나서 확장하지 않는다.

1. 승인된 기능의 실제 구현과 정상 동작 확보를 최우선 결과로 삼는다.
   조사·분석·설계는 구현에 필요한 범위에 한정하고, 조사만 반복하거나
   추가 진단·문서·보조도구 개발로 본래 구현을 대체하지 않는다.
2. 검증은 필수 요소(기존 기능 보존, 계산·데이터 정합성, 변경 지점의
   회귀, 복원 가능성, 실주문 차단 등)에 집중한다. 불필요한 전수검증,
   중복 검증, 증거 수집의 무한 반복을 지양한다. 필수 검증 생략이나
   근거 없는 PASS·완료 선언은 허용하지 않는다.
3. 구현 중 새로운 개선점·결함·연구 과제가 발견되어도 승인된 목적
   밖으로 작업을 자동 확장하지 않는다. 관련 위험이 치명적이지 않다면
   후속 과제로 기록하고 원래 구현으로 복귀한다. 목표·계약·범위의
   변경이 필요하면 먼저 사용자 결정을 받는다.
4. 작업은 지나치게 짧은 단위로 끊지 않고 원래 승인된 기능 목표별로
   구현 → 필수 테스트 → 정정 → 복원점 → 결과 보고를 묶어 진행한다.
   제1·제2원칙, Broker 안전, 단일 Mutation Owner, 승인 Gate는 유지한다.
