# AGENT_WORKFLOW_REFERENCE

Document role:
- This file is the single Source of Truth for AI operating rules.
- All AI agents working on this project must follow this file before README, session protocols, older operation manuals, Work Resume notes, or historical Canonical text.
- Other documents provide project contracts, indexes, evidence, or recovery context. They do not define AI operating procedure unless this file explicitly delegates that role.

## 1. Authority And Interpretation

Priority order:

1. Latest explicit user instruction
2. `00_CANONICAL/REFERENCE/AGENT_WORKFLOW_REFERENCE.txt`
3. Latest Official Canonical for technical project contracts
4. Latest Work Resume for recovery context
5. Actual local code, Runtime files, logs, and execution evidence
6. Reference Index as a document index only
7. Historical and archived files only as evidence

Rules:
- Latest explicit user instruction always overrides this file.
- The user owns project concepts, rules, policies, states, terms, UI contracts, data contracts, and structure contracts.
- AI has no authority to create, change, replace, expand, shrink, reinterpret, or delete project contracts without explicit user approval.
- AI reasoning is only a tool for finding evidence. It is not implementation authority.
- If implementation and contract conflict, fix the implementation. Do not rewrite the contract to fit AI interpretation.
- User-unapproved contract change is project contamination.

## 2. Work Purpose

The project goal is working automatic trading software, not document growth, structure growth, or Git activity.

Every task starts with one fixed problem statement or Big Feature Goal.

Default work flow:

1. Define the actual problem
2. Trace the real call path
3. Confirm the actual stop point
4. Make the smallest necessary change
5. Verify through execution, tests, Runtime evidence, or logs
6. Report only the result and remaining real stop points

Do not change the problem during the task. New findings are reported separately unless the user explicitly expands scope.

## 3. Implementation First

Implementation First means actual user-facing project behavior has priority over process work.

Default priority:

1. Real problem resolution
2. Cause confirmation
3. Minimal implementation
4. Verification
5. Local version management
6. Documentation only when requested or at Project Freeze

Forbidden during implementation unless explicitly requested:
- Long repeated structure audits
- Middle-of-work Canonical, Changelog, or Work Resume creation
- Expanding the task into future design
- Treating tests, files, helper functions, or state names as completed user features
- Ending at an internal pipeline stage when the requested user flow remains disconnected

## 4. Big Feature Goal

Work unit is a user-usable feature, not a function, file, helper, adapter, preview, validator, gate, wrapper, executor, or state transition.

A Big Feature is complete only when the user can use it in the actual production flow or when the exact remaining stop point is proven.

During a Big Feature:
- Do not repeatedly split work into smaller featurelets.
- Do not declare completion because one internal layer or test passes.
- Do not select the next feature before the current one reaches a usable state or a proven blocker.
- Small fixes discovered inside the same feature stay inside the same feature.

Completion report must explain the user-visible capability, actual flow, safety boundary, validation result, and remaining stop point if any.

## 5. Change Scope Rule

AI does not perform work outside the current task scope.

Without explicit user approval, do not perform:
- Refactoring
- Optimization
- Naming changes
- Structure changes
- Contract changes
- Test changes
- Documentation changes
- Git work
- Extra feature additions

If an improvement is discovered, report it as:

```text
Additional improvement candidate
- Target:
- Reason:
- Expected impact:
- Recommended separate task:
```

Do not include it in the current work.

## 6. Shared Foundation And Architecture Contamination

Default: no new shared foundation work.

Shared foundation review is allowed only when all are true:
- The current Big Feature cannot be completed with existing structure.
- The blocker is Source of Truth, Canonical Writer, Broker I/O, common storage, external event input, or shared Mutation Boundary.
- Solving it is necessary to avoid bypassing a safety boundary.
- The change can be made with minimal modification to existing structure.

Do not create new layers, writers, policies, previews, gates, adapters, services, wrappers, or executors for convenience, reuse speculation, cleanliness, or future extensibility.

Architecture contamination includes:
- AI-created concepts not approved by the user
- Repeated wrappers around existing responsibility
- Writer or Source of Truth dispersion
- Production call graph changes without contract authority
- Lifecycle owner changes without approval
- Treating unit-test count as production validity

When structural risk is present, report the blocker and minimal option before implementation.

## 7. Source Of Truth And Runtime Safety

Project technical contracts live in the latest Official Canonical. AI operating rules live only in this file.

Runtime safety rules:
- Do not write Runtime files unless the user requested a task that requires it and an existing writer/commit boundary is used.
- Do not directly mutate Queue, Fill, Position, Broker Holdings, locks, state, or rules files unless explicitly authorized.
- Do not create fake Runtime evidence.
- Do not manually create empty JSON to bypass initialization.
- Do not call Kiwoom SendOrder, Broker API, or real order APIs without explicit user approval.
- Do not treat preview, validation, dry-run, or dialog display as commit.
- Do not change Source of Truth or Writer ownership without user approval.

Real side effects must go through the existing canonical writer, service, or commit boundary.

## 8. Session Startup Policy

At the start of a new session, resume implementation from the latest Work Resume. Startup is not document review.

Startup triggers:
- New conversation
- Continuing previous work
- Resuming after a Git baseline change
- User asks to verify current baseline before work

Session Startup Source Resolution Policy:

Before reading project documents or source code, identify the active work environment.

- ChatGPT with GitHub connector: use the GitHub docs repository and GitHub code repository as the remote backup and restoration baseline.
- Local Codex / VSCode: use the local docs repository and local code repository as the working baseline.

Use the source that matches the active environment. Do not mix GitHub connector state and local repository state unless the user explicitly asks for a comparison.

Startup execution flow:

1. Read the Latest Work Resume only for the previous completion state and next implementation target.
2. Confirm the current Git Baseline (branch and commit). Report to the user only if it differs from the expected baseline.
3. If the next implementation scope is clear from the Work Resume, start implementation immediately.
4. If no explicit next implementation task exists in the Source of Truth, identify the earliest user-visible production gap in the current baseline, declare it as the next Big Feature implementation target, briefly report the rationale, and immediately begin implementation.

Reference rules:

5. Refer to the corresponding Latest Canonical section only when needed during implementation.
6. Use Reference Index only to locate a required document.
7. Re-read this file only when operating rules changed, a new operating rule must be applied, or the user asks.

Forbidden:
- Broad structure audit without need
- Re-reading AGENT, Reference Index, full Canonical, historical documents, or broad project structure by default
- Adding startup checks inferred from general development or Git practices
- Treating old Work Resume next steps as current user instruction
- Starting implementation before the fixed problem and allowed scope are known

Reference Index is only an index. It is not an operating policy document.
Follow only the operating procedures defined by this project. Documents support implementation; they must not become a repeated startup gate when the Latest Work Resume already provides the next implementation point.

## 9. Conversation Shutdown / Project Freeze Policy

Conversation Shutdown is Project Freeze, not casual summarization.

Shutdown triggers:
- User says the work is ending
- User says to move to the next conversation or next window
- User says "마감", "작업 종료", "오늘은 여기까지", "Freeze", or equivalent
- User asks to create a next-session baseline

Project Freeze is allowed even though Implementation First normally places documentation after implementation. Freeze work is operational baseline creation, not feature documentation.

Freeze includes, when requested or needed:
- Project state check
- Git status check
- Commit of completed project work
- Push to GitHub as backup and next-session recovery baseline
- New Latest Official Canonical for confirmed project contracts only
- New Latest Work Resume for recovery state
- New Latest Changelog for Canonical changes
- Reference Index update when latest document pointers change
- Final verification that local and remote baselines match

Big Feature Freeze must record:
- Current Big Feature Goal
- Current Big Feature progress
- Completion criteria
- Current blocker or next start point
- Why the next Big Feature must not be selected yet, if the current one is not complete

Freeze is complete only when the next AI can continue the same work from GitHub and the recorded documents without reading the previous conversation.

Freeze must not record ideas, unapproved plans, or discussed UI proposals as Canonical.

## 10. Conversation Closing Standard Procedure

Run this procedure only when the user explicitly says they are moving to the next conversation, opening a new window, closing the window, finishing, wrapping up, or equivalent.

Step 1. Codex Closing Prompt

Create a concrete closing prompt for Codex to finish the current work.

The Codex Closing Prompt must include:

1. Source of Truth document update:
   - Latest Canonical when needed
   - AGENT_WORKFLOW_REFERENCE when needed
   - Reference documents when needed
   - Work Resume when needed
   - Changelog or other Canonical documents when needed
2. Verification:
   - Review changed content
   - Run `git diff --check`
   - Run any other required verification
3. Git work:
   - Commit
   - Push
   - Confirm latest GitHub state
4. Final report:
   - Updated Source of Truth document list
   - Commit SHA
   - Push result
   - Verification result
   - Next Session Startup Prompt

The Codex Closing Prompt must end by creating the Next Session Startup Prompt so the next session can start implementation immediately.

The final report should contain only the required result. Do not include unnecessary intermediate work logs.

Step 2. Next Session Startup Prompt

After the closing work is complete, create a concrete Next Session Startup Prompt for the next conversation.

The prompt must include:

1. Environment resolution:
   - ChatGPT with GitHub connector
   - Local Codex / VSCode
2. Source of Truth selection:
   - GitHub environment uses the GitHub repository.
   - Local environment uses the local repository.
   - Do not mix the two environments unless the user asks.
3. Startup procedure:
   - Do not use memory or the previous conversation as Source of Truth.
   - Check `00_CANONICAL/REFERENCE/AGENT_WORKFLOW_REFERENCE.txt`.
   - Check `00_CANONICAL/REFERENCE/00_REFERENCE_INDEX.md`.
   - Check the latest `MASTER_SPEC_CANONICAL`.
   - Check the latest `WORK_RESUME`.
   - Check required Reference documents only when the next task needs them.
4. Repository state:
   - Branch
   - Commit
   - Dirty or untracked state
   - Recently completed work
   - Current implementation location
5. Next implementation task:
   - Name one concrete implementation task to perform first in the next session.
   - The task must be specific enough to implement immediately.
   - If no explicit next implementation task exists in Source of Truth, use the earliest user-visible production gap in the current baseline as the next Big Feature implementation target.
   - Do not select a new feature or change scope without explicit user instruction.
   - Do not write the next action as an abstract area such as "continue Execution Layer" or "continue order system"; name the concrete task identifier.

Step 3. Handover Validation

Before closing the conversation, verify:
- The Next Session Startup Prompt alone is enough to resume work.
- The next task is specific enough to implement immediately.
- The prompt refers to the latest Source of Truth for the selected environment.
- No confirmed decision is missing from the applicable Source of Truth document.
- Required document updates are complete.
- GitHub backup is complete when GitHub backup was required.

## 11. Local Git And GitHub

Git is used for:
- Local version management
- Diff and history inspection
- File-level recovery after mistakes
- Final backup commit at stable points

GitHub is used for:
- Remote backup
- AI state restoration
- Project baseline verification
- Remote baseline verification after push
- Next-session recovery reference after the local baseline is pushed
- Collaboration history only when the user explicitly needs it

GitHub is not a development procedure and not a reason to add collaboration workflow.

Rules:
- Do not run Git operations unless requested or necessary for an approved Freeze/Git task.
- Do not use `git add .` or `git add -A`.
- Stage only specified files.
- Do not reset, restore, stash, clean, or delete protected dirty/untracked files unless the user explicitly asks.
- Report branch, local SHA, remote SHA, ahead/behind, status, diff, and untracked files when doing baseline verification.

## 12. Document Roles

Document hierarchy: AI operating rules -> AGENT_WORKFLOW_REFERENCE; technical contract -> Latest Canonical; recovery -> Latest Work Resume; change history -> Latest Changelog; navigation -> Reference Index; repository guide -> README; historical evidence -> 20_ARCHIVE.

Document roles:

- `AGENT_WORKFLOW_REFERENCE`: single AI operating rule source
- `00_REFERENCE_INDEX.md`: index to latest documents
- Canonical: project technical contract
- Work Resume: recovery and next-session context
- Changelog: Canonical change history
- README: repository guide
- Historical / Archive: evidence only

Rules:
- Do not modify old Canonical, old Changelog, or old Work Resume.
- New confirmed contract goes into a new Canonical.
- Canonical only records confirmed implementation or confirmed policy.
- Work Resume records recovery state, current baseline, next start point, and unresolved blockers.
- Changelog records what changed in a Canonical update.
- Intermediate documents are forbidden unless user explicitly asks.

## 13. Prompt Standard

Permanent operating rules are not repeated in every task prompt.

Task prompt should contain only:

1. Purpose
2. Target scope
3. Additional restrictions unique to this task
4. Verification
5. Report format

Default prompt length should stay small:
- Analysis: about 10-20 lines when possible
- Implementation: about 20-40 lines when possible
- Git or document task: about 10-20 lines when possible

Prompt checklist:
- Is this directly related to the current task?
- Does it avoid repeating this operating rule file?
- Does it avoid unrelated Git, test, document, or collaboration workflow instructions?
- Is the purpose one sentence?
- Is the report format not excessive?

## 14. Verification And Reporting

No conclusion without evidence.

Valid evidence:
- Code path
- Runtime value
- state file
- Queue file
- Log
- Test result
- GUI execution result
- Git status or diff for Git tasks

Every change or conclusion must distinguish evidence from inference.

Examples of evidence:
- Test result
- `py_compile` result
- `git status`
- Commit hash
- Runtime file content
- Log line
- Queue or state record

If evidence is missing, report "not confirmed".

Report order for bug/feature work:

1. Problem definition
2. Call chain
3. Actual stop point
4. Cause
5. Evidence
6. Change location
7. Change summary
8. Verification result
9. Remaining issue

Do not over-report file and function names before explaining actual user-facing behavior.

## 15. Prohibited Defaults

Unless explicitly requested, do not:
- Create new project concepts
- Create new statuses
- Create new UI contracts
- Create new Source of Truth
- Create new writer or mutation boundary
- Add hidden Runtime writes
- Connect real SendOrder
- Use Broker API
- Generate new Canonical, Changelog, or Work Resume during implementation
- Perform Git work
- Modify unrelated files
- Expand a bug task into architecture cleanup
- Turn analysis into implementation

## 16. Final Principle

The AI's job is to make the current real project work under the user's contracts.

When in doubt:

1. Preserve the contract
2. Trace the real execution path
3. Fix only the proven blocker
4. Verify with real evidence
5. Report the next real blocker
