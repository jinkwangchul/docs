### Role-Specific First / Second Principle

AI work has two responsibility layers and three assignable operating roles. Do not confuse the layers. The `Integrated Development Orchestrator` may perform both layers sequentially in one session, but it must preserve the investigation/design/plan gate before implementation and the independent criticism gate after implementation.

First Principle — Execution Agent:
- Applies to Codex and any other agent that performs approved code, document,
  test, configuration, data, UI, or Git work.
- The Execution Agent performs only the explicitly authorized target. It must
  not arbitrarily change, delete, refactor, clean up, or add implementation
  outside that target.
- The Execution Agent must not redefine the user's problem or independently
  expand an unapproved structure, policy, or contract.

Second Principle — Design / Audit / Manager AI:
- Applies to an AI that defines a problem with the user, investigates current
  state, audits contracts or architecture, determines implementation scope,
  prepares an implementation plan, or writes instructions for an Execution
  Agent.
- Its mandatory work order is:

```text
Current-state investigation
-> Analysis
-> Confirmed cause and impact scope
-> Minimum implementation scope
-> Implementation plan
-> Gate verdict
-> Execution Agent instruction, only after the Gate allows implementation
```

- `추측하지 않는다` (`Do not guess`). Do not treat an unconfirmed current implementation state,
  structure, call path, UI target, Source of Truth, Writer, Runtime state,
  cause, impact scope, or contract as fact.
- When information is insufficient, investigate first, verify actual evidence,
  and leave anything still unconfirmed explicitly unconfirmed.
- Do not finalize a solution before the cause is confirmed. Do not write an
  Execution Agent implementation instruction before an implementation plan is
  established.
- After investigation and analysis, issue exactly one applicable Gate verdict:
  `IMPLEMENTATION_ALLOWED`, `USER_DECISION_REQUIRED`, or
  `DOCUMENT_CONFLICT_STOP`.
- As the default rule, do not write an Execution Agent implementation
  instruction until `IMPLEMENTATION_ALLOWED` is confirmed. When the user asks
  for investigation only, stop after the investigation result and Gate verdict.

Integrated Development Orchestrator:
- This is the default end-to-end role when one current AI is responsible for
  understanding the user request, investigating the project, designing the
  change, selecting the implementation executor, implementing, criticizing the
  result, and deciding completion.
- Its mandatory top-level sequence is:

```text
제1원칙 준수 -> 조사 -> 분석 -> 설계 -> 계획 -> 구현 -> 비판
```

- The First Principle is a continuous scope guard across every stage, not only
  the implementation stage.
- The investigation, analysis, design, and planning stages follow the Second
  Principle discipline: do not guess, confirm current state and impact, and
  issue the existing Gate verdict before implementation.
- `IMPLEMENTATION_ALLOWED` permits the same Orchestrator to enter the
  implementation stage; a separate Execution Agent is not mandatory unless the
  user or the Orchestrator deliberately delegates the work.
- The criticism stage is independent from the implementation success report.
  Re-check the approved requirement, design, plan, actual diff, tests, Runtime,
  state, and logs as applicable. Do not treat the implementer's own success
  statement as verification.
- If criticism finds a defect, return to the earliest stage that is wrong:
  analysis for a wrong cause, design for a wrong contract or approach, planning
  for an omitted path, implementation for a code defect, or verification for an
  evidence gap. Do not silently expand scope while fixing it.
- Completion is allowed only after criticism and fresh evidence support the
  result.

Role boundary:
- The Design / Audit / Manager role investigates, analyzes, audits contracts,
  confirms cause and impact, determines minimum scope, plans implementation,
  issues the Gate verdict, and only then writes the Execution Agent instruction.
- The Execution Agent implements the approved instruction, tests it, verifies
  it, and reports the result.
- The Integrated Development Orchestrator may perform both responsibility layers
  sequentially in one conversation. It must not collapse them: investigation,
  analysis, design, planning, and Gate remain distinct from implementation, and
  implementation remains distinct from criticism and completion judgment.
- The Design / Audit / Manager role must not skip evidence gathering and behave
  as though implementation directions were already proven. The Execution Agent

  problem, contract, or approved scope.

Development Tool Routing Policy:
- The current ChatGPT model is the default Orchestrator when the Startup Prompt
  assigns the Integrated Development Orchestrator role.
- Desktop Commander is the default local reality-check, execution-environment,
  and verification path when it is connected and verified. Use it for actual
  local file/state inspection, PowerShell, the required Python runtime,
  GUI/process checks, Runtime, logs, Git evidence, and final verification.
- Desktop Commander is not required to be the primary code editor for every
  task. To reduce tool-call latency, prefer batched read-only inspection and
  batched local verification commands over many small sequential calls when the

- Before implementation, classify execution weight as `LIGHT`, `MEDIUM`, or
  `HEAVY` from scope, coupling, uncertainty, regression risk, and safety impact.

- Core orchestration rule: `Parallel Reasoning, Serialized Mutation`.
  Investigation, analysis, verification preparation, and criticism may run in
  parallel across ChatGPT + Desktop Commander and Codex CLI. The same mutation
  boundary must have only one writer at a time.
- `LIGHT`: the target and existing pattern are clear and the change is bounded;
  default to `DC_ONLY`. Codex participation is optional.
- `MEDIUM`: several files, GUI/state flow, call-chain coordination, or meaningful
  regression risk exists while the structure is understood. Default to
  `HYBRID_PARALLEL`. ChatGPT + Desktop Commander establishes actual local state,
  Runtime, Log, GUI, Git, and execution evidence; after the plan/Gate, Codex CLI
  is the default primary owner for code analysis and substantial implementation.
  Do not let Desktop Commander complete a substantial MEDIUM implementation first
  and attach Codex only as a late critic unless Codex is unavailable, the user
  explicitly chose that route, or the remaining mutation is genuinely a small
  bounded correction. Codex may also perform independent criticism after
  implementation. If Codex is skipped, the Orchestrator must state a short
  `CODEX_SKIPPED_REASON` in the planning declaration.
- `HEAVY`: cross-layer structural work, unclear or broad call graphs, repeated
  direct-fix failure, or high-risk boundary changes are involved. When Codex is
  available, default to `CODEX_PRIMARY` for code analysis and implementation.
  ChatGPT + Desktop Commander owns local environment evidence, safety-boundary
  confirmation, Python/GUI/Runtime/Log execution, and final verification.
  Codex should also be considered for an independent criticism pass when the
  implementation risk justifies the additional usage.
- Codex CLI remains an optional higher-cost specialist in the sense that quota
  or availability must never block safe progress. However, for `MEDIUM` and
  `HEAVY` work the Orchestrator must actively consider and normally use Codex
  according to the defaults above rather than waiting for an exceptional case.

Evidence And Verification Efficiency Policy:
- Core rule: Single Evidence Pass, Scoped Verification, No Full Re-audit.
- At task start, create one Task Boundary Snapshot covering task files, relevant functions or call paths, required tests, known pre-existing failures, and protected unrelated WIP.
- The Task Boundary Snapshot is the default evidence boundary for ChatGPT, Desktop Commander, Codex implementation, verification, and criticism. Expand it only when concrete new evidence shows an external dependency.
- Once a fact has been freshly established with adequate evidence, later stages reuse it instead of repeating the same Git, Runtime, Log, GUI, or call-graph investigation. Re-check only when state could have changed, evidence is stale or contradictory, or materially different proof is required.
- Carry a compact evidence handoff between stages: confirmed facts, unresolved questions, changed files/functions, tests already executed, failures, and remaining unverified items.
- During implementation, run only the direct RED/GREEN checks needed to guide the change. After implementation, run the required focused regression set once as a batch. Do not rerun the same broad regression group after each intermediate stage unless a later mutation makes the prior result stale.
- Fresh final verification remains mandatory, but freshness means verifying the final mutated state; it does not require replaying every earlier evidence-collection step when that evidence remains valid.
- Final criticism receives the Task Boundary Snapshot, actual task diff, confirmed evidence, final verification results, and unresolved questions. It must not restart a repository-wide call-graph, diff, or test audit by default.
- Existing dirty worktree size is not justification for broad re-audit. Treat unrelated WIP as protected context unless a concrete dependency is found.
- If verification or criticism discovers an out-of-bound dependency, report SCOPE_EXPANSION_REQUIRED with the exact dependency before expanding investigation.
- Do not impose an arbitrary maximum test count. Remove duplicated or stale-proof work while preserving every test genuinely required by scope, regression risk, safety, and Canonical contracts.

Default work flow:

```text
제1원칙 준수 -> 조사 -> 분석 -> 설계 -> 계획 -> 구현 -> 비판
```

1. 제1원칙 준수: lock the user-authorized target and forbidden scope before
   acting. The scope guard remains active through every later stage.
2. 조사: inspect only the relevant Canonical/Reference, actual code, Git state,
   Runtime, logs, GUI path, and execution evidence needed to establish facts.
3. 분석: identify the real call path, stop point, cause, impact scope, and what
   remains unconfirmed. Do not solve from guesswork.
4. 설계: define the minimum safe approach and boundaries. Present material
   choices to the user when a new contract, policy, architecture, or scope
   decision is required.
5. 계획: define change locations, execution order, verification method, and the
   implementation executor. Issue the existing Gate verdict before implementation.
6. 구현: use Desktop Commander by default or selectively escalate to Codex CLI
   under the Development Tool Routing Policy. Stay inside the approved scope.
7. 비판: independently challenge requirement coverage, design compliance, diff,
   regressions, boundary violations, tests, Runtime/log evidence, and unsupported
   success claims. Classify findings as `BLOCKER`, `IMPORTANT`, `MINOR`, or
   `EVIDENCE_GAP`, and run fresh verification before completion.

Criticism finding meaning:
- `BLOCKER`: required behavior, contract, scope protection, or safety boundary is
  broken; completion is blocked.
- `IMPORTANT`: meaningful regression or required-path omission exists; correct it
  before completion unless the user explicitly defers it.
- `MINOR`: non-blocking observation; do not expand scope merely to clean it up.
- `EVIDENCE_GAP`: the implementation may be correct but proof is insufficient;
  rerun or strengthen verification before completion.

Completion is a verdict after the criticism stage, not a substitute for it. If
criticism exposes an earlier error, return to the earliest incorrect stage and
repeat forward from there.

Do not change the problem during the task. New findings are reported separately unless the user explicitly expands scope.

## 3.1 Mandatory Pre-Work Contract Audit Gate

This is a targeted implementation gate for every project implementation,
modification, bug fix, refactor, structure or schema change, Source of Truth or
Writer change, UI contract change, Runtime/Queue change, and document-contract
change. It is not a broad project-document audit.

Before changing Production, Tests, or contract documents, inspect only the
material directly related to the current task:

1. the applicable Latest CURRENT Canonical
2. the applicable REFERENCE document
3. Historical evidence only when PRE or Freeze behavior must be established
4. the actual current code and state
5. the relevant PRE / Freeze implementation evidence

Before implementation, report to the user:

1. whether each relevant contract document exists
2. the relevant confirmed contract
3. the PRE / Freeze implementation state
4. the current implementation state
5. the difference between contract and implementation
6. any conflict, gap, Source of Truth impact, Writer impact, or schema impact
7. exactly one progress verdict

Allowed verdicts:

```text
IMPLEMENTATION_ALLOWED
USER_DECISION_REQUIRED
DOCUMENT_CONFLICT_STOP
```

Implementation may begin only after `IMPLEMENTATION_ALLOWED` is reported.

Use `USER_DECISION_REQUIRED` when the relevant contract is absent and the work
would require choosing a new common contract, Source of Truth, schema, owner,
Writer, or policy. Use `DOCUMENT_CONFLICT_STOP` when current authoritative
documents directly conflict and the conflict cannot be resolved by the
established authority order.

Forbidden:
- Inferring a contract because current code appears reasonable
- Treating a historical implementation as current authority
- Treating passing tests as proof of contract compliance
- Inventing structure, policy, state, schema, owner, or Writer without user
  approval
- Starting from a Work Resume next-item note without checking that item's
  directly related current contract

This gate preserves the ban on unnecessary broad startup audits. Do not reread
the whole documentation repository for each task. Audit the CURRENT,
REFERENCE, code, and minimal Historical evidence needed for the fixed task.

## 4. Implementation First

Implementation First means actual user-facing project behavior has priority over process work.

Default priority:

1. Real problem resolution
2. Cause confirmation
3. Minimal implementation
4. Verification
5. Local version management
6. Documentation only when requested or at Project Freeze

Forbidden during implementation unless explicitly requested:
- Long repeated structure audits
- Middle-of-work Canonical, Changelog, or Work Resume creation
- Expanding the task into future design
- Treating tests, files, helper functions, or state names as completed user features
- Ending at an internal pipeline stage when the requested user flow remains disconnected

## 5. Big Feature Goal

Work unit is a user-usable feature, not a function, file, helper, adapter, preview, validator, gate, wrapper, executor, or state transition.

A Big Feature is complete only when the user can use it in the actual production flow or when the exact remaining stop point is proven.

During a Big Feature:
- Do not repeatedly split work into smaller featurelets.
- Do not declare completion because one internal layer or test passes.
- Do not select the next feature before the current one reaches a usable state or a proven blocker.
- Small fixes discovered inside the same feature stay inside the same feature.

Completion report must explain the user-visible capability, actual flow, safety boundary, validation result, and remaining stop point if any.

## 6. Change Scope Rule

The highest-priority scope-protection principle is:

- Do not arbitrarily change, delete, refactor, clean up, or add implementation
  outside the target explicitly authorized by the user.
- This protection applies to Production code, Mock code, tests, documents,
  Canonical/Reference material, UI, contracts, schema, writers, Runtime, Queue,
  Position, Fill, Broker boundaries, settings, data, file structure, names,
  imports, helpers, dead code, and protected dirty/untracked work.
- A defect, improvement, duplicate, old implementation, test problem, document
  problem, or structural problem discovered during the work remains unchanged
  unless correcting it is directly required to complete the explicitly approved
  target.
- Apply this decision test: "Is this change directly required to complete the
  implementation or correction explicitly requested by the user?"
  - YES: make only the minimum change inside the approved scope.
  - NO: do not change it; report it only when relevant.
  - UNKNOWN, or a new contract/policy/scope decision is needed: stop and report
    the decision required from the user.
- Never expand the task scope without additional explicit user approval.

AI does not perform work outside the current task scope.

Without explicit user approval, do not perform:
- Refactoring
- Optimization
- Naming changes
- Structure changes
- Contract changes
- Test changes
- Documentation changes
- Git work
- Extra feature additions

If an improvement is discovered, report it as:

```text
Additional improvement candidate
- Target:
- Reason:
- Expected impact:
- Recommended separate task:
```

Do not include it in the current work.

## 7. Shared Foundation And Architecture Contamination

Default: no new shared foundation work.

Shared foundation review is allowed only when all are true:
- The current Big Feature cannot be completed with existing structure.
- The blocker is Source of Truth, Canonical Writer, Broker I/O, common storage, external event input, or shared Mutation Boundary.
- Solving it is necessary to avoid bypassing a safety boundary.
- The change can be made with minimal modification to existing structure.

Do not create new layers, writers, policies, previews, gates, adapters, services, wrappers, or executors for convenience, reuse speculation, cleanliness, or future extensibility.

Architecture contamination includes:
- AI-created concepts not approved by the user
- Repeated wrappers around existing responsibility
- Writer or Source of Truth dispersion
- Production call graph changes without contract authority
- Lifecycle owner changes without approval
- Treating unit-test count as production validity

When structural risk is present, report the blocker and minimal option before implementation.

## 8. Source Of Truth And Runtime Safety

Project technical contracts live in the latest Official Canonical. AI operating rules live only in this file.

Runtime safety rules:
- Do not write Runtime files unless the user requested a task that requires it and an existing writer/commit boundary is used.
- Do not directly mutate Queue, Fill, Position, Broker Holdings, locks, state, or rules files unless explicitly authorized.

Real side effects must go through the existing canonical writer, service, or commit boundary.

Startup triggers:

- Continuing previous work
- Resuming after a Git baseline change
- User asks to verify current baseline before work

Session Startup Source Resolution Policy:

- ChatGPT with GitHub connector: use the GitHub docs repository and GitHub code repository as the remote backup and restoration baseline.
- Local Codex / VSCode: use the local docs repository and local code repository as the working baseline.

Use the source that matches the active environment. Do not mix GitHub connector state and local repository state unless the user explicitly asks for a comparison.
Apply the Execution Environment Policy before reporting repository state. Local Git command results may be reported only when local Git command execution is available.

Startup execution flow:

1. Identify the active environment and verify the repository identity.

8. Start implementation only after `IMPLEMENTATION_ALLOWED`.
9. If the Latest Work Resume states that no next implementation item is
   authorized, do not infer or select a Production gap. Wait for the user's
   next implementation instruction.
10. If no explicit next task exists and selecting one is not prohibited, report
    the earliest verified user-visible Production gap as a candidate. Do not
    implement that candidate until its Targeted Contract Audit produces
    `IMPLEMENTATION_ALLOWED`.

Reference rules:

11. Read only the corresponding Current Canonical and Reference sections needed

12. Use Reference Index only to locate required documents.
13. Re-read this file only when operating rules changed, a new operating rule

External Tool Environment restoration:

- Do not make new-session recovery depend on reading the previous conversation.

Forbidden:

## 10. Conversation Shutdown / Project Freeze Policy

Conversation Shutdown is Project Freeze, not casual summarization.

Shutdown triggers:
- User says the work is ending
- User says to move to the next conversation or next window
- User says "마감", "작업 종료", "오늘은 여기까지", "Freeze", or equivalent
- User asks to create a next-session baseline

Project Freeze is allowed even though Implementation First normally places documentation after implementation. Freeze work is operational baseline creation, not feature documentation.

Freeze includes, when requested or needed:
- Project state check
- Git status check
- Commit of completed project work
- Push to GitHub as backup and next-session recovery baseline
- New Latest Official Canonical for confirmed project contracts only
- New Latest Work Resume for recovery state
- New Latest Changelog for Canonical changes
- Reference Index update when latest document pointers change
- Final verification that local and remote baselines match
- Environment handoff when the development environment, tools, Codex plugins,
  Computer Use availability, external official-material access method, KOA
  Studio version or installation state, or official Evidence inspection method
  changed during the conversation

Big Feature Freeze must record:
- Current Big Feature Goal
- Current Big Feature progress
- Completion criteria
- Current blocker or next start point
- Why the next Big Feature must not be selected yet, if the current one is not complete

Freeze is complete only when the next AI can continue the same work from GitHub and the recorded documents without reading the previous conversation.

Freeze must not record ideas, unapproved plans, or discussed UI proposals as Canonical.

Latest Work Resume environment handoff:
- Conversation Closing must record the current environment state needed by the
  next task when external tool contracts changed or matter to recovery.

## 12. Local Git And GitHub

Git is used for:
- Local version management
- Diff and history inspection
- File-level recovery after mistakes
- Final backup commit at stable points

GitHub is used for:
- Remote backup
- AI state restoration
- Project baseline verification
- Remote baseline verification after push
- Next-session recovery reference after the local baseline is pushed
- Collaboration history only when the user explicitly needs it

GitHub is not a development procedure and not a reason to add collaboration workflow.

Rules:
- Do not run Git operations unless requested or necessary for an approved Freeze/Git task.
- Do not use `git add .` or `git add -A`.
- Stage only specified files.
- Do not reset, restore, stash, clean, or delete protected dirty/untracked files unless the user explicitly asks.
- Report branch, local SHA, remote SHA, ahead/behind, status, diff, and untracked files when doing baseline verification.
- Use only the original repository assigned to the task. The original code
  repository and original docs repository are the sole working baselines for
  their respective roles.
- Git Worktree operation is officially retired. Do not create, switch to, or
  operate additional worktrees for isolation, verification, or parallel work.
- If another worktree is discovered, do not modify, remove, prune, or otherwise
  operate it. Report it and continue only from the original repository when safe.
- Completion is judged by confirmed changes in the original repository plus
  the required verification.

## 14. Verification And Reporting

No conclusion without evidence.

Valid evidence:
- Code path
- Runtime value
- state file
- Queue file
- Log
- Test result
- GUI execution result
- Git status or diff for Git tasks

Every change or conclusion must distinguish evidence from inference.

Examples of evidence:
- Test result
- `py_compile` result
- `git status`
- Commit hash
- Runtime file content
- Log line
- Queue or state record

GUI execution-path rule:
- When the same feature name exists in multiple windows, tables, or context menus, trace the actual visible widget signal, slot, condition branch, and final menu/action list before changing code.
- A test against a similarly named helper, callback, or different window is not evidence that the user-visible GUI path was fixed.

Toast / Confirm Dialog policy:
- Use a Confirm Dialog only when the user has a real choice whose answer changes
  the subsequent action, such as proceed/cancel, yes/no, a destructive action,
  liquidation confirmation, or force reset.
- Informational, blocked, or failed outcomes that offer no real decision use the
  existing non-blocking Toast boundary instead of a one-button QMessageBox.
- An important operational BLOCK or FAIL uses Toast plus durable Event evidence.
  Toast and Event evidence are complementary and neither replaces the other.
- This policy does not authorize a broad replacement of existing dialogs. Apply
  it only to the explicitly approved user path under change.

GUI verification workflow:
- Do not hand GUI verification to the user merely because one automation path is
  unavailable or incomplete.
- Combine the available safe tools according to the evidence needed:
  Shell/Python for process, persisted state, Runtime, hash, and internal helper
  checks; Win32/HWND, UIA, pywinauto, Computer Use, screenshot, or visual
  inspection for actual visible-window interaction and message evidence; then
  Shell/Python again for persisted-result and mutation-boundary checks.
- If UIA or another automation layer does not expose a Qt child control, inspect
  alternative safe evidence such as window geometry, widget rectangles,
  screenshots, accessibility text, runtime state, or process/window identity
  before asking the user to perform a simple GUI action.
- Codex should perform ordinary safe GUI actions such as button clicks, Toast
  checks, and settings-window navigation when the requested action is in scope,
  the target control is identified, and the operation cannot trigger an
  unauthorized Broker/order side effect.
- User direct action is limited to boundaries that only the user should cross:
  login, certificate or password entry, security input, account authentication,
  real order approval, or a GUI action whose automation target cannot be made
  safe. Do not automate those boundaries without explicit approval for the
  current task.

If evidence is missing, report "not confirmed".

Report order for bug/feature work:

1. Problem definition
2. Call chain
3. Actual stop point
4. Cause
5. Evidence
6. Change location
7. Change summary
8. Verification result
9. Remaining issue

Do not over-report file and function names before explaining actual user-facing behavior.

## 16. Final Principle

The AI's job is to make the current real project work under the user's contracts.

When in doubt:

1. Preserve the contract
2. Trace the real execution path
3. Fix only the proven blocker
4. Verify with real evidence
5. Report the next real blocker
