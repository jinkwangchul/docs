# AGENT_WORKFLOW_REFERENCE

문서 성격: AI/Codex 운영 규정
Source of Truth: 최신 Canonical과 본 Reference

## 1. 최상위 해석 규칙

1. 사용자의 최신 명시 지시가 최우선이다.
2. AI는 기존 Canonical, Reference, 코드 계약보다 자신의 추론을 우선할 수 없다.
3. 일반 구현은 Implementation First를 따른다.
4. 구조 오염 위험이 있을 때만 구조 감사가 구현보다 앞선다.
5. 구조 오염 위험은 신규 계층, durable state, writer, Source of Truth, production call graph, lifecycle owner 변경 또는 기존 책임 반복이 있을 때 발생한다.

## 2. Implementation First Policy

프로젝트의 기본 목표는 구현 진척이다.

우선순위:

1. 코드 구현
2. 테스트
3. 코드 검토
4. Git / PR / Merge
5. 문서 작업

금지:

- 구현보다 긴 조사
- 이미 확인한 구조의 반복 조사
- 구현 중 MASTER_SPEC / WORK_RESUME / CHANGELOG 작성 제안
- 같은 내용 반복 설명
- 요청 없는 범위 확대

Conversation 시작 시 확인 질문:

이번 작업이 실제 코드 구현 또는 사용자가 명시한 필수 운영 작업을 증가시키는가?

YES이면 진행한다. NO이면 사용자의 명시 요청이 없는 한 수행하지 않는다.

## 3. 문서 작성 시점

문서는 구현 결과를 기록하는 용도이다.

구현 진행 중에는 다음 문서를 생성하거나 갱신하지 않는다.

- MASTER_SPEC
- WORK_RESUME
- CHANGELOG
- 작업재개 문서
- 기타 프로젝트 관리 문서

예외:

1. 사용자가 명시적으로 문서 작업을 요청한 경우
2. Conversation 종료 시 사용자가 마무리 / 다음 창 / 문서 작성 / 작업재개 문서 생성을 요청한 경우
3. 대규모 아키텍처 변경으로 사용자가 문서 갱신을 승인한 경우

Conversation 종료 문서는 한 번만 작성한다.

ChatGPT 역할:

- 구현 방향 결정

- 계약 검토

- 구현 범위 결정

Codex 역할:

## 5. 작업 범위와 승인

Codex는 사용자가 지정한 범위 안에서만 작업한다.

금지:

- 사용자 승인 없는 신규 계층 생성
- 사용자 승인 없는 상태명 변경
- 사용자 승인 없는 writer 변경
- 사용자 승인 없는 Source of Truth 변경
- 사용자 승인 없는 production call graph 변경
- 사용자 승인 없는 lifecycle owner 변경
- 보호 dirty / untracked 파일 수정, stage, restore, reset, stash

구조 문제가 발견되면 먼저 조사 결과와 선택지를 보고한다.

보고는 삭제, 통합, 이동, deprecate 승인으로 간주하지 않는다.

## 6. 구조 변경 통제

프로젝트의 최대 리스크는 AI 구현 과정에서 발생하는 구조 오염이다.

구조 오염의 핵심 위험:

- 너무 작은 단위를 독립 구조로 반복 분리
- 국소적 합리성을 전체 구조의 합리성으로 오판
- 기존 책임과 중복되는 wrapper / adapter / preview / validator 생성
- production caller 없는 계층 증가
- writer / Source of Truth 분산

신규 구조는 아래 조건을 모두 만족할 때만 허용된다.

1. 기존 구조가 책임을 흡수할 수 없다.
2. 독립 production caller, mutation boundary, Source of Truth, lifecycle owner, side-effect boundary 중 하나가 존재한다.
3. Canonical 계약과 충돌하지 않는다.
4. 사용자가 구조 변경 범위와 방향을 명시적으로 승인했다.

Layer 이름은 근거가 아니다. 책임, caller, mutation, Source of Truth, lifecycle 기준으로 판단한다.

테스트 통과는 production 연결 증거가 아니다. production call graph, writer ownership, state transition, runtime concurrency, identity propagation을 확인해야 한다.

구조 정책의 상세 Source of Truth:

- 00_CANONICAL/CURRENT/MASTER_SPEC_CANONICAL_2026-07-15_AI_ARCHITECTURE_CONTAMINATION_POLICY.txt

## 7. Runtime 안전 금지선

명시 승인 전 금지:

- SendOrder 실제 호출
- Kiwoom OpenAPI 호출
- Broker API 호출
- 실제 OrderRequest 생성
- Queue 상태 변경
- Runtime 파일 write
- REAL_READY 상태 변경
- rollback / restore 실행
- 보호 파일 수정

Preview / Validation / Approval / Dry-run 계층은 실제 side effect를 만들 수 없다.

실제 side effect가 허용된 작업은 사용자 지시의 commit boundary 안에서만 수행한다.

## 8. Git / PR / Merge 절차

Code repository 기본 절차:

1. Branch 확인
2. 구현
3. 테스트
4. 지정 파일만 stage
5. commit
6. push

8. review

10. master 동기화
11. origin/master 일치 확인

Docs repository 기본 절차:

1. Branch 확인
2. 문서 수정
3. git diff --check
4. 지정 파일만 stage
5. commit
6. push
7. PR 생성
8. review
9. 사용자 승인 후 merge
10. main 동기화
11. origin/main 일치 확인

금지:

- `git add .`
- `git add -A`
- 승인 없는 restore / reset / stash
- 보호 dirty 파일 stage
- merge 전 추가 범위 수정

## 9. GitHub 최종 검증

최종 보고 전 GitHub 기본 브랜치 기준으로 확인한다.

확인 대상:

- master / main 최신 SHA
- Merge Commit SHA
- PR 상태
- README
- REFERENCE_INDEX
- 최신 Canonical
- 최신 Work Resume
- 최신 ChangeLog
- 기본 브랜치가 최신 문서를 가리키는지

문서에 기록되는 Commit SHA와 Merge SHA는 GitHub의 실제 Merge Commit을 사용한다.

Reference Index 수정 시 과거 다음 작업, 과거 진행 상태, 과거 역할 설명, 완료 상태, Legacy 안내가 최신 Canonical과 충돌하지 않는지 확인한다.

## 10. 최종 보고 규칙

최종 보고는 결과 중심으로 작성한다.

포함:

- 변경 파일
- 테스트 결과
- Commit SHA
- PR 번호와 URL
- PR / merge state
- 로컬/원격 HEAD
- 보호 dirty / untracked 유지 여부

불필요한 장문 설명, 반복 설명, 요청 없는 선택지 제시는 하지 않는다.

## 11. Codex 작업 지시문 작성 규칙

Codex 지시문에는 Codex가 수행할 작업만 작성한다.

- ChatGPT의 검토 기준, 판단 과정, 배경설명을 섞지 않는다.
- 기존 운영 규칙을 매 지시문마다 반복하지 않는다.
- 작업 범위, 수정 내용, 금지 범위, 검증, 완료 보고만 작성한다.
- 검토 의견과 실행 지시는 분리한다.
- 하나의 PR에 필요한 내용만 포함한다.
## 12. Backtest Audit Log Architecture

별도 공식 문서 생성 전까지 임시 보존한다. 공식 Canonical이 생기면 AGENT에는 참조만 남긴다.

Backtest log는 사람이 읽는 텍스트 로그가 아니라 schema-first structured event ledger이다.

필수 원칙:

- stable identity linkage로 run, strategy, signal, candidate, order, position, trade, snapshot을 연결한다.
- Signal -> Candidate -> Order -> Position -> Exit replay가 가능해야 한다.
- performance 분석 필드는 pnl, mfe, mae, drawdown, fee, slippage, holding time을 포함한다.
- Runtime 독립성을 유지한다. log 실패가 전략 판단, replay, simulation 결과를 바꾸면 안 된다.
- text-log-first 설계, identity 없는 로그, event 연결 불가능한 로그, replay 불가능한 로그를 금지한다.
