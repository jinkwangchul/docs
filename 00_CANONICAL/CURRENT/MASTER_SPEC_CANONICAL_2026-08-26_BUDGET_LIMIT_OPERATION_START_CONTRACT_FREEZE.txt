2. Starting Budget AMOUNT Default
==================================================

For AMOUNT mode, the default starting budget is:

  Fresh Current Price * starting_budget_defaults.amount_multiplier

The source path is:

  operation_policy.json -> starting_budget_defaults -> amount_multiplier

The currently persisted multiplier value may be 1.5, but 1.5 is not a fixed
Canonical minimum ratio. If the environment setting changes, new default
calculation uses the changed multiplier.

Fresh Current Price is the calculation source for a new default. Last Known
price is display evidence and must not be used as the source for a new AMOUNT
default calculation.

==================================================
3. Starting Budget One-Time Resolution
==================================================

Starting budget is not recalculated on every ordinary realtime Tick after it is
resolved.

Re-evaluation is allowed only at the established resolution boundaries:

- initial resolution
- operator setting change
- the first Fresh Current Price needed in a new authenticated session

Ordinary realtime Tick movement must not rewrite or continuously change an
already resolved starting budget.

Display-oriented Last Known price and calculation-oriented Fresh Session Price
remain separate concepts.

4. Starting Budget Invalid Recovery
==================================================

This section applies to AMOUNT mode only. Quantity mode is outside this
invalid-recovery contract.

When the AMOUNT editor receives invalid input, including number parse failure,
zero or negative value, value below the current default, or another existing
validation failure:

  invalid -> Toast -> editor close -> discard invalid input

If the previous explicit amount remains valid under the current default:

- keep the previous explicit value
- do not rewrite the same value through the writer
- restore the Table projection to the previous value

If the previous explicit amount is also below the current default:

- treat the previous explicit override as invalid under the current condition
- clear the explicit override
- return to the Canonical default calculation path

The current Production representation for that default path is:

  buy_amount = 0

This means "use the default calculation path." It does not mean storing the
calculated default as a new manual explicit amount.

If no Fresh price is available and an explicit amount exists, the explicit
amount must not be deleted merely because the current default cannot be
computed. If no Fresh price is available and no explicit amount exists, the
existing `금액 대기` contract applies.

5. Recommended / Minimum Limit Basis
==================================================

The raw basis for recommended and minimum Stock limits is:

  effective/resolved starting budget * environment multiplier

The currently persisted multipliers are:

- recommended: 100
- minimum: 25

These values are multipliers, not percentages. The multiplier values themselves
are the current operational-buffer policy. Do not reinterpret them as 100% and
25%.

6. Limit Digit Alignment
==================================================

The environment setting display is:

- `자리맞춤 ON`
- `자리맞춤 OFF`

The persisted key is:

  ui/stock_limit_digit_alignment

The default is ON. Recommended and minimum limits use the same setting.

ON:

  Raw -> round_money_to_two_significant_digits()

This is the same upper-two-significant-digits rounding rule used by the
existing total-budget display calculation.

OFF:

  Raw amount unchanged

Example:

- Raw: 12,500,000
- ON: 13,000,000
- OFF: 12,500,000

Superseded interpretations:

- OFF is not floor/down-rounding.
- Minimum limit does not use a separate ceiling rule.
- The prior leading-place ceiling helper is not the current Stock limit
  alignment contract.
- Recommended and minimum limits do not use different rounding rules.

7. Limit State And Invalid Recovery
==================================================

Existing limit provenance values are preserved, including UNSET, RECOMMENDED,
MANUAL, UNKNOWN, and WAITING.

Invalid limit editor input includes at least:

- below minimum limit
- above system total budget

Common invalid flow:

  invalid -> Toast -> editor close -> discard invalid input -> restore normal
  Table projection

If a previous valid CONFIGURED state exists:

- MANUAL restores the previous enabled / amount / source
- RECOMMENDED restores the previous enabled / amount / source
- the invalid input must not cause the same state to be rewritten by the writer

If no previous valid CONFIGURED state exists and the row was UNSET:

- return to UNSET
- enabled=false
- amount=null
- source=null

The rule is:

  restore previous valid CONFIGURED state when one exists; otherwise return to
  UNSET.

9. Operation Start Admission And Order Permission
==================================================

Operation Start admission is not Order permission.

Operation Start may succeed when the current time is outside an actual trading
session, including:

- before 09:00 in CONTINUOUS / manual operation
- before the configured SCHEDULED operation boundary
- before a selected pre-market ATS session
- after pre-market ATS and before the regular session
- after the regular session and before a selected post-market ATS session
- any non-trading gap between selected future sessions on the same day

A successful start uses the existing common Operation Start backend:

  existing lifecycle and global prerequisites
  -> structural target
  -> per-target Recovery and validation
  -> explicit current-session participant registration
  -> stale-signal cutoff
  -> current time projection

The registered participant enters the operation bucket even when the resulting
projection is `감시/대기` and current order permission is false.

Time outside an actual trading session is not an Operation Start admission
blocker. Existing login, account, authentication, Recovery, validation, Review,
Emergency, and structural-target guards remain fail-closed.

Actual order permission remains independently fail-closed:

  no active actual order-permitted session -> OUTSIDE_OPERATION_TIME

Operation Start success and current order prohibition may therefore be true at
the same time. This contract does not permit pre-09:00 regular-market orders or
relax `routine_order_permission`.

10. Current Time Projection
==================================================

One time boolean must not determine status, method activity, liquidation
activity, participant membership, and order permission together.

PRE_OPERATION_BOUNDARY:

- status: `감시/대기`
- method: Routine canonical value, inactive
- liquidation: canonical liquidation value, inactive
- participant: true
- when manual liquidation policy is OFF, liquidation text is `-`

OPERATION_BOUNDARY_REACHED:

- the operation-method boundary has been reached
- the stock trading-setting start has not yet been reached
- status: `감시/대기`
- method: Routine canonical value, active
- liquidation: canonical liquidation value, active
- participant: true

ACTIVE_TRADING_WINDOW:

- status: `매수/매도`
- method: Routine canonical value, active
- liquidation: canonical liquidation value, active
- participant: true
- actual order permission still applies every final safety gate

Operation-method boundaries are:

- CONTINUOUS / 수동: 09:00
- SCHEDULED / 시간운영: configured environment operation start time

These boundaries activate the regular Routine and regular liquidation
projection. They do not by themselves begin stock BUY/SELL. The per-stock
trading-setting start remains the separate `감시/대기 -> 매수/매도` boundary.
Therefore, reaching 09:00 does not unconditionally mean `매수/매도`.

All session windows are interpreted as `[start, end)` unless a more specific
current contract explicitly states otherwise.

==================================================
11. ATS Session Contract
==================================================

ATS is not an independent operation mode. ATS is a selected additional actual
trading session. Pre-market and post-market ATS are symmetric under this rule.

During an active selected ATS session:

- status: `매수/매도`
- method: persisted ATS `execution_method`, active
- liquidation: `-`
- participant remains true

ATS has no automatic close, early close, separate liquidation policy,
automatic-close-plus-liquidation, or early-close-plus-liquidation route.

The ATS Source of Truth is:

  stocks/<stock>/state.json
  manual_ats_selection.selected_sessions
  manual_ats_selection.execution_method

Allowed execution methods are:

- ROUTINE
- MARKET
- CURRENT_PRICE

Missing legacy `execution_method` is read-only ROUTINE. Reading legacy data must
not mutate the file. An invalid value produces
`INVALID_ATS_EXECUTION_METHOD` and execution fails closed. The only canonical
writer is `write_manual_ats_runtime_selection()`; no parallel writer is
authorized.

`execution_method` controls how an existing Routine-generated BUY/SELL signal
is mapped at execution. It does not generate a signal, bypass Approval or the
Policy Gate, or define liquidation:

- ROUTINE: preserve the existing execution method
- MARKET: map BUY/SELL to MARKET with price 0
- CURRENT_PRICE: read fresh `MarketDataHost` `last_price` and map to LIMIT
- unavailable or invalid CURRENT_PRICE evidence:
  `ATS_CURRENT_PRICE_UNAVAILABLE`, no fallback

`manual_ats_selection.execution_method` is separate from an operator ATS normal
termination action. `execution_method == MARKET` or `CURRENT_PRICE` is not
termination evidence. A termination route requires its own request, command,
Queue, and completion evidence.

12. Pre-Market Timeline And Non-Trading Gaps
==================================================

Canonical example:

  Operation Start: 07:50
  ATS: 08:00-08:50
  CONTINUOUS operation boundary: 09:00
  per-stock regular trading start: 09:30

Projection:

- 07:50-07:59:59: `감시/대기` | Routine inactive | liquidation inactive
- 08:00-08:49:59: `매수/매도` | ATS method active | `-`
- 08:50-08:59:59: `감시/대기` | Routine inactive | liquidation inactive
- 09:00-09:29:59: `감시/대기` | Routine active | regular liquidation active
- 09:30 and later in the regular window:
  `매수/매도` | Routine active | regular liquidation active

NON_TRADING_GAP is the canonical common projection when:

- current-session participant is true
- no actual trading session is active now
- a future selected session remains today

Its result is:

- status: `감시/대기`
- method: underlying Routine value, inactive
- liquidation: underlying canonical liquidation value, inactive
- participant retained
- retirement prohibited
- orders blocked with `OUTSIDE_OPERATION_TIME`

The same rule applies before pre-market ATS, from pre-market ATS to regular
operation, from regular operation to post-market ATS, between multiple ATS
sessions, and in other same-day future-session gaps.

The old `BETWEEN -> 매수/매도 inactive` projection is SUPERSEDED and DO NOT USE
FOR CURRENT IMPLEMENTATION.

A simple ATS session end is not operation end, participant retirement,
automatic liquidation, or Review entry. If a future session exists, participant
and holding remain.

At the final ATS session end, ROUTINE execution context with no actual
MARKET/CURRENT_PRICE termination execution has carryover-equivalent effect. It
is not a liquidation failure.

13. Long-Term Holding And Immediate Review
==================================================

Long-term holding supports holding across days or weeks beyond one daily or
single-operation scope. Long-term holding ON does not mean every residual
holding is normal.

Source and reader:

  operation_policy.json
  review_policy.long_term_holding_enabled
  gui_operation_environment.read_review_policy()

Route truth table:

| Route evidence | Long-Term policy | Residual evidence | Result |
| --- | --- | --- | --- |
| manual + regular close/liquidation route | ON or OFF | holding remains | immediate REVIEW |
| manual + no regular close route | ON | holding-only | normal long-term holding |
| SCHEDULED + CARRYOVER | ON | holding-only | normal long-term holding |
| ATS ROUTINE final end + no actual termination | ON | holding-only | carryover-equivalent normal long-term holding |
| MARKET/CURRENT_PRICE cleanup route performed | ON or OFF | holding remains | immediate REVIEW |

Long-Term ON never exempts pending order, pending unknown, Runtime/account
mismatch, Broker/internal mismatch, integrity error, reconciliation failure,
Recovery failure, Emergency abnormality, corruption, or another independent
safety issue.

Normal end classification is immediate:

  end route completion
  -> fresh residual / pending / integrity inspection
  -> route-disallowed residual
  -> immediate REVIEW

The canonical Review mutation boundary remains
`runtime_stock_state_mutation.mutate_runtime_stock_state()`. Startup integrity
is a SECONDARY RECOVERY SAFETY NET for crash, abnormal termination, missed end
writer, prior-session residue, or external Broker/internal inconsistency. It is
not the first owner of a normal operation-end residual decision.

The historical `normal end -> next program restart -> integrity -> REVIEW`
first-classification route is SUPERSEDED and DO NOT USE FOR CURRENT
IMPLEMENTATION.

14. Participant, Retirement, And Stale Signal
==================================================

Canonical active membership is:

  _current_session_operation_participant_stock_codes

It is process-local and non-persistent. Only a successful explicit Operation
Start adds a current participant. Persisted
`runtime/operation_state.json.operation_participant_stock_codes` is a day
ledger, not active-membership Source of Truth. Startup Recovery must not restore
that ledger automatically into process-local participant membership.

Final retirement order is:

  route / residual decision
  -> REVIEW write and read-back when required
  -> retirement decision

Retiring first, projecting WAITING, and inspecting residual later is forbidden.
Retirement is also forbidden in a NON_TRADING_GAP with a future session.

After same-day normal completion, a stock may rejoin through the existing stock
context-menu `운영시작` only when the existing eligibility conditions pass.

A successful Operation Start uses the existing `ignore_signals_before` cutoff
so prior-session signals cannot re-enter the new operation. Do not solve stale
signals by cleaning or mutating the signal file.

20. Running Base Budget Adjustment
==================================================

Starting-budget editing has two distinct contracts.

When the stock is not current-running, the existing direct config edit remains
available, including mode changes between QUANTITY and AMOUNT.

When the stock is current-running:

- direct mutation of `trade_amount_type`, `buy_qty`, and `buy_amount` remains
  blocked
- the `기본예산변경` dialog may create a current-operation Runtime adjustment
- the current mode is immutable; only its value may change
- the persisted base `config.json` is not overwritten by the Runtime adjustment
- candidates, approvals, Queue rows, and orders created before confirmation are
  never rewritten retrospectively

The existing per-stock `state.json` is the persistence owner. The existing
canonical Runtime stock-state mutation writer remains the only writer. No
parallel JSON, Source of Truth, or lifecycle is created.

The adjustment is bound to the current operation by `trade_started_at`.
Pending state may therefore survive process restart and normal Recovery for the
same operation. It is ignored when `trade_enabled` is false or when a later
operation has a different `trade_started_at`. A Runtime adjustment never
silently becomes the non-running permanent base config.

21. Immediate And Next-Cycle Signal Contract
==================================================

The generic state machine observes only newly queued standard BUY and SELL
signals.

Immediate apply:

  WAIT_FIRST_BUY -> BUY -> APPLIED

The first BUY generated after confirmation receives the adjusted base-budget
input. SELL signals before that BUY do not alter the rule. Later BUY signals in
the same operation continue to receive the adjusted input.

Next-cycle apply:

  WAIT_SELL -> SELL -> WAIT_FIRST_BUY -> BUY -> APPLIED

BUY signals before the first post-confirmation SELL continue to receive the old
base-budget input. After one or more SELL signals, the first subsequent BUY and
later BUY signals receive the adjusted input.

A duplicate or non-queued signal does not advance the adjustment state.

==================================================
22. Main / Routine Independence
==================================================

Main does not interpret a Routine's strategy, name, cycle, round, averaging
stage, holding quantity, or internal state machine for budget adjustment.

Permitted inputs are limited to:

- a standard BUY signal
- a standard SELL signal
- the operator-confirmed Runtime adjustment state

SELL is not assumed to mean a full sale or cycle completion. Holding or position
quantity is not consulted. A zero holding without a SELL signal cannot activate
a next-cycle adjustment, and a remaining holding cannot prevent SELL followed
by BUY from activating it.

Main supplies only the effective base-budget input. Each Routine retains
authority over its own BUY calculation and resulting execution intent. Adding
or renaming a Routine must not require a Main budget-adjustment branch.

25. Operation Start Final-Session Pre-Admission
==================================================

The Operation Start time contract has two distinct operation-mode branches.

SCHEDULED / 시간운영 uses the configured operation start and end boundary
only. ATS sessions are not combined with this branch:

- before the configured start: Operation Start is allowed and projects
  `감시/대기`
- inside the configured window: Operation Start is allowed
- at or after the configured end: `FINAL_SESSION_ENDED` and pre-admission block

CONTINUOUS / 수동운영 uses the regular session together with the actually
selected ATS sessions for that Stock. ATS is considered only in this branch:

- an active regular or selected ATS session allows Operation Start
- an inactive session with a future same-day session produces
  `BETWEEN_SESSIONS` / `NON_TRADING_GAP`, allows Operation Start, and keeps
  watch/wait projection with order permission `OUTSIDE_OPERATION_TIME`
- when the regular session and every selected ATS session have ended and no
  future session remains, `FINAL_SESSION_ENDED` blocks Operation Start

`FINAL_SESSION_ENDED` is evaluated before state write, current-session
participant registration, OperationHost start, Execution Universe admission,
or Routine input. A final-end block therefore has participant mutation `0`.
The current time gate for actual order permission remains a separate
fail-closed boundary.
