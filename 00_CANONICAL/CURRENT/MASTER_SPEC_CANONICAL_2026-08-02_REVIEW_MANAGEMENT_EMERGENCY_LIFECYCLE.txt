- Existing row color, status color, situation signal, filter, and count

- The general stock-list protection style may continue to render REVIEW_REQUIRED

Review Management window:

- The Review Management status column must not show REVIEW_REQUIRED as

- The Review Management window does not use whole-row orange styling for review

- Review Management status-column values are limited to:
  - `긴급정지`
  - `미해결`
  - `해결`

2. Review Management Collector Role

The Review Management collector is the Source of Truth for the Review
Management table and the main review-management badge count.

The collector's role is to collect program issues and operation-blocking
targets that require operator review. It is not a normal stock-status renderer.

Review Management table columns:

1. 코드
2. 종목
3. 위치
4. 상태
5. 검토 전환 시각
6. 사유
7. 검출

Column meaning:

- 상태: current review-processing stage.
- 사유: the cause that put the stock into Review Management.
- 검출: the actual production point where that cause was detected.
- 검토 전환 시각: first time the stock entered the current review collection
  record.

Reasons are concise cause tags. They must not be complete explanatory
sentences, internal code names, module names, loader names, or function names.

Confirmed current reasons:

- `운영 데이터 없음`
- `운영 데이터 읽기 오류`
- `운영 데이터 불일치`
- `긴급정지 해제 시 보유잔량 존재`

3. Review Management Status Lifecycle

Review Management status is not produced by copying `state.status`, by copying
REVIEW_REQUIRED, or by comparing reason strings.

Allowed status values:

- `긴급정지`
- `미해결`
- `해결`

Status contracts:

- `긴급정지`: the stock is individually emergency-stopped by an explicit
  selected-stock operator action; trading is blocked; the item is collected
  immediately. A global emergency stop alone does not create this Review row.
- `미해결`: no active emergency stop is being shown for the row, but operation
  availability is not confirmed. This includes missing or unreadable state data
  and failed availability checks. Operator normalization is required and return
  is blocked.
- `해결`: emergency stop has been released and the existing operation
  availability check passed. The stock is not automatically returned to
  operation; it waits for the Review Management return button.

Forbidden:

- Showing REVIEW_REQUIRED as a Review Management status tag.
- Determining Review Management status from `review_reason` text.
- Treating emergency release alone as resolved.
- Automatically starting operation after the row becomes `해결`.

4. Emergency Stop Entry Contract

Emergency-stop Review entry is scope-sensitive.

Confirmed Review entry points:

- Operating data mismatch while already running.
- Pre-start data mismatch during operation start.
- Stock right-click `검토정지`.

`GLOBAL_EMERGENCY_STOP`:

- Activates the global emergency latch and blocks trading for all runtime
  targets.
- Changes applicable stock operation state to `EMERGENCY_STOPPED` and
  `trade_enabled=False`.
- Does not create new Review metadata and does not increase the Review count.
- Existing Review metadata is not re-entered or assigned a new transition time.

`SELECTED_STOCK_EMERGENCY_STOP` (operator-facing action `검토정지`):

- Stops only the explicitly selected single or multiple stocks.
- Does not activate the global emergency latch.
- Immediately isolates the target in Review with `trade_enabled=False`,
  `review_required=True`, and `review_status=PENDING`.
- Records `emergency_scope=SELECTED` only as durable operator provenance.
- Uses `사용자 검토정지` / `종목 검토정지` for new entries; historical
  emergency wording is not migrated.
- Reuses safe Review preparation and current return-availability projection.
  The Review status is `해결` for ALLOWED evidence and `미해결` for BLOCKED.

`GLOBAL_EMERGENCY_RELEASE_FAILURE`:

- Global release runs the existing stock availability, integrity, pending-order,
  active close/liquidation, server reconciliation, and Recovery guards.
- A normal target returns to `STOPPED` with `trade_enabled=False` without Review
  entry.
- Only a target whose guard fails enters Review, using the official reason for
  the actual failure and detection point `긴급정지 해제`.

On selected-stock `검토정지`:

1. Only the explicitly selected target stock is isolated in Review.
2. `emergency_scope=SELECTED` records provenance but is not an active-emergency
   return blocker by itself.
3. `trade_enabled=False`.
4. Routine BUY and SELL permission is blocked by the canonical Review state
   through `canonical_routine_order_permission()`.
5. Review classification is recorded.
6. Review status is projected as `해결` or `미해결` from current evidence.
7. Review reason, detection point, and first transition time are saved through
   the existing review metadata contract.

`buy_enabled` and `sell_enabled` are legacy compatibility state fields. They
are not the Source of Truth for current order permission and are not required
emergency-stop state mutations. Current order permission is calculated from
canonical runtime state and operation policy.

Operating data mismatch while already running:

- 상태: `긴급정지`
- 사유: `운영 데이터 불일치`
- 검출: `운영 중`

Pre-start data mismatch during operation start:

- 상태: `긴급정지`
- 사유: `운영 데이터 불일치`
- 검출: `운영 시작`

5. Emergency Release Contract

The actual emergency-release path is:

`gui_main_emergency_ops.release_emergency_stop_target()`

Emergency release is not operation return.

After emergency release, the system must run the existing operation availability
check:

- Pass:
  - No Review row is created solely by the global emergency lifecycle.
  - The stock becomes `STOPPED` with `trade_enabled=False`.
  - No automatic operation return occurs.
- Fail:
  - Review status becomes `미해결`.
  - Operator normalization is required.
  - Return is blocked.

Emergency release does not restore `buy_enabled` or `sell_enabled` permission.
After the integrity, Review, and Recovery checks pass, the stock remains
`STOPPED` with `trade_enabled=False`. Operation resumes only after an explicit
operator start request passes the common start guard. The successful start
records `RUNNING` with `trade_enabled=True`; BUY and SELL permission is then
calculated by `canonical_routine_order_permission()` from the canonical state
and policy context.

Example:

- If holding quantity remains after emergency release:
  - 상태: `미해결`
  - 사유: `긴급정지 해제 시 보유잔량 존재`
  - 검출: `긴급정지 해제`

6. Return Button Contract

The actual return path is:

`GlobalReviewRequiredWindow.return_selected_items_to_auto_list()`

Return gate:

- Only rows whose collector `display_status` is `해결` may return.
- `미해결` rows are blocked.
- `긴급정지` rows are blocked.

Return means returning to the operation-eligible list. It does not mean
immediate auto-start.

7. General Collector Cases

Missing `state.json`:

- 상태: `미해결`
- 사유: `운영 데이터 없음`
- 검출: `종목관리`
- The collector must not create or mutate the missing file.

Unreadable `state.json`:

- JSON parse failure or top-level non-dict state data is unreadable.
- 상태: `미해결`
- 사유: `운영 데이터 읽기 오류`
- 검출: `종목관리`
- The collector must not repair, overwrite, or normalize the bad file.

Normal REVIEW_REQUIRED rows:

- Existing `review_reason`, `review_location`, and `review_entered_at` remain
  the Source of Truth for cause, detection point, and first transition time.
- `review_reason` may accumulate multiple official operator-facing causes in
  first-seen order using the existing `A / B / C` text format. Repeated causes
  are not duplicated; no parallel `review_reasons` durable field is created.
- A follow-up cause never overwrites the first non-empty `review_entered_at` or
  `review_location`. Cause-specific internal evidence remains in
  `review_detail` and Observer evidence; there is no location-history SoT.
- Cause text does not determine `review_status`, `display_status`, or return
  availability. Those lifecycle projections continue to use current evidence.
- GLOBAL emergency activation itself is not a Review cause to merge. An actual
  Review entry caused by a failed emergency release uses that failure as its
  official cause.
- Opening or refreshing the Review Management window must not create, change,
  or overwrite the detection point. It may run the separate safe
  reconciliation preparation defined below; that boundary never changes Review
  cause, detection point, entered-at metadata, emergency ownership, or return
  destination.

8. Review Status Source of Truth

The collector supplies:

- `row["display_status"]`
- `row["return_availability"]`

The UI displays only `display_status`. Its allowed values are:

- `긴급정지`: the actual emergency stop remains active.
- `미해결`: emergency is not active, but the current return safety evidence is
  blocked or unavailable.
- `해결`: emergency is not active and the current return safety evidence is
  allowed.

`return_availability` is a separate read-only projection with values
`ALLOWED` or `BLOCKED`. It is determined from current Production evidence:

- actual emergency-stop state,
- state/config/orders readability,
- holding and pending-order integrity,
- active queue and close/liquidation evidence,
- Broker/Runtime mismatch evidence,
- Production Recovery readiness.

`review_status=RESOLVED` or an emergency-release marker alone is not sufficient
for `해결`. `해결` is possible only when the same official availability contract
returns `ALLOWED`.

The collector result is a read-only preview. `복귀` and `미지정` must rerun the
same availability contract immediately before mutation. A stale `ALLOWED`
screen value never bypasses the latest safety check. Missing/corrupt virtual
rows are always `미해결/BLOCKED`, and collection must not create or repair a
state file.

GLOBAL emergency release and Review return remain separate transitions.
SELECTED `검토정지` has no operator-facing release transition:

- emergency release does not auto-start operation,
- a pre-existing Review row remains in Review after successful emergency
  release and may become `RESOLVED`,
- explicit Review return must pass the latest availability check and ends at
  `STOPPED` with `trade_enabled=False`,
- Review return is never an operation-start command.
- an ALLOWED SELECTED Review ends only through explicit `복귀` or `미지정`,
- no selected release menu or prerequisite release action is exposed.

15. Unresolved Review Operator Guidance

The existing Review Management window provides a compact, read-only guidance
area for the selected row. It projects only already available evidence:

- operator-facing Review reason(s), with duplicates removed,
- persisted detection point,
- current return block reason,
- the operator action needed to normalize the evidence,
- the condition under which return can become available.

Internal reason codes are not presented as operator instructions. Missing and
corrupt virtual rows remain fail-closed and the guidance must not create,
repair, or overwrite their files. Emergency-active rows instruct the operator
to release emergency stop first. An allowed row states that explicit return
ends at `STOPPED` and does not start automatic operation.

The guidance projection is not a Gate or a new Review SoT. `복귀` and `미지정`
continue to rerun the canonical `review_return_availability()` contract at the
moment of mutation. `강제초기화` remains a separate dangerous operation and is
not suggested as the normal resolution path. No automatic Review return,
unassignment, Recovery execution, queue mutation, order request, or SendOrder
is introduced.

16. Resolved Return GUI Roundtrip

Only a selected row whose current projection is `해결/ALLOWED` enables the
normal `복귀` action. The displayed projection is never reused as execution
authority: immediately before mutation, the existing RESTORE backend reruns
`review_return_availability()`. If current pending, Recovery, Broker/Runtime,
emergency, close/liquidation, or integrity evidence blocks return, no RESTORE
mutation occurs and the row remains in Review.

A successful RESTORE transition:

- clears the active Review status/reason/location/timestamp metadata while the
  existing `review_routine` identity remains available for RESTORE continuity,
- writes `status=STOPPED`,
- writes `trade_enabled=False`,
- preserves the routine assignment,
- removes the row on the same window reload,
- refreshes the main Review count from the shared collector.

Review return is not operation start. It must not write `RUNNING`, enable
trading, resume routine signals, create Queue records, or call SendOrder.
Multi-selection retains the existing per-row partial-success contract: each
target reruns the same Gate, successful rows leave Review, and blocked rows
remain selected when possible with updated guidance. Missing/corrupt virtual
rows remain disabled and no file is created or repaired.

18. Emergency Scope and Release Lifecycle

New emergency-stop mutations persist ownership in the existing stock state:

- `emergency_scope=GLOBAL` belongs to the control-window global latch.
- `emergency_scope=SELECTED` belongs to an explicit stock selection.
- a missing or unsupported scope is `UNKNOWN` and is never auto-migrated.

GLOBAL activation sets the account latch first, preserves existing Review rows,
and writes only non-Review stocks as `EMERGENCY_STOPPED/GLOBAL` with
`trade_enabled=False`. GLOBAL activation itself creates no Review entry.

GLOBAL release performs the existing Recovery and Queue readiness checks as a
read-only common preflight. Preflight failure mutates no stock and leaves the
global latch active. After preflight, only `EMERGENCY_STOPPED/GLOBAL` stocks are
processed. A normal stock becomes `STOPPED`; a stock-specific safety problem
releases GLOBAL emergency ownership and becomes `REVIEW_REQUIRED/PENDING` with
the internal evidence retained in Review detail. The latch may be cleared only
after read-back confirms that no GLOBAL-owned emergency remains and no state
write failed. A remaining SELECTED emergency does not retain the GLOBAL latch.

SELECTED `검토정지` immediately enters Review and records
`emergency_scope=SELECTED` as provenance. It does not create a separate active
emergency status or require an operator-facing release. Main Monitoring and
AutoTradeSetting expose no selected-release QAction or callback; the existing
backend is retained only for legacy/internal compatibility. Review availability
ignores SELECTED provenance itself and evaluates actual Recovery, holding,
pending/Queue, active close/liquidation, and integrity evidence. The GLOBAL
latch remains an unconditional Review-return blocker. An ALLOWED row may leave
Review only through explicit `복귀` or `미지정`, ending at `STOPPED` with
`trade_enabled=False`; no path automatically starts operation.

19. Canonical Review Position Reconciliation Boundary

A complete immutable `BrokerAccountSnapshot` from the same completed
`RecoverySessionIdentity` may be authoritative evidence for reconciling a
Review stock's canonical position fields. The boundary may change only
`holding_qty` and `avg_price`; when the complete Broker snapshot has no row for
the stock, both become zero. An already-present `holding_amount` may also be
zeroed only in that absent-row case, and no new position alias is introduced.

Account, trading-day, login-session, recovery-session, HOLDINGS completion,
OPEN_ORDERS completion, stock identity, unresolved order/Queue evidence, and
the expected state-file SHA-256 must all match. Any uncertain or stale evidence
blocks the write. A successful position reconciliation preserves Review,
Emergency, close/liquidation, routine, operation, and trading-permission state;
it never resolves Review, returns the stock, or starts operation automatically.

20. Safe Review Reconciliation Preparation

Review Management is destination-decision UI: the persistent operator actions
are `복귀` and `미지정`, with `강제초기화` remaining separate. It does not expose
`보유정보정합`, `조기마감정합`, or selected-emergency release as ordinary lower
actions. On window open and explicit `상태재판정`, a preparation boundary may
reuse the canonical reconciliation services before the Collector's read-only
query.

LOCAL_SAFE handling is limited to existing local canonical terminal evidence;
it never guesses a Broker value and therefore remains safe while disconnected.
BROKER_SAFE position reconciliation requires the exact process-local completed
Recovery handoff for the current account, login session, trading day, and
Recovery session, with every existing service gate including state SHA and
Queue/open-order evidence intact. Eligible legacy EARLY_CLOSE no-target residue
uses its own existing evidence gates. Actual emergency ownership, active
order/cancel/close/liquidation evidence, command intent, and uncertain evidence
are not auto-mutated.

Preparation never returns or unassigns Review, releases emergency, starts
operation, creates Queue work, or calls SendOrder. The Collector itself remains
writer-free; automatic reconciliation is a separate pre-query step.

21. Legacy EARLY_CLOSE No-Target Reconciliation Boundary

A stale legacy `operation_command_mode=EARLY_CLOSE` residue may be reconciled
only for a Review stock when one complete immutable Broker snapshot from the
same completed Recovery identity proves zero Broker/local position, zero
pending BUY/SELL, zero active Queue/cancel work, and zero unresolved Broker
order. The expected state-file SHA-256 must still match at the atomic write
boundary. Any identity mismatch, incomplete or uncertain evidence, or real
active close/liquidation/final-sell evidence blocks reconciliation.

The mode remains `EARLY_CLOSE` as historical intent. Reconciliation writes only
the existing `EARLY_CLOSE_NO_TARGET` operation notice, its reason and timestamp,
plus `updated_at`. It never
manufactures liquidation/order/fill or close-completion evidence and never
changes Review, Emergency, position, command history, routine assignment, or
trading permission. It does not release Emergency, resolve/return Review, or
start operation automatically.

An explicit Review return or unassignment must preserve the canonical terminal
tuple `operation_command_mode=EARLY_CLOSE` and
`operation_notice=EARLY_CLOSE_NO_TARGET`, including the existing notice reason
and timestamp. Clearing that tuple would reactivate historical EARLY_CLOSE
intent. Other nonterminal operation notices retain the existing clear behavior.

The safe preparation boundary may invoke this existing service only before the
Review window's read-only collection when the current process has the exact
completed Recovery handoff. It captures current state SHA and fails closed on
stale state or account/session/day identity mismatch. Collector paths remain
read-only and never invoke reconciliation themselves.
