3. Stock Library Diagnostic Persistence
==================================================

The Production diagnostic contract is incident-only.

Normal Stock Library sync:
- creates no file under `runtime/diagnostics`
- persists no full Master projection diagnostic snapshot
- records the compact sync outcome through the existing Event Journal

Incident Stock Library sync:
- writes a compact `stock_library_invalid_codes_*.json` diagnostic only when
  `invalid_count > 0`
- keeps at most one incident diagnostic file for the same login session
- records compact counts, reason evidence, session identity, and the generated
  diagnostic filename
- does not promote the diagnostic file into a runtime Source of Truth

The former normal full-snapshot persistence contract is retired.

==================================================
4. Event Journal Role
==================================================

The Event Journal is append-only Audit Evidence and Operator History. Stock
Library sync and diagnostics retention reuse its existing Production writer.

The Event Journal records compact success/failure and issue-presence evidence.
It is not the Source of Truth for:
- Recovery
- Trading state
- Assignment
- Queue or execution state
- Broker acceptance

Event Journal evidence must not be used to reconstruct or silently mutate any
of those owners.

5. Seven-day Incident Retention
==================================================

`I5_SEVEN_DAY_RETENTION_POLICY_COMPLETE` is authoritative.

- Retention is age-only; session-count retention has no authority.
- Incident age `> 7 days` is eligible for `ROTATE_CANDIDATE`.
- Incident age exactly `7 days` is `KEEP`.
- Recent incidents are `KEEP`.
- The current login session is `PROTECTED`.
- Temporary, partial, active, malformed, unknown, or unstable files are never
  automatic delete candidates.

The prior permanent incident-protection interpretation is superseded by this
seven-day contract.

==================================================
6. Automatic Retention Trigger
==================================================

`I7_AUTOMATIC_SEVEN_DAY_INCIDENT_RETENTION_COMPLETE` is authoritative.

Automatic retention runs only after a new authenticated login identity is
established. The one-shot key is the canonical diagnostics root plus connection
epoch plus login session id.

For one authenticated session:
- automatic retention is attempted at most once
- zero candidates is a no-op
- candidates use the canonical planner, plan-bound automatic authority, and
  canonical executor
- a retention failure is recorded compactly and does not block login or Stock
  Library operation

There is no retention timer, scheduler, daemon, background worker, writer-inline
cleanup, Recovery cleanup, or startup cleanup.

==================================================
7. Delete Safety Boundary
==================================================

The executor is not a second planning authority. It executes only a validated
canonical plan and revalidates each candidate before mutation.

Required protections:
- canonical diagnostics-root containment
- canonical filename, payload type, and schema
- size, `mtime_ns`, and SHA-256 signature stability
- current-session and active-target reprotection
- malformed/unknown fail-closed behavior
- partial I/O failure isolation; remaining candidates continue
- one-shot manual or automatic authorization bound to the exact plan

The only retention mutation primitive is
`stock_library_diagnostics_retention._unlink_file()` calling `Path.unlink()`
for one file. Recursive delete, directory removal, rename, move, replace,
archive, and compression are not retention operations.
