3. PRODUCTION CANDLE OWNERSHIP CONTRACT

3.1 Routine responsibility

A Routine may declare only what its evaluator needs:
- projection mode;
- positive warmup bars when cache capacity is requested;
- its own interpretation of active filters, delays, and lookbacks.

Main must not interpret RSI, MACD, Bollinger, moving-average, OCR, price-box, or
other strategy semantics to decide cache size.

3.2 Main / MarketData responsibility

Main/MarketData owns:
- broker request scheduling;
- historical minute-candle retention;
- realtime shadow ownership;
- projection into Routine-visible bars;
- execution/observation/standby target union;
- bootstrap and incremental refresh;
- reconnect/session coordination;
- capacity and fail-closed limits.

3.3 Capacity

Required minute candles are derived from the Routine-declared warmup and applied
bar interval, plus the 10 percent margin. The common maximum is 200,000 minute
candles. A Routine that does not declare candle capability is not made a candle
refresh target merely because the stock participates in execution.

4. LOGIN, BOOTSTRAP, AND REFRESH CONTRACT

- Login monitoring synchronization occurs before Production recovery proceeds.
- Registered candle-capable stocks join Production standby even when they are not
  currently execution-ready.
- Login bootstrap uses `drain_all=True`.
- The normal per-cycle request budget is 15 targets, but drain-all bootstrap does
  not discard targets above 15. It processes the entire target set serially and
  inserts a conservative batch pause after each 15 requested targets.
- The ordinary minute cycle remains bounded/round-robin for normal refresh.
- While a login/bootstrap candle refresh is already in flight, the operation
  signal pipeline defers and resumes from the completion callback. Cache
  preparation is therefore not bypassed by the operation timer.
- Session transition clears transient refresh coordination, bootstrap-completed
  tracking, queues, and realtime session state. It does not erase the declared
  standby requirement map merely because the broker session changed. The new
  login semantic sync recalculates current requirements.

5. TRANSIENT STANDBY-REQUIREMENT FAILURE CONTRACT

The final audit found and reproduced a real gap: replacing the standby map from
only successfully calculated requirements could silently delete a previously
valid requirement for a still-registered stock when that stock suffered a
transient Routine/rules/declaration error.

The frozen correction is:

- `sync_candle_standby_requirements` accepts an explicit preserve set.
- Only a still-current stock whose standby calculation failed is eligible to
  retain its previous valid requirement.
- A local per-item validation failure inside MarketData may likewise retain the
  previous requirement for that same stock.
- A successfully calculated stock uses the new requirement.
- A stale, unregistered, unsupported, or non-Candle Routine stock is not kept
  merely because an old requirement existed.
- Preserved codes are exposed in diagnostic output.
- If every new calculation fails but a previous current requirement is
  preserved, login bootstrap still runs for the preserved standby target.

This is bounded continuity, not stale-state immortality.
