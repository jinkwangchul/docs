3. BrokerSession And Readiness
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

BrokerSessionSnapshot identifies broker connectivity with connection_epoch and
login_session_id. BrokerReadinessSnapshot projects whether broker request
prerequisites are currently satisfied. Readiness is an input to execution
safety, not complete trading or order permission.

connection_epoch rules:

- Initial process state has an initial generation.
- Successful login establishes a new login_session_id and session generation.
- A confirmed connected-to-disconnected transition invalidates the session and
  advances the generation.
- Repeated disconnected observation alone does not advance it indefinitely.
- Reconnect success establishes a new broker session.

[OFFICIAL_CONTRACT_VERIFIED]

GetConnectState returns connected/not-connected evidence. It does not by itself
authorize Recovery, routine execution, or SendOrder.

5. Global TR Governor
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

Production CommRqData flow passes through one process-local FIFO Governor owned
by KiwoomApi. Current project-conservative pacing is 1,000 ms. This is project
policy, not a claim that Kiwoom officially guarantees a universal fixed five
requests per second.

Queued requests recheck BrokerSession provenance immediately before broker
dispatch. Broker timeout starts after successful dispatch, not at enqueue.

[OFFICIAL_CONTRACT_VERIFIED]

The installed official evidence indicates that CommRqData, CommKwRqData, and
SendCondition families may share or receive dynamic request restrictions. It
does not establish exact stable minute/hour/day ceilings.

7. Execution Universe And Roster
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

Execution Universe is the central projection of stocks that may participate in
actual execution in the current process/current session. Membership and global
broker/Recovery readiness are separate axes.

Execution readiness includes at least:

- current-session participant membership
- local stock safety and status
- Review and Emergency isolation
- operation exclusion
- Recovery/global readiness

Persisted trade_enabled, RUNNING, or real_trade_enabled values alone do not
create current Execution Universe membership.

Operator-facing roster meaning:

- operation: successful explicit current-session operation-start participant
- waiting: registered but not a current execution participant
- excluded: normal candidate with operation_excluded=True
- review: Review/safety isolated

Registration and participation are distinct. The participant set is
process-local and is registered only for codes whose explicit operation start
succeeded.

Registration, exclusion release, Recovery completion, and persisted RUNNING do
not create a participant. Exclusion release alone means excluded -> waiting; it
does not start operation or create trade_started evidence.

Initial selected start:

- Successfully selected A/B become participants.
- An unselected normal assigned C is excluded by the initial selected-roster
  boundary.
- Review-isolated stocks are not bulk-mutated.

Already-running explicit add:

- Starting waiting B adds B without changing other waiting/excluded stocks.
- Starting excluded D first releases D's exclusion, then adds D only if start
  succeeds.

==================================================
8. Canonical Candle Commit
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

The canonical one-minute candle Source of Truth is:

stocks/<stock>/candles.json

There is no additional candle database or ledger. The authoritative commit
boundary uses:

- per-path process-local RLock
- read/merge/normalize
- same-directory temporary file
- flush and fsync
- strict temporary read verification
- os.replace
- strict final read-back
- semantic equality and SHA-256 content verification

Only a verified commit is authoritative.

Identity rules in Code Freeze:

- canonical_content_hash: SHA-256 of normalized canonical candle content.
- bar_key: `<stock_code>:1:<bar_time ISO seconds>`.
- bar_identity: SHA-256 of sorted compact JSON containing stock_code,
  timeframe_minutes=1, bar_time, open, high, low, close, and volume.
- commit_identity: SHA-256 of sorted compact JSON containing stock_code,
  timeframe_minutes=1, and canonical_content_hash.

BAR_COMMITTED is emitted only for a verified and changed canonical commit.
An unchanged verified commit or failed/unverified commit emits no event.

==================================================
9. BAR_COMMITTED And Per-stock Fast Path
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

BAR_COMMITTED means that canonical candle SoT changed and passed final
read-back verification. It is not a raw market event, signal success, broker
order, broker acceptance, or fill confirmation.

Current sources are opt10080 and realtime_primary.

TR operation flow:

opt10080 canonical commit(A)
-> BAR_COMMITTED(A)
-> MarketDataHost validation
-> canonical_bar_ready_for_operation(A)
-> AutoTradeOperationHost
-> current Execution Universe recheck
-> routine evaluate(A) only

A does not wait for candle refresh completion of B through N. The Production
fast path does not use a normal automatic batch-end all-stock routine probe.

An opt10080 BAR_COMMITTED event becomes an operation trigger only when it
correlates with an operation-owned request context containing rqname, stock
identity, canonical path/hash, and original operation-cycle minute key.
Manual, diagnostic, or otherwise unowned opt10080 commits do not trigger
automatic routine execution.

OnReceiveTrData and OnReceiveRealData do not directly run routine evaluation or
order processing. MarketDataHost/OperationHost queues use QTimer.singleShot(0,
...) drains to leave the broker callback stack. This is not a worker-thread
execution design.

11. Realtime Shadow And Primary
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

Realtime ticks are normalized process-locally and assembled into one-minute
shadow bars for comparison with canonical TR bars and diagnostic evidence.
Shadow bars do not write candles.json.

Safety rules:

- The first observed minute has volume_complete=False.
- Cumulative-volume reset or a minute gap fails volume completeness
  conservatively.
- An out-of-order old tick cannot rewrite a past completed bar.

Modes are process-local:

- TR_PRIMARY_SHADOWING
- REALTIME_ELIGIBLE
- REALTIME_PRIMARY
- TR_RECONCILING

In the current broker session, a full-volume comparison means MATCH with
price_match=True, volume_compared=True, and volume_match=True. With other
readiness conditions satisfied, it permits TR_PRIMARY_SHADOWING ->
REALTIME_ELIGIBLE. Promotion to REALTIME_PRIMARY occurs only after revalidation
at the next normal operation-cycle boundary, never directly inside that
comparison callback.

One full match is project Phase 9 policy, not an official Kiwoom guarantee.
REALTIME_PRIMARY and eligibility are never restored from persistence or reused
across a broker-session change.

Realtime primary flow:

completed realtime one-minute bar
-> validation and minute authority
-> Phase 6 atomic canonical commit
-> read-back verification
-> BAR_COMMITTED(source=realtime_primary)
-> MarketDataHost normalized ready event
-> AutoTradeOperationHost
-> routine evaluation

Raw realtime ticks never directly trigger routine evaluation. If
volume_complete=False, canonical write, BAR_COMMITTED, and routine evaluation
are prohibited and TR reconciliation is required.

==================================================
12. Minute Authority And TR Reconciliation
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

Each stock_code + market minute has one process-local canonical writer
authority: REALTIME or TR_RECONCILIATION. First claim owns the minute. If TR
reconciliation owns it first, a late realtime bar cannot overwrite it.

Minute authority and realtime commit tracking are bounded to 512 identities.
Pending shadow/reconciliation comparison state is also bounded to 512 entries.

Realtime-primary quality failures reuse KiwoomApi.request_minute_candles(). The
fallback therefore retains BrokerSession provenance, the global TR Governor,
screen allocation, opt10080, atomic canonical commit, and BAR_COMMITTED. No
direct CommRqData fallback exists.

Current reconciliation triggers include:

- expected realtime minute missing
- realtime volume incomplete
- realtime primary canonical commit failure

The same stock/minute request is deduplicated process-locally. TR callback
ok=True is insufficient to prove repair; the target minute must exist in the
canonical file on read-back.

Successful repair returns TR_RECONCILING -> TR_PRIMARY_SHADOWING. Returning to
REALTIME_PRIMARY requires a fresh full match, eligibility, and a later normal
operation-cycle promotion.

13. Host Ownership Boundary
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

MarketDataHost owns:

- operation-owned TR request identity
- realtime registration orchestration
- realtime shadow queue/build/comparison lifecycle
- MarketDataAuthority and minute source authority
- reconciliation
- canonical path/hash/source validation
- source-specific evaluation_tick_key

AutoTradeOperationHost owns:

- operation timer and Recovery operation boundary
- operation/status orchestration
- normalized canonical-ready trigger queue
- final Execution Universe recheck
- single-stock routine probe
- Consumer/Executor and existing order execution boundary

MarketDataHost alone binds raw bar_committed and
realtime_shadow_bar_completed. It emits canonical_bar_ready_for_operation after
validation. OperationHost does not reinterpret raw TR/realtime meaning.

evaluation_tick_key:

- TR source: original operation-owned request operation_cycle_minute_key.
- realtime primary: completed bar_time plus one minute in KST.

Market data collection, commit, and routine execution do not depend on GUI
visibility. UI/chart notification is downstream and cannot be a prerequisite
for canonical commit, routine evaluation, Consumer, or Executor.

14. Stock Registration Policy
==================================================

[IMPLEMENTED_AND_CODE_VERIFIED]

operation_policy.json uses stock_registration.default_location with allowed
values WAITING and EXCLUDED. Missing or malformed configuration defaults to
WAITING. No separate registration settings file exists.

The default applies once only to a true-new central stock. True-new is based on
central repository record and physical stock-folder existence, not merely on
routine assignment absence. Uncertainty is treated conservatively as existing.

True-new WAITING:

- operation_excluded=False
- state STOPPED
- no participant

True-new EXCLUDED:

- operation_excluded=True
- state STOPPED
- no participant

Global operation RUNNING does not change new-registration placement. Changing
the default is not retroactive. First assignment, routine move, unassign, and
reassign do not rewrite an existing stock's exclusion category. The historical
global-running `first assignment -> excluded` helper contract is retired.

15. Restart And Reconnect Safety
==================================================

[SIMULATION_VERIFIED]

On process restart, persisted RUNNING, trade_enabled, trade_started_at, and past
global RUNNING state do not recreate the current-session participant set.
Execution Universe remains fail-closed until explicit operation start.
Recovery completion alone does not create participants.

Same-process disconnect/reconnect is distinct: the process-local roster may
remain, but the new broker session resets BrokerSession identity, Recovery
readiness, MarketDataHost session state, REALTIME_PRIMARY, REALTIME_ELIGIBLE,
registration assumptions, and prior MATCH evidence. Before fresh Recovery and
market-data readiness, execution fails closed. Disconnect does not rewrite
category or exclusion.

A fresh session starts at TR_PRIMARY_SHADOWING. Required canonical gaps are
repaired through governed opt10080 reconciliation.
