11. SELL Execution Full Preview Upstream Contract

11.1 Preview Flow

SELL execution preview flows through these stages:

SELL_REAL_READY_ADAPTER_PREVIEW
-> SELL Common Execution Preview
-> SELL Execution Readiness Preview
-> SELL Signal Gate Preview
-> SELL Execution Queue Preview
-> SELL Execution Full Preview Orchestrator

The Full Preview input is the ordered set of SELL preview stage results and
candidate identities required to evaluate readiness without writing Runtime,
Queue, or broker state.

11.2 Stage Responsibilities

- Execution Readiness confirms that the SELL candidate can enter execution
  readiness review without changing durable state.
- Signal Gate confirms that the candidate passes the SELL signal gate contract.
- Queue Preview confirms that the candidate can form a preview-only
  ORDER_QUEUED record contract.
- Full Preview preserves the ordered stage results, aggregates status, and
  stops on BLOCKED or INVALID without selecting candidates.

11.3 MARKET Contract

- `current_price` must not be injected automatically.
- MARKET SELL is allowed only when an explicit MARKET contract is satisfied.
- If the explicit MARKET contract is not satisfied, the preview status is
  BLOCKED.

11.4 PENDING / CANCEL Contract

- Preview and Runtime contracts remain separated.
- PENDING or CANCEL candidates must not be promoted into the normal SELL
  execution path.
- Actual cancel calls are prohibited in Preview.

11.5 Multiple Candidate Contract

- Preview must not automatically select a candidate.
- Preview must not automatically remove a candidate.
- All candidates and their input order must be preserved.
- Candidate selection belongs outside the Preview chain.

11.6 Preview MASTER_ENGINE Ownership

- The SELL Preview Chain is owned by MASTER_ENGINE.
- Routine layers provide preview inputs and results only.
- This ownership does not change Runtime Commit ownership after the Preview
  boundary.

12. Runtime Living Contract

This section records the current code contract for Runtime, Queue, SendOrder,
Chejan, Fill, and Position. It supersedes older history-only Runtime Commit
progress notes in this file.

12.1 Runtime Source of Truth

- `routine_signals.json`: Signal source of truth.
  - Writer Owner: `routine_signal_queue.py`.
  - Responsibility: persist routine signal candidates before queue conversion.
- `order_queue.json`: Order lifecycle source of truth.
  - Writer Owner: `execution_queue_writer.mutate_order_queue()`.
  - Responsibility: preserve order lifecycle, dispatch claim, SendOrder call
    lifecycle, Chejan lifecycle, and queue revision.
- `fills.json`: Fill event ledger source of truth.
  - Writer Owner: `execution_fill_recorder.py`.
  - Responsibility: append reviewed fill events only.
- `positions.json`: Position state source of truth.
  - Writer Owner: `position_update_service.py`.
  - Responsibility: apply recorded fill deltas to position state.
- `broker_holdings.json`: Kiwoom broker holding snapshot source of truth.
  - Writer Owner: `broker_holding_recorder.py`.
  - Responsibility: preserve the latest live Kiwoom gubun=1 account/code
    holding snapshot and its reconciliation evidence against internal
    positions.
  - Broker holdings do not automatically create, delete, or overwrite
    `positions.json`.

12.2 Queue Living Contract

- Canonical writer: `execution_queue_writer.mutate_order_queue()`.
- The canonical writer owns the queue lock, revision/CAS check, backup,
  temp write, atomic replace, and post-write verification.
- Queue mutation must re-read the queue under lock before applying a mutation.
- Dispatch, SendOrder lifecycle, and Chejan lifecycle state mutation must pass
  through this boundary.
- Builder, Adapter, Preview, Validator, and Dry-run layers must not mutate the
  queue.

12.2.1 Operation Policy Gate Contract

- Owner: `operation_policy_gate.apply_operation_policy_gate_for_order()`.
- The Operation Policy Gate owns the durable `APPROVED` ->
  `EXECUTABLE` / `BLOCKED_POLICY` transition.
- The input state must be `APPROVED`.
- Policy pass writes `status=EXECUTABLE`.
- Policy block writes `status=BLOCKED_POLICY`.
- `execution_enabled` remains `False` after this transition.
- Queue mutation must use `execution_queue_writer.mutate_order_queue()`.
- Direct snapshot writers are prohibited for this transition.
- Same-result reapplication is a no-op.
- Duplicate target identity, stale revision, and progressed lifecycle states
  must not overwrite the queue.
- After `EXECUTABLE`, the existing Execution Enable -> REAL_READY flow remains
  unchanged.

12.3 SendOrder Lifecycle

Queue lifecycle before broker evidence:

ORDER_QUEUED
-> DISPATCH_CLAIMED
-> SEND_ATTEMPTED
-> SEND_CALL_IN_PROGRESS
-> SEND_CALL_ACCEPTED / SEND_CALL_REJECTED / SEND_UNCERTAIN

- `send_order_called=True` is allowed only after the real callable boundary has
  been entered.
- `SEND_CALL_ACCEPTED` means the SendOrder callable result was accepted by the
  local call contract. It is not broker acceptance.
- Broker acceptance, rejection, fills, and cancellation are confirmed only by
  the Chejan lifecycle.

12.4 Chejan Contract

Kiwoom gubun=0 order and fill events are normalized, reviewed, and recorded
through the Chejan lifecycle before Fill or Position follow-up work is
performed. `SEND_CALL_ACCEPTED` is not broker acceptance; only Chejan evidence
can confirm broker acceptance, rejection, fills, or cancellation.

Current allowed lifecycle transitions for normal order/fill events:

- `SEND_CALL_ACCEPTED` or `SEND_UNCERTAIN`
  -> `BROKER_ACCEPTED`
- `SEND_CALL_ACCEPTED` or `SEND_UNCERTAIN`
  -> `BROKER_REJECTED`
- `SEND_CALL_ACCEPTED`, `SEND_UNCERTAIN`, `BROKER_ACCEPTED`,
  `PARTIALLY_FILLED`, or `FILLED`
  -> `PARTIALLY_FILLED` / `FILLED`
- `SEND_CALL_ACCEPTED`, `SEND_UNCERTAIN`, `BROKER_ACCEPTED`, or
  `PARTIALLY_FILLED`
  -> `CANCELLED` / `PARTIAL_CANCELLED`

Chejan recording appends event history and reduces broker lifecycle on the
matching queue record. It does not write fills or positions.

When a Chejan event produces `PARTIAL_FILL` or `FULL_FILL`, Fill ledger
recording and Position updates run only after the canonical Queue lifecycle
record succeeds. Event identity is preserved so repeated live Chejan events do
not duplicate Queue, Fill, or Position mutations. Missing downstream Fill or
Position work is persisted as manual reconciliation state on the Queue record
and may be retried by event identity without reapplying the already recorded
Queue lifecycle.

Kiwoom gubun=1 holding events are not Fill events. They update
`broker_holdings.json` and are compared read-only against `positions.json`.
Consistent snapshots clear the broker-holding reconciliation state for the
same account/code only. Mismatches are preserved as manual reconciliation
evidence and do not modify internal Position state.

Cancel/modify Chejan evidence is fully connected through the current production lifecycle. Manual cancel/modify
requests can be created as separate `ORDER_QUEUED` records and sent through
SendOrder type 3/4/5/6 with `original_order_no`. Chejan FID 904 is preserved
as the canonical original order number, and broker Chejan evidence links the
request record to the original order identity before applying original-order
effects.

12.5 Fill Contract

- Writer Owner: `execution_fill_recorder.py`.
- Fill recording appends to `fills.json` only.
- It does not mutate Queue or Position state.
- Duplicate detection uses `execution_identity_source` plus
  `execution_identity` when present.
- FID 909 remains an execution identity source. Existing fallback duplicate
  detection is kept only for records without explicit identity source/value.
- Append uses file lock, backup, temp write, atomic replace, and post-write
  verification.

12.6 Position Contract

- Writer Owner: `position_update_service.py`.
- Position updates consume recorded fill records.
- Idempotency scope is `position_id + broker + account_no + code`.
- Cumulative quantity delta is tracked separately per order identity.
- Position updates do not mutate Queue or Chejan state.
- Broker holding snapshots are external evidence. They are compared with
  internal positions but must not silently overwrite internal positions.

12.7 Preview Safety Line

In this Runtime / Execution pipeline, the following layers do not perform file writes, queue mutations, SendOrder
calls, broker calls, or Runtime state changes:

- Preview
- Adapter
- Builder
- Validator
- Dry-run

12.8 Projection / Recovery / Reconciliation Contract

- Projection is a Runtime reconstruction layer.
- Projection reads Queue and Fill evidence to calculate Runtime state
  candidates.
- Projection must not write Runtime state or change any Source of Truth.
- Recovery decides whether Runtime recovery is required and possible.
- Recovery must not perform automatic normalization or write outside the
  approved Commit Boundary.
- Reconciliation checks Queue, Fill, and Position consistency.
- Reconciliation detects mismatches and provides preview results only.
- Projection, Recovery, and Reconciliation are Reader and Validator layers.
- They must not call Canonical Writers.
- They must not call SendOrder or broker APIs.
- Runtime writes remain allowed only at the approved Commit Boundary.

13. BUY Budget Increase Policy Revision

This section replaces older BUY increase descriptions that used fixed X2/X3 or user-array style wording. The project philosophy remains unchanged: BUY planning may define target values, but the final executable order is still constrained by budget, holdings, and execution safety checks.

13.1 Initial Budget Setting Terms

The initial setting terms are:

- 최초 예산 설정
  - 주수 설정
  - 예산 설정

The old first-setting terms "주수기준" and "금액기준" are deprecated.

The term "금액 기준" remains valid only when it means the increase method described below.

13.2 Increase Methods

Supported increase methods are:

- 회차 기준
- 금액 기준

The old fixed X2, X3, and user-array descriptions are deprecated.

13.3 회차 기준 Contract

회차 기준 supports two operators:

- 합(+)
- 곱(×)

The operator and numeric value are entered directly by the operator. The UI must not restrict the value to fixed combo choices such as X2 or X3.

Examples:

- + 2
- × 2
- × 1.5
- + 5

Calculation:

- 1회차 = 최초 예산 설정값
- From 2회차:
  - 합(+): current order target = previous round number + configured value
  - 곱(×): current order target = previous round number × configured value

Example, initial shares 2주 and 회차 기준 × 2:

- 1회차: 2주
- 2회차: 2주
- 3회차: 4주
- 4회차: 6주
- 5회차: 8주

Example, initial shares 2주 and 회차 기준 + 2:

- 1회차: 2주
- 2회차: 3주
- 3회차: 4주
- 4회차: 5주
- 5회차: 6주

13.4 금액 기준 Contract

금액 기준 supports only 곱(×).

The multiplier is entered directly by the operator.

Examples:

- × 1.2
- × 1.5
- × 2
- × 3

Calculation:

- 1회차 = 최초 예산 설정값
- From 2회차:
  - current round budget target = previous round budget value × configured multiplier

Example, initial budget 10000 and 금액 기준 × 2:

- 1회차: 10000
- 2회차: 20000
- 3회차: 40000
- 4회차: 80000
- 5회차: 160000

Older examples such as 100 -> 300 -> 900 -> 2700 are deprecated when they imply fixed X3 policy or conflict with the operator-entered multiplier contract.

13.5 Supported Combinations

주수 설정 supports:

- 회차 기준(+)
- 회차 기준(×)
- 금액 기준(×)

예산 설정 supports:

- 회차 기준(+)
- 회차 기준(×)
- 금액 기준(×)

The total supported combinations are six.

13.6 예산 설정 Policy

예산 설정 does not calculate a target share count directly.

예산 설정 determines the maximum buy budget for each round. At actual order time, the system calculates the maximum integer quantity that can be bought at the current order price without exceeding the confirmed budget.

No order may be created above the confirmed budget.

13.7 Actual Order Contract

The calculated value is a round target, not the final executable order.

Immediately before the actual order is created, the final quantity must apply:

- total budget
- routine budget
- per-symbol budget
- maximum holding quantity
- other order restrictions

The final order quantity is the quantity that remains valid after these constraints are applied.

13.8 UI Contract

Increase values are entered directly by the operator.

The UI contract is:

- operator selection: + or ×
- input value: direct operator input

Fixed combo-only values are prohibited for this policy.
