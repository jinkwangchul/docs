2. Group And RoutineInstance Deletion Safety
==================================================

Group and RoutineInstance complete deletion use the shared read-only
`preview_delete_scope()` policy before mutation.

- A Stock in the current-session running set blocks deletion.
- A Stock that is not running, has `holding_qty > 0`, and is not protected by
  Review blocks deletion as a long-term holding.
- A Review-protected Stock with holdings does not trigger the long-term-holding
  blocker. This permits the approved Group/Instance deletion path; it does not
  release Review or issue a Broker command.
- A missing `state.json` file fails closed. The current shared JSON reader
  normalizes malformed/non-dict content to an empty dictionary, so malformed
  state content is not separately blocked by this deletion preview.
- Successful deletion clears only the affected Stock assignment to
  `UNASSIGNED`; the central Stock record is preserved.
- Group deletion retains its durable marker, atomic registry update,
  read-back, and rollback contract. RoutineInstance deletion stages the
  instance directory and restores Stock/Episode evidence on failure.

Relationship Sources of Truth remain:

- Group to RoutineInstance: `instance.json.group_id`
- RoutineInstance to Stock: `assigned_routine_instance_id`
- assignment history: canonical Assignment Episode records

3. Complete Program Factory Reset
==================================================

Complete program initialization is a local filesystem transaction, not an
order, liquidation, cancellation, correction, or Broker operation.

- Operation, holding, Review, authentication, account, and Broker connection
  state do not block the reset safety check.
- The GUI requires the exact confirmation text `전체초기화`.
- Before filesystem staging, the GUI quiesces owned timers/hosts. A failed
  reset resumes the prior runtime only after complete rollback.
- The service writes and verifies a transaction marker, stages all targets,
  creates pristine local runtime state, performs read-back validation, and
  removes the transaction only after success.
- Failure performs rollback. Incomplete rollback remains fail-closed with
  transaction residue.
- Removed program/user operation data includes Logical Groups,
  RoutineInstances, registered Stocks, archived Stocks, Assignment Episodes,
  Performance Ledger, migration manifests, artifacts, reports, logs, and
  non-preserved Runtime data.
- Preserved product/static data includes Routine Definitions, Engines,
  `runtime/stock_library.json`, `runtime/stock_library_meta.json`, the bundled
  Stock Library, screen registry, base-stock source, and project changelog.
- Routine-local derived approval/report artifacts are removed without deleting
  the Routine Definition package.
- `broker_orders_called` is invariantly `0`. The reset path does not call
  `CommConnect`, TR, `SendOrder`, cancellation, correction, or liquidation.

The current-window Production GUI reset was exercised successfully. Current
read-only post-reset evidence shows no `.factory_reset_transactions` residue,
preserved Routine/Engine and Stock Library files, and subsequently recreated
Logical Group/Instance/Stock user data. This is filesystem evidence only; it
does not convert a Broker-side assumption into execution evidence.

4. Registration And Login Safety
==================================================

- Registering a Stock already assigned to the same RoutineInstance is an
  idempotent no-op.
- A Stock with a CURRENT assignment to another RoutineInstance is blocked from
  duplicate registration.
- Successful assignment writes the canonical assignment relationship and
  Assignment Episode transition; it does not rewrite historical ownership.
- The Stock registration dialog has one process-wide instance per target
  RoutineInstance. Reopening reuses, reparents, raises, and activates it.
- `KiwoomApi.login()` is single-flight. While `_login_requested` is true,
  another request returns `login_in_progress` and does not call `CommConnect`
  again.

5. Stock Library And Broker-call Boundary
==================================================

The connected-session Stock Library sync reads master data through the
existing Kiwoom ActiveX master functions:

- KOSPI: `GetCodeListByMarket("0")`
- KOSDAQ: `GetCodeListByMarket("10")`
- NXT eligibility: `GetCodeListByMarket("NXT")`
- Stock name: the existing master-name function

The canonical local search record stores `code`, full `name`, `market`,
`nxt_available`, raw `master_stock_state`, raw `master_construction`, raw
`master_stock_info`, `master_stock_market_kind`, derived `status`, and derived
`classification`. Status and classification are metadata on the existing Stock
Library record, not a parallel Source of Truth. If master evidence is missing,
the UI preserves the unknown value rather than inferring a normal state.
The Stock registration search reads only the local Stock Library snapshot.
Searching causes zero additional TR or master calls.

6. Stock Registration Dialog Contract
==================================================

The current result structure is fixed:

`종목코드 | 종목명 | 시장 | 등록상태 | 분류 | 비고 | 현재주가 | 등락률 | 체결강도 | 전일대비 | 거래대금 | 거래량 | 시총 | 상태`

- All data columns use `QHeaderView.Fixed`; user resize, stretch, and
  ResizeToContents are not used.
- Dialog width is fixed from row-number header, all fixed data columns,
  vertical scrollbar, frame, and layout margins. The horizontal scrollbar is
  disabled and the vertical scrollbar is always reserved.
- Row numbers reserve a centered three-digit `999` width.
- Stock name reserves the current-font Korean 14-character width. A fitting
  name is centered. An overflowing full name is left-aligned and clipped at the
  cell boundary without ellipsis; only a clipped name receives its full-name
  persistent Tooltip.
- Market identity comes from the Stock Library. The current UI renders KOSPI
  as `KOSPI` in navy and KOSDAQ as `코스닥` in brown. Selection preserves
  readable text.
- `비고` displays `NXT` only when `nxt_available is True`; false or unknown is
  blank.
- `분류` is projected from official Master evidence only. The canonical value
  `일반종목` is rendered as `일반` in the cell; ETF, ETN, SPAC, REIT, 기타, and
  `-` retain their canonical display values. The `[일반종목]` badge is a local
  filter: OFF shows the complete current result, ON shows only canonical
  `classification == "일반종목"`, and toggling does not re-search or issue a
  TR.
- `상태` is built from `GetMasterConstruction` and `GetMasterStockState` raw
  evidence. A long or multi-value cell may be elided with `...`, but its
  persistent Tooltip contains the complete original text. Missing evidence is
  displayed as `-` with no status Tooltip.
- The market snapshot columns are transient UI data. `현재주가`, `등락률`,
  `체결강도`, `전일대비`, `거래대금`, `거래량`, and `시총` are filled from the
  existing one-shot snapshot path; `전일대비` means current cumulative volume
  divided by previous total cumulative volume multiplied by 100, not a
  same-time comparison.
- Current table styling uses a white background, `#EBEBEB` separators/border,
  and a distinct blue selection background. Alternating row colors are not
  enabled in the current implementation.
- Typing, deleting, `textChanged`, `textEdited`, and `editingFinished` do not
  search. Enter and the `검색` button call the same search path exactly once.
- Search, double-click registration, explicit registration, duplicate guards,
  CURRENT/UNASSIGNED classification, and Stock Library validation retain their
  existing behavior.

13. AutoTradeSetting Right Population And Count
==================================================

The right registered-Stock table has two explicit population modes.

`FLAT_FILTER_SCOPE` applies while the left view represents a flat filtered
population, including `[유효] + [종목] + [전체/현재/과거]`. The whole filtered
population owns the right scope. Clicking one Stock row does not narrow the
right table to its parent Routine Instance.

`HIERARCHICAL_SELECTION_SCOPE` applies when the left hierarchy is exposed.
Group selection resolves all Instance Stocks in that Group, Routine Instance
selection resolves that Instance, Stock selection resolves the Stock row's
parent Instance, and Root/all selection resolves all registered Stocks.

Therefore left display intent has precedence over row selection in flat mode,
while canonical selected identity owns scope in hierarchical mode. The same
Stock click may intentionally produce different scopes in the two modes.

The right `운영/대기/제외/검토` filters operate only inside the already-resolved
right population. They must not reintroduce out-of-scope Stocks. Aggregate
badges and filtered rows use the same canonical Stock-code classification and
deduplication.

`종목(N)` follows the current display mode. In operation/waiting display it is
the unique operation/waiting population count; in all-Stock display it is the
unique registered population count. It is neither an always-registered count
nor an always-operation/waiting count.

15. Context Menu And Routine Clone Status
==================================================

Main Monitoring and AutoTradeSetting Stock context menus use the shared Stock
context-menu builder. Their common candidate actions are Operation Start,
Review Stop, select all, clear selection, operation exclusion, real-order
permission toggle, Early Close, individual liquidation, ATS settings, time
change, reset, Stock registration, unregister, and mini chart. Action presence
and enabled state remain fail-closed by canonical row identity, current
selection, and callback availability; a context without required evidence does
not invent an enabled action.

A current-running Stock cannot be moved directly to operation exclusion. The
same authoritative guard applies to double-click, context-menu, and any other
mutation caller. Context-menu disabling is an operator affordance, not the sole
safety boundary; direct callback invocation must also fail closed. After the
Stock is no longer current-running, the existing non-running exclusion contract
applies.

State-specific menus preserve their existing action composition, ordering, and
separators. Disallowed actions remain visible and are disabled rather than
deleted or hidden. A disabled parent action blocks access to its submenu, and a
backend callback cannot bypass the same state guard. Disabled actions use one
muted gray foreground instead of semantic active colors; in particular, a
disabled Early Close action must not remain green. Enabled actions retain their
existing semantic colors.

AutoTradeSetting Routine Instance context menus include `루틴복제` between
settings and deletion. AutoTradeSetting and Main reuse the same canonical
snapshot clone helper and repository writer. Early Close and immediate
liquidation are not added to the AutoTradeSetting Routine Instance menu.
