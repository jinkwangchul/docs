3. SIGNAL VALIDATION V2 DOMAIN
======================================================================

3.1 Purpose and source of truth

IndicatorFollowSignalValidationWindow is a modeless, independent working copy
for repeated Historical signal-only replay. It starts from the current unsaved
Indicator-Follow settings snapshot, projects only the approved signal controls,
requests Historical candles, calls the existing evaluator, and displays the
immutable replay result.

V2 does not acquire Production or Mock Runtime state, MarketDataHost, normal
Candle commit, realtime registration, Candidate/Signal Queue, order, SendOrder,
Chejan, position, PnL, or execution authority. It does not alter V1 or the
September 13 read-only chart contract.

3.2 Header and controls

The V2 compact header contains current stock, timeframe in supported minute
bars, and a Validation-only candle count. The default candle count is 100 in
both the visible control and the flow's initial Historical request. Direct
numeric entry is supported without spin arrows. Candle count is not applied
back to the source routine settings.

Basic, BUY, and SELL sections are all collapsed on first entry while all three
headers remain visible. Their outer collapsed height, header height, title and
separator geometry, and vertical centerline are normalized inside V2 without
changing the common registration/edit builders. Expanding a section adds only
its detail body.

The initial normal-window fit uses current available screen geometry. Initial
centering runs once. After the operator owns the geometry, validation, settings
apply, stock changes, and section toggles preserve user size and position.

3.3 Stock workflow and metadata

The current stock is a plain display rather than a ComboBox. The basic section
expands an inline one-row recent-stock projection and a Stock Selection button.
The button uses the existing IndicatorFollowValidationStockPicker. Recent-stock
items select through the same activation path.

The existing QSettings MRU contract is retained: recent-first order,
de-duplication, restart restoration, and a maximum of 15 stored records. The
inline projection keeps complete code/name pairs that fit the actual available
width and removes oldest hidden records through the existing store contract.

Selecting the current stock again does not issue a redundant Historical
request. Selecting another stock invalidates the prior request generation,
clears the old result, requests a fresh read-only market snapshot and Historical
replay, and rejects stale market/Historical callbacks by generation and stock
identity.

The stock tooltip is a three-line operator projection: identity/market/status/
NXT; current/open/high/low; and change rate/previous-day rate/execution
strength. It merges verified static library metadata with the existing
read-only initial market snapshot. Missing safe values remain "-". Hover does
not itself issue a broker request.

3.4 Validation and final-candidate handoff lifecycle

Initial validation uses the current timeframe, candle count, and signal
settings. Thereafter the validation Context and Routine strategy controls have
different refresh semantics. A confirmed timeframe change immediately starts a
fresh Historical request and Replay. A confirmed candle-count edit does the
same, using the count directly as the read-only Historical request size. Spin
editing does not issue a request for every intermediate digit. These automatic
Context refreshes update only V2 and emit no parent Candidate. Candle count
remains Validation-only; timeframe remains a Routine setting included in a
later Candidate.

BUY/SELL expressions and detail/filter controls do not auto-Replay while the
operator edits them. They invalidate the canonical signal-UI fingerprint and
mark the displayed result stale. The single primary action is always presented
as [설정적용]. If the current result already matches the current V2 state, the
action emits one detached Candidate without a duplicate Replay. If the result
is stale, the action first validates the current final state; only a successful
result with the same fingerprint emits the Candidate once. A failed validation
emits nothing and leaves the parent Working UI unchanged. Existing per-window
request generation and request identity ensure that a late older Historical
result cannot replace the newest Context result.

The Candidate passes through the existing Flow/Binder to the still-live source
registration/edit dialog. It contains only the approved signal-control
whitelist and is applied to the parent Settings Working UI through the existing
canonical UI-state loader. It does not include candle count, selected
Validation stock, chart/view state, Replay identity/result, execution method,
Runtime policy, or other non-signal state. A closed or unavailable source fails
closed.

V2 is a Routine Configuration Validation Workspace. Its seed is the parent
dialog's current unsaved Working settings; V2 does not reread disk. Any number
of edits, validation runs, stock changes, candle-count changes, and chart
interactions remain inside the V2 Working Copy until [설정적용] succeeds. The
button remains enabled and labelled [설정적용] after success, so B, C, and D may
each be validated and handed off in sequence; N successful actions produce N
Candidate handoffs. A separate status may report "설정 적용 완료". No handoff
creates/updates an Instance or writes rules.json, Runtime, Broker, or order
state. Registration and edit/save remain the sole persistent writers.

3.5 Settings Working Copy undo contract

The Settings dialog button formerly labelled "다시 불러오기" is now
[되돌리기]. It preserves its existing location and restores a detached
canonical in-memory snapshot through the established UI-state apply helper. It
does not reread rules, registry, or another persistent source.

Registration and edit dialogs now use one identical fixed-baseline contract.
After the dialog's initial/template settings (registration) or saved settings
(edit) have been loaded into the UI, one detached
_initial_settings_undo_snapshot is captured. It is immutable for that dialog
lifetime. Manual edits, opening or closing V2, Context refreshes, successful or
failed Replay, and any number of successful Candidate handoffs do not replace
it. [되돌리기] always restores that dialog-open snapshot through the canonical
loader without rereading persistent rules.

There is no registration-only undo target, no V2-launch snapshot promotion, no
history stack, and no redo. Thus registration A -> manual B -> V2 C/D/E ->
[되돌리기] returns to A; edit saved A -> V2 B/C/D -> [되돌리기] likewise
returns to A.

Candidate handoff remains distinct from persistence. The existing registration
and edit/save actions remain the sole writers and build their payload from the
current parent Working UI, including the accepted Candidate when the operator
chooses to commit it.

4. SELL SIGNAL SEMANTICS
======================================================================

The Runtime meaning of an empty, missing, or whitespace-only UI SELL expression
is normalized in routine_macd_engine.py.

The configured/evaluated UI conditions ui_condition_a, ui_condition_b, and
ui_condition_c may retain all of their settings and diagnostic observations,
but without a valid common signal_expression they are excluded from the final
SELL aggregation participating set. They cannot create a fallback OR SELL and
cannot contribute final matched groups, details, signal index, delay, or
aggregation cause metadata.

Independent SELL signals such as macd_sell and profit_rate_sell remain eligible
when their own conditions pass. A SELL caused by an independent signal does not
inherit non-participating UI A/B/C evidence. Valid UI expressions, including
AND, OR, parentheses, and supported NOT forms, retain their established
expression-centric evaluation.

The normalization changes participation, not stored UI data. It does not erase
A/B/C values, add a default expression, or migrate rules.json.

5. SIGNAL EVIDENCE AND CHART CONTRACT
======================================================================

Official BUY/SELL markers remain located at evaluation_index/evaluation_time.
signal_index/signal_time and delay_bar remain the condition-evidence location
and do not replace the official marker position.

Marker tooltips contain the signal side/time followed only by operator evidence
lines in the form:

  BUY or SELL + evaluation time
  ▪ filter-name actual-value

Evidence selection follows the final decision structure:

- AND includes all cooperating filters;
- OR includes direct filters from every surviving branch;
- NOT excludes the rejected obstacle and shows only the surviving signal side;
- a filter belonging only to a failed path is excluded; and
- only identical condition plus identical evaluation evidence is de-duplicated.

Internal A/B/C identifiers, PASS/FAIL wording, raw trace paths, and duplicated
group/aggregation rows are not operator tooltip content. The underlying reason,
matched_groups, details, trace, and aggregation observations remain intact.

The chart uses real Historical timestamps for approximately readable major
ticks and does not synthesize dates. The price axis remains fixed while the
candles and time axis scroll. BUY and SELL marker positions, marker tooltips,
bar selection, and the selected-Candle summary remain separate projections of
the immutable replay snapshot.

6. COMPLETED TRADE CYCLES AND ESTIMATED RETURN
======================================================================

6.1 Completed cycle projection

completed_validation_cycles() is the source of truth for the lower table. A
cycle contains:

- cycle_number;
- contributing BUY indexes and buy_count;
- average_buy_price from the established Validation average-price context;
- SELL index and sell_price; and
- estimated_return_percent =
  (sell_price - average_buy_price) / average_buy_price * 100.

Leading SELL, BUY-less SELL, trailing SELL, and the final BUY segment without a
SELL do not create a completed cycle. A BUY at the same evaluation bar as a SELL
does not enter the cycle closed by that SELL. Cycle-row selection moves to the
matching SELL candle without changing marker or signal meaning.

The lower table has seven operator columns: cycle, BUY range, BUY count,
estimated average, SELL time, SELL price, and estimated return. It keeps five
visible rows, an always-visible vertical scrollbar, no horizontal scrollbar,
and the verified fixed presentation height (264 px on the Windows harness) with
column ratios independent of row count.

6.2 Top aggregate estimated return

The top Estimated Return no longer displays only the latest completed cycle.
It reads self._completed_cycles and computes a cost-weighted aggregate:

  cycle_cost = average_buy_price * buy_count
  cycle_profit = cycle_cost * estimated_return_percent / 100
  aggregate = sum(cycle_profit) / sum(cycle_cost) * 100

No completed cycle or total cost <= 0 displays "-". This is not a simple mean,
sum, compound return, reinvestment model, budget model, or execution PnL. It
does not reread candles or recompute cycle averages/SELL prices. The lower-cycle
calculation and every cycle field remain unchanged.

7. REPLAY PERFORMANCE NORMALIZATION
======================================================================

7.1 Phase 2: frozen Entry reuse

The context provider receives a new prior-entry list container, but the already
frozen ValidationReplayEntry values are reused instead of being reconstructed
through deep JSON conversion on every prefix. Mutating the container or a
detached property projection does not mutate stored entries. Canonical replay
output remains byte-equivalent to the former deep-recreation reference.

7.2 Phase 3: same-prefix indicator reuse

For the default evaluator, one context-independent base indicator series is
built per eligible Historical prefix and reused for SELL then BUY evaluation.
Each side receives its own shallow mapping view before context enrichment, so
AVG_PRICE/SIGNAL_PRICE additions (and legacy ORDER_PRICE compatibility data) do
not mutate the shared base mapping or leak between sides. The underlying MACD,
RSI, moving-average, Bollinger, and Price Box lists remain read-only in this path.

Custom evaluators keep their existing API and call order. No whole-series
future lookup, incremental indicator formula, worker, timer batch, or event-loop
pumping was introduced. build_indicator_series calls for the standard fixture
were reduced to 98/198/498 for 100/200/500 candles, approximately half of the
former SELL-plus-BUY duplicate count.

7.3 Phase 4: default read-only fast path

The read-only fast path is restricted to the exact default Production evaluator
and either no context provider or the exact default Validation average-price
provider. At each evaluation index it reuses the detached rules mapping and the
current prefix list for base-series build, context, SELL, BUY, signal-time
lookup, and entry construction. SELL and BUY still receive independent context
dictionaries.

Default evaluator, default average-price provider, trace observer, and entry
construction were verified not to mutate candle, rules, prior-entry, supplied
context, signal, or trace inputs. ValidationReplayEntry and
ValidationReplaySnapshot continue canonical defensive storage and detached
public projections.

Any custom evaluator or custom context provider stays on the prior JSON
defensive-copy path. A custom evaluator/provider that mutates nested candle or
rules data cannot mutate the Replay source or the following evaluation.

7.4 Equivalence and past-only isolation

Reference and optimized results remain canonically identical for:

- replay success/failure identity and metadata;
- candles and evaluation range;
- BUY/SELL evaluation index/time and signal index/time;
- delay_bar, matched_groups, details, and trace;
- average-price context and completed-cycle inputs; and
- MACD/OSC, RSI, moving averages, Bollinger, and Price Box configurations.

Appending extreme future candles after an identical first 100-candle prefix
does not change index 99 indicator values, BUY/SELL signals, or trace. Price Box
continues to use only the Historical prefix visible at that evaluation index.
