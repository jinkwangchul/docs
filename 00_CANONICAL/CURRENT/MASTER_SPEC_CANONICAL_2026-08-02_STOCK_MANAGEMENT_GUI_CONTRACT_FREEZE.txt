1. REVIEW_REQUIRED Display Contract

- REVIEW_REQUIRED is an independent protected state that requires operator review.
- REVIEW_REQUIRED is not a child state of running, emergency stop, or operation exclusion.
- A REVIEW_REQUIRED stock must not automatically transition back into an operable state.
- In GUI rows, REVIEW_REQUIRED is displayed as `검토종목`.
- A REVIEW_REQUIRED row uses orange foreground across the row text columns.
- This row-color contract is separate from the situation-signal contract.

2. Situation Signal Contract

- The situation signal column represents trading availability.
- REVIEW_REQUIRED displays a red situation signal.
- Emergency stop displays a red situation signal.
- Data mismatch displays a red situation signal.
- Monitoring/waiting displays the existing gray situation signal.
- Existing normal operation signal behavior is preserved unless a higher-priority protected condition applies.
- The situation signal foreground must not be overwritten by row-wide protection styling.

3. Status And Situation Sorting Contract

- The status column and situation column use the same state-rank Source of Truth for sorting.
- Clicking either column must produce the same row order for the same sort direction.
- REVIEW_REQUIRED and emergency stop have different ranks and must not be mixed into one sort group.
- The sort contract changes only sort keys; it does not change status labels, signal colors, row colors, filters, or counts.

4. Registered Stock Unregister Contract

- Unregister targets are the rows explicitly selected by the user in the registered-stock-status table.
- Whole visible lists must not be treated as unregister targets unless those rows are selected.
- A specific routine selection is not required when selected rows carry enough identity.
- Running stocks, emergency-stopped stocks, and REVIEW_REQUIRED stocks are unregister-blocked.
- Backend unregister execution receives only unregister-eligible stocks.
- Blocked stocks remain registered and are not passed to the backend.
- The result toast is exactly one line:

  `종목해제 N종목 | 해제불가 M종목`

- Both counts are always shown, including zero.
- The toast must not show stock names, stock codes, reasons, or extra words such as completion/success/processing.

5. Stock Register Entry From Performance Tree

- The auto-trade performance tree provides a `종목등록` entry for routine areas where a valid routine instance identity exists.
- Routine rows and stock rows may both be entry points to the same routine stock-register function.
- A stock-row `종목등록` action does not register the right-clicked stock.
- A stock row is used only to obtain its owning `instance_id`.
- The implementation must reconstruct normal routine metadata from that `instance_id` and open the same general routine stock-register dialog used by the routine-row path.
- Stock-row metadata such as stock code, stock name, stock path, stock status, and other stock-specific fields must not be passed as registration-dialog metadata.
- Current, past, and all performance views do not change the target routine identity.

6. Stock Register Dialog Contract

- The routine stock-register dialog title is:

  `<루틴명> - 종목등록`

- The routine name comes from the official routine metadata display value.
- The dialog has bottom buttons in this order:

  `등록`, `닫기`

- The `등록` button registers the currently selected search result through the same backend path as the existing double-click or Enter registration path.
- The button is disabled when no search result is selected and enabled when a result is selected.
- Search, search results, duplicate checks, backend registration, saving, and refresh contracts are unchanged.

  5. separator
