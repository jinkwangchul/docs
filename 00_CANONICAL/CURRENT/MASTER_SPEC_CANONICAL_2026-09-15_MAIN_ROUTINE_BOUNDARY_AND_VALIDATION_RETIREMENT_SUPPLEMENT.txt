4. MAIN ROUTINE INSTANCE DELETION VERIFICATION
======================================================================

4.1 Original error and classification

The former test
MainRoutineMonitoringDisplayTest.
test_main_routine_delete_no_confirmation_does_not_delete constructed a
types.SimpleNamespace as the Main window and passed an invalid instance id.
The real deletion-scope collector first raised ValueError("삭제할 등록 루틴을
찾을 수 없습니다."). The handler then attempted QMessageBox.warning(window,
...), and PyQt rejected the SimpleNamespace as argument 1 because it was not a
QWidget. The error was a test-fixture/type and repository-data defect, not
evidence that the Production handler required a changed deletion policy.

4.2 Corrected fixture boundary

The tests now construct a real gui_windows.MainWindow/QMainWindow object without
running Production initialization. Each test uses a temporary project root with
valid Routine package, Routine Instance, stock, and Runtime JSON fixtures. The
actual Main handler is:

  gui_windows.MainWindow.delete_routine_instance_from_main_table

The actual deletion-scope collector and, for allowed deletion, the actual
routine_instance_deletion_service are exercised. Only operator confirmation,
UI refresh/event output, and other external presentation effects are mocked.
No Broker, login, SendOrder, position writer, or user repository is invoked.

4.3 Verified outcomes

Cancellation:

- QMessageBox.No leaves the target instance present;
- the deletion service is not called;
- refresh is not called; and
- a byte snapshot of all temporary package, instance, stock, order-queue, and
  position files is identical before and after.

Allowed deletion:

- the real service removes only the approved target Routine Instance;
- its Routine package remains installed;
- an independent Routine Instance and both Routine packages remain unchanged;
- the Main refresh/event boundary is invoked after success; and
- no package auto-uninstall or unrelated data cleanup is introduced.

Protected deletion:

- an instance assigned to a stock is rejected by the real scope before the
  confirmation dialog;
- the operator receives the existing protection message; and
- the complete temporary repository byte snapshot remains unchanged.

Package absence is verified separately in a fresh subprocess and temporary
package root. With Indicator-Follow absent, generic Main/settings modules import,
an independent manifest Routine is discovered and evaluated, and its execution
admission succeeds. A missing Routine Instance remains fail-closed with
ROUTINE_GATE_UNAVAILABLE. This test does not claim automatic reassignment or
package removal behavior.
