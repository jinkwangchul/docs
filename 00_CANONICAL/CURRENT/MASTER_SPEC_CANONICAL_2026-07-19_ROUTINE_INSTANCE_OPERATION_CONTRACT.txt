11. Routine Type / Routine Instance Operation Contract

11.1 Identity and ownership

- Routine Type is a parent category and template. It supplies the common
  routine form and groups related registered routines, but it is not the
  direct execution or stock-assignment unit.
- Routine Instance is the actual settings, operation, and stock-assignment
  unit.
- A stock belongs directly to a Routine Instance, not directly to a parent
  Routine Type. Parent values are derived through child instances.

11.2 Routine tree presentation

- Preserve the existing parent/child tree and checkbox interaction model.
- A parent category name is displayed slightly larger than child instance
  names so the hierarchy is immediately visible without adding a separate
  panel or duplicate header.
- Parent aggregate text uses this format:

  Registered(value) | Running(value) | Stopped(value) | Error(value)

- The aggregate is visible while the parent is collapsed.
- While the parent is expanded, the aggregate is hidden by default and is
  shown temporarily only when the pointer is over the displayed parent-name
  text.
- The Registered Stock Status toolbar displays its entries in this fixed
  order: `전체 | 조기마감 강제종료`. The all-scope entry is a clickable `전체`
  badge using the same component and visual contract as the Routine Performance
  `전체` badge. `|` is a non-interactive separator between view scope and
  operation commands.
- The `전체` badge retains the existing view-only production entry point that
  selects the union of stocks registered under every current Routine Type and
  Routine Instance. This UI-form change does not alter its aggregation contract
  and does not invoke or reuse the Early Close or Forced Stop command backends.
- In the all-stocks view, the status summary begins with `전체` and uses
  `전체 그룹(N) 루틴(N) 종목(N) 실행(N) 정지(N) 검토(N)`. A parent or instance
  name is not shown because no single parent or instance owns that view scope.
- Status, Method, and Liquidation columns retain their existing Runtime
  indicator meanings in the all-stocks view. Only the query scope changes.

11.3 Parent operation commands and targets

- The parent context menu provides Early Close and Immediate Liquidation.
- The actual command targets are the checked child Routine Instances under
  that parent.
- Unchecked child instances are not affected by the parent command.
- The GUI remains a thin operation entry point and does not duplicate backend
  policy or order-processing logic.

11.4 Existing automatic-trading policy reuse

- Parent context-menu commands are additional entry points into the existing
  automatic-trading policies, not new close or liquidation policies.
- Existing policies for operation time, regular market operation, configured
  minutes before market close, market-order liquidation, carry-over, and
  unfilled orders remain authoritative.
- Early Close is not synonymous with immediate market-order liquidation. It
  follows the existing early-close and market-close settings and policy flow.
- Immediate Liquidation is a one-time command, not a persistent operating-mode
  change. A REQUESTED result records acceptance of the request only and does
  not mean that an order was queued, submitted, accepted, filled, or completed.

11.4.1 Individual Liquidation and Early Close One-shot Override Contract

- Environment settings define persistent default policy for automatic close,
  early close, and liquidation. A context menu may read those defaults to mark
  the initially selected method or time. This is read-only reference
  information that lets the operator compare the current default with the
  one-shot command being prepared; it is not the command's persistent state.
- Individual Liquidation (`개별청산`) is an operator-initiated, one-shot
  liquidation procedure for the selected stock. Its method (`시장가`,
  `현재가`, or `이월`) and `minutes_before_regular_close` value apply only to
  that invocation.
- Context-menu Early Close (`조기마감`) is also an operator-initiated, one-shot
  command. Its selected method and related execution options apply only to that
  invocation. Automatic Close (`자동마감`) remains the separate automatic
  procedure entered according to persistent settings and time policy.
- A context-menu selection is a command override. It must not modify
  `operation_policy.json`, the environment-setting `liquidation`,
  `early_close`, or `auto_close` defaults, or any other persistent default
  policy.
- The top Early Close button applies the current environment-setting default
  without an override UI. The context-menu Early Close entry may override that
  default for its current invocation only. Both use the same backend purpose
  and Runtime evidence boundary.
- The interpretation that an Individual Liquidation context-menu selection is
  saved as a per-stock persistent setting is retired. The interpretation that
  an Early Close context-menu selection changes an environment-setting default
  is also retired.
- The selected override travels with the invocation through the existing
  command or request boundary. Existing `OperationCommandRequest` fields are
  `target_scope`, `target_id`, `command`, `source`, `occurred_at`, and
  `command_id`. Early Close uses `command=EARLY_CLOSE`; its existing
  compatibility payload uses `EarlyCloseCompatibility.method` and
  `EarlyCloseCompatibility.policy`.
- Existing option names such as `method` and
  `minutes_before_regular_close` retain their current meanings when carried by
  the applicable execution request. This contract does not invent a duplicate
  command schema or Source of Truth.
- `IMMEDIATE_LIQUIDATION` is the existing Immediate Liquidation (`즉시청산`)
  command and must not be renamed or repurposed as Individual Liquidation.
- Opening a new context menu starts a new command choice. If an explicit
  in-progress, unconfirmed command edit state exists, that state may be shown;
  otherwise the menu shows the current environment-setting defaults. A value
  used by a completed one-shot command is never promoted to a default.
- The stock table Status, Method, and Liquidation columns are Runtime
  indicators. They display the state and policy actually accepted in Runtime,
  independent of whether the caller was the top button, a context menu, or
  another approved command entry point. Menu marker state is not a table
  indicator source.
- An accepted command records the selected override as part of that command or
  request evidence. It does not authorize a write to persistent default-policy
  files. Existing Queue, Final Send Gate, SendOrder, Chejan, and broker
  evidence boundaries remain unchanged.

11.4.2 Manual ATS Session-scoped Selection Contract

- `operation_policy.extra_sessions` is the persistent Source of Truth only for
  each ATS session's display name, start time, and end time. It does not apply
  an ATS session automatically to any stock.
- A manual-operation stock receives ATS applicability only when the operator
  selects one or more ATS sessions for that individual stock or a multi-stock
  selection in the ATS Settings UI.
- The per-stock ATS selection is Runtime state scoped to both the current
  trading date and the current program execution session. It is not a
  persistent stock setting and must not be restored from
  `config.json/manual_ats_sessions`.
- Program startup clears prior per-stock ATS selections. A new trading date,
  market-session end, or recovery classified as a new market session also
  invalidates and clears those selections. Clearing ATS selection must not
  change the stock's `CONTINUOUS` manual-operation mode.
- After reset, the ATS Settings UI starts with all ATS selections cleared for
  that stock. The stock continues as ordinary manual operation.
- `manual_operation.use_extra_session_1..3` is not an ATS auto-application
  policy. Legacy values must not make a stock ATS-enabled or order-eligible.
- `MANUAL_ATS_LIQUIDATION` is a one-shot command. Its execution boundary must
  verify both the stock's valid current Runtime ATS selection and the matching
  `operation_policy.extra_sessions` time definition. A selection from another
  trading date or program execution session is fail-closed.
- The accepted command evidence carries the selected ATS session keys,
  trading date, and program execution session identifier. Queue, Dispatch
  Claim, Final Send Gate, SendOrder, Chejan, and broker evidence contracts are
  unchanged.

11.5 Result presentation

- When authoritative real-trading results become available, each affected
  Routine Instance may display Trading Complete or Partially Complete.
- Completion determination must reuse the existing order-result and Chejan
  evidence flow. This Canonical does not define a new completion algorithm.
- Data inconsistency remains subject to the existing review-management policy
  and must not be disguised as a completion result.

11.6 Monitoring and aggregation

- Stock monitoring displays the assigned Routine Instance, not the parent
  Routine Type.
- A child aggregate is calculated from stocks assigned to that Routine
  Instance.
- A parent aggregate is the combined result of its child Routine Instances.
- The same Routine Instance identity must be used for assignment, monitoring,
  aggregation, review handling, and operation-command target resolution.

11.7 Safety boundary

- Reuse the existing backend and Operation Command Service.
- Do not duplicate business logic in GUI code.
- This documentation update does not change Queue, Final Send Gate, SendOrder,
  Chejan, runtime, or production code contracts.
